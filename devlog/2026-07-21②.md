## 1. PatientDetailOutletContextのPick

```tsx
type PatientDetailOutletContext = Pick<
  PatientOutletContext,
  "patient" | "updatePatient" | "usedRoomsForEdit"
>;
```

`PatientOutletContext`全体ではなく、`PatientDetail`が実際に使う項目だけを選んでいる。

### Pickを使う理由

- 使用する値を明示できる
- コンポーネントの役割が分かりやすくなる
- 不要なContextを含めずに済む

`PatientOutletContext`全体を指定しても動くが、`Pick`を使う方が必要な項目を理解しやすい。

## 2. useOutletContextの実行

```tsx
const { patient, updatePatient, usedRoomsForEdit } =
  useOutletContext<PatientDetailOutletContext>();
```

次のコードは、関数そのものを表す。

```tsx
useOutletContext<PatientDetailOutletContext>
```

末尾に`()`を付けると、関数を実行してContextを取得できる。

```tsx
useOutletContext<PatientDetailOutletContext>()
```

## 3. useFormの3つの型

```tsx
useForm<
  PatientInput,
  unknown,
  PatientOutput
>
```

それぞれの意味は次のとおり。

```text
PatientInput
→ Zodによる検証・変換前のフォーム入力値

unknown
→ resolverへ渡す追加Contextを使用しない

PatientOutput
→ Zodによる検証・変換後の値
```

変換前は、数値入力欄も文字列になる可能性がある。

```tsx
{
  room: "101",
  age: "70",
}
```

Zodによる変換後は数値になる。

```tsx
{
  room: 101,
  age: 70,
}
```

## 4. PatientInputでReturnTypeを使う理由

```tsx
export type PatientInput = z.input<
  ReturnType<typeof makePatientSchemaPartial>
>;

export type PatientOutput = z.output<
  ReturnType<typeof makePatientSchemaPartial>
>;
```

`makePatientSchemaPartial`はZodスキーマを返す関数。

```tsx
export const makePatientSchemaPartial = (
  usedRooms: number[],
) => {
  return z.object({
    // 患者用スキーマ
  });
};
```

`typeof makePatientSchemaPartial`では、関数そのものの型が取得される。

```tsx
(usedRooms: number[]) => Zodスキーマ
```

今回は関数が返すZodスキーマの型が必要なので、`ReturnType`を使用する。

```tsx
ReturnType<typeof makePatientSchemaPartial>
```

一方、`recordSchema`は関数ではなく、Zodスキーマが直接入った変数。

```tsx
export const recordSchema = z.object({
  // 看護記録用スキーマ
});
```

そのため、`ReturnType`は必要ない。

```tsx
export type RecordInput = z.input<typeof recordSchema>;
export type RecordOutput = z.output<typeof recordSchema>;
```

### 使い分け

```text
makePatientSchemaPartial
→ スキーマを返す関数
→ ReturnTypeが必要

recordSchema
→ スキーマが直接入った変数
→ typeofだけでよい
```

## 5. patientとdataを合体させる理由

```tsx
const patientToUpdate = {
  ...patient,
  ...data,
};
```

`patient`は、Outlet Contextから取得した患者オブジェクト。

```tsx
const { patient } =
  useOutletContext<PatientDetailOutletContext>();
```

`patient`の型は`Patient`なので、患者IDを含んでいる。

```tsx
export type Patient = {
  id: string;
  name: string;
  room: number;
  age?: number;
  disease?: string;
  history?: string;
  progress?: string;
};
```

一方、`data`は患者フォームの検証済みデータ。

```tsx
const handlePatientSubmit = async (
  data: PatientOutput,
): Promise<void> => {
```

`PatientOutput`は`makePatientSchemaPartial`から作られているため、フォーム項目だけを持っている。

```tsx
{
  name,
  room,
  age,
  disease,
  history,
  progress,
}
```

`data`には患者IDがない。

そこで、元の患者情報とフォームデータを合体させる。

```tsx
const patientToUpdate = {
  ...patient,
  ...data,
};
```

例えば、元の患者情報が次の場合、

```tsx
const patient = {
  id: "1",
  name: "変更前の名前",
  room: 101,
  age: 70,
};
```

フォームの検証済みデータが次の場合、

```tsx
const data = {
  name: "変更後の名前",
  room: 102,
  age: 71,
};
```

合体後は次のようになる。

```tsx
const patientToUpdate = {
  id: "1",
  name: "変更後の名前",
  room: 102,
  age: 71,
};
```

同じプロパティがある場合、後ろに書かれた値が優先される。

```tsx
{
  ...patient, // 元の患者情報
  ...data,    // 最新のフォーム値で上書き
}
```

### 重要な理解

```text
...patient
→ idを含む元の患者情報を展開する

...data
→ Zod検証後の最新フォーム情報を展開する

patientToUpdate
→ idを持った最新の患者情報になる
```

`...patient`は厳密には`id`だけを追加する処理ではなく、患者オブジェクト全体を展開する処理。

ただし、同じ項目は後ろの`...data`で上書きされるため、結果的に`data`に存在しない`id`が`patient`から引き継がれる。

## 6. updatePatientとresetの使い分け

```tsx
updatePatient(patientToUpdate);
reset(data);
```

`updatePatient`には、患者を特定する`id`と最新情報が必要。

```tsx
updatePatient(patientToUpdate);
```

`reset`にはフォーム項目の最新情報だけが必要。

```tsx
reset(data);
```

### 使い分け

```text
updatePatient(patientToUpdate)
→ idと最新の患者情報が必要

reset(data)
→ 最新のフォーム項目だけ必要
```

`reset(data)`は、フォームを空欄にする処理ではない。

```text
保存したdataを、
フォームの新しい基準値として設定する
```

そのため、次に編集画面を開いたときも、保存後の最新情報が表示される。

## 7. 更新結果を確認する理由

```tsx
const updatedPatient =
  await updatePatient(patientToUpdate);

if (!updatedPatient) {
  return;
}
```

`updatePatient`の戻り値は次の型。

```tsx
Promise<Patient | undefined>
```

API更新に失敗した場合、`updatePatient`内の`catch`でエラーを捕まえて`undefined`を返す。

```text
API更新に失敗
    ↓
catchでエラーを捕まえる
    ↓
undefinedを返す
```

次の判定がなければ、

```tsx
if (!updatedPatient) {
  return;
}
```

更新に失敗した場合でも、成功後の処理が実行される。

```tsx
reset(data);
clearErrors();
onErrorsChange?.({});
setIsEditing(false);
```

その結果、保存に失敗しているのに、編集画面が閉じて成功したように見えてしまう。

### 判定の目的

```text
更新成功
→ 後ろの処理へ進む
→ フォームを閉じる

更新失敗
→ returnで処理を終了
→ 入力内容と編集画面を残す
```

## 8. defaultValues

```tsx
const defaultValues = useMemo(
  () => ({
    name: patient?.name ?? "",
    room: patient?.room ?? "",
    age: patient?.age ?? "",
    disease: patient?.disease ?? "",
    history: patient?.history ?? "",
    progress: patient?.progress ?? "",
  }),
  [patient],
);
```

`defaultValues`は、現在の患者情報をフォームの初期値にするために作成している。

例えば、患者情報が次の場合、

```tsx
const patient = {
  id: "1",
  name: "山田太郎",
  room: 101,
  age: 70,
  disease: "肺炎",
};
```

フォームの初期値は次のようになる。

```tsx
{
  name: "山田太郎",
  room: 101,
  age: 70,
  disease: "肺炎",
  history: "",
  progress: "",
}
```

### `?? ""`の意味

```tsx
patient?.history ?? ""
```

```text
値がある
→ その値を使う

nullまたはundefined
→ 空文字を使う
```

### `[patient]`の意味

```tsx
[patient]
```

これはフォームへ入れる配列ではなく、`useMemo`の依存配列。

```text
patientが変わる
    ↓
defaultValuesを作り直す
```

`patient`が変わらなければ、前回作った`defaultValues`を再利用する。

## 今日のまとめ

- `Pick`で使用するContextだけを明示する
- `useOutletContext()`の`()`で関数を実行する
- `PatientInput`はZod変換前の型
- `PatientOutput`はZod変換後の型
- スキーマを返す関数には`ReturnType`を使う
- `recordSchema`はスキーマ変数なので`typeof`だけでよい
- `...patient`は`id`を含む元の患者情報を展開する
- `...data`は最新のフォーム情報で同じ項目を上書きする
- `updatePatient`には`id`を含む`patientToUpdate`を渡す
- `reset`にはフォーム項目だけを持つ`data`を渡す
- 更新失敗時は`return`して成功後の処理を実行させない
- `defaultValues`は現在の患者情報をフォームの初期値にする
- `[patient]`は`useMemo`の依存配列
