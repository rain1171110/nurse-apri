## 3. 看護記録更新をPrismaへ変更

看護記録本体とバイタル情報は別のテーブルなので、受信データを分ける。

```ts
const { vitals, ...recordData } = req.body;
```

例えば、次のデータを受信した場合、

```ts
{
  patientId: "患者ID",
  date: "2026-07-26",
  author: "岡﨑洋子",
  content: "状態良好",
  vitals: {
    T: 36.5,
    P: 70,
  },
}
```

次のように分けられる。

```ts
vitals;
// {
//   T: 36.5,
//   P: 70,
// }
```

```ts
recordData;
// {
//   patientId: "患者ID",
//   date: "2026-07-26",
//   author: "岡﨑洋子",
//   content: "状態良好",
// }
```

完成した更新処理は次のとおり。

```ts
app.put("/api/records/:id", async (req, res) => {
  try {
    const { id } = req.params;
    const { vitals, ...recordData } = req.body;

    const updatedRecord = await prisma.nursingRecord.update({
      where: {
        id,
      },
      data: {
        ...recordData,
        vitals: {
          upsert: {
            create: vitals,
            update: vitals,
          },
        },
      },
      include: {
        vitals: true,
      },
    });

    res.json(updatedRecord);
  } catch (error) {
    console.error("PUT /api/records/:id error:", error);
    res.status(500).json({ error: "Failed to update record" });
  }
});
```

### `upsert`とは

```ts
upsert: {
  create: vitals,
  update: vitals,
}
```

`upsert`は、次の処理をまとめたもの。

* バイタルが存在する場合：更新する
* バイタルが存在しない場合：新規作成する

## 4. 患者削除をPrismaへ変更

削除では、更新後の内容を渡す必要がない。

そのため、`data: req.body`は使用せず、削除対象を示す `where`だけを指定する。

```ts
app.delete("/api/patients/:id", async (req, res) => {
  try {
    const { id } = req.params;

    await prisma.patient.delete({
      where: {
        id,
      },
    });

    res.json({ id });
  } catch (error) {
    console.error("DELETE /api/patients/:id error:", error);
    res.status(500).json({ error: "Failed to delete patient" });
  }
});
```

### 削除と更新の違い

更新では `where`と`data`が必要。

```ts
await prisma.patient.update({
  where: {
    id,
  },
  data: req.body,
});
```

削除では `where`だけが必要。

```ts
await prisma.patient.delete({
  where: {
    id,
  },
});
```

### レスポンスの形

次のコードでは、IDだけの文字列が返る。

```ts
res.json(id);
```

```json
"32ded91d-..."
```

次のコードでは、`id`プロパティを持つオブジェクトが返る。

```ts
res.json({ id });
```

```json
{
  "id": "32ded91d-..."
}
```

フロントエンドの戻り値型に合わせて、オブジェクトで返す。

```ts
Promise<{ id: string }>
```

## 6. JSON保存用コードを削除

以前は、Node.jsのファイル操作機能を使って `data.json`を読み書きしていた。

```text
Express
  ↓
Node.jsのfs
  ↓
data.json
```

現在は、Prismaを通してPostgreSQLを操作している。

```text
Express
  ↓
Prisma
  ↓
PostgreSQL
```

そのため、次のimportが不要になった。

```ts
import { readFileSync, writeFileSync } from "node:fs";
import path from "node:path";
import { fileURLToPath } from "node:url";
import type {
  NursingRecord,
  Patient,
} from "./generated/prisma/client.js";
```

次の型も不要になった。

```ts
type AppData = {
  patients: Patient[];
  records: NursingRecord[];
};
```

`data.json`の場所を作るコードも不要になった。

```ts
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
const dataPath = path.join(__dirname, "data.json");
```

ファイルを読み書きする関数も不要になった。

```ts
const readData = (): AppData => {
  const raw = readFileSync(dataPath, "utf-8");
  return JSON.parse(raw) as AppData;
};

const writeData = (data: AppData): void => {
  writeFileSync(
    dataPath,
    JSON.stringify(data, null, 2),
    "utf-8",
  );
};
```

データ全体をJSONへ書き込んでいた `PUT /api/data`も不要になった。

現在は、各データを専用のAPIで操作している。

```text
POST   /api/patients

DELETE /api/patients/:id

POST   /api/records
```

## 7. 今日理解した重要ポイント

以前は、Node.jsを使用して `data.json`を読み書きしていた。

```ts

writeFileSync();
```

現在は、PostgreSQLがデータを保存・管理し、Prismaを使ってデータを操作している。

```ts

prisma.patient.update();
prisma.patient.delete();
```

ただし、Node.js自体を使わなくなったわけではない。

役割は次のとおり。

* Node.js：ExpressやPrismaを動かす実行環境
* Express：フロントエンドからのリクエストを受け取る

* PostgreSQL：データを実際に保存・管理する

## 2. PostgreSQLの`null`とZodの型エラーを修正

看護記録を編集すると、未入力のバイタル項目で次のエラーが発生した。

```text
Invalid input: expected string, received null
```

PostgreSQLでは、未入力の任意項目が`null`として返される。

```ts
{
  T: 35,
  P: 50,
  R: null,
  SBP: null,
  DBP: null,
  SPO2: null
}
```

以前の`optionalNumber`では、`undefined`は許可していたが、`null`は許可していなかった。

```ts
z.union([z.string(), z.number()]).optional()
```

`.optional()`を`.nullish()`へ変更した。

```ts
export const optionalNumber = (
  min: number,
  max: number,
  msgMin: string,
  msgMax: string,
) =>
  z
    .union([z.string(), z.number()])
    .nullish()
    .transform((v) => (v == null ? "" : String(v).trim()))
    .transform((v) => (v === "" ? undefined : Number(v)))
    .refine((v) => v === undefined || Number.isFinite(v), {
      message: "数字を入力して下さい",
    })
    .refine((v) => v === undefined || v >= min, {
      message: msgMin,
    })
    .refine((v) => v === undefined || v <= max, {
      message: msgMax,
    });
```

違いは以下のとおり。

```ts
.optional(); // undefinedを許可
.nullish();  // undefinedとnullを許可
```

変更後は、PostgreSQLから返された`null`がフォームの空欄として正しく扱われるようになった。

## 4. Expressの`req.body`に型を付けた

Expressでは、型を指定しない場合、`req.body`の中身をTypeScriptが正確に認識できない。

患者追加・編集で受け取るデータの型を作成した。

```ts
type CreatePatientBody = {
  name: string;
  room: number;
  age?: number;
  disease?: string;
  history?: string;
  progress?: string;
};
```

看護記録で受け取るバイタルと記録の型を作成した。

```ts
type VitalSignsBody = {
  T?: number;
  P?: number;
  R?: number;
  SBP?: number;
  DBP?: number;
  SPO2?: number;
};

type CreateRecordBody = {
  patientId: string;
  date: string;
  author: string;
  content?: string;
  vitals: VitalSignsBody;
};
```

Prismaが生成した`VitalSigns`型には、DB側で作られる`id`と`recordId`も含まれる。

そのため、フロントエンドから受け取るデータには、送信用の`VitalSignsBody`を使用した。

## 10. Expressのジェネリクスの順番

Expressのルートで使用した3つの型は、以下の順番になっている。

```ts
<Params, ResBody, ReqBody>
```

覚え方は以下のとおり。

```text
URLから受け取る → APIから返す → bodyで受け取る
```

使用例：

```ts
// :idなし、bodyあり
app.post<{}, {}, CreatePatientBody>
```

```ts
// :idあり、bodyあり
app.put<{ id: string }, {}, CreatePatientBody>
```

```ts
// :idあり、bodyなし
app.delete<{ id: string }>
```

今回の型指定では、以下の場所に型が反映される。

```ts
app.put<{ id: string }, {}, CreateRecordBody>(
  "/api/records/:id",
  async (req, res) => {
    req.params.id; // string
    req.body;      // CreateRecordBody
  },
);
```

この型引数の順番は、Expressの型定義ファイルで決められている。

```text
node_modules/@types/express-serve-static-core/index.d.ts
```

## 11. サーバー側の型チェック

フロントエンド側ではなく、サーバー側の`tsconfig.json`を明示して型チェックする必要がある。

```bash
npx tsc --project server/tsconfig.json --watch
```

以下のテストコードを一時的に追加した。

```ts
const test: string = req.body.room;
```

`room`は`number`型なので、TypeScriptが正しくエラーを検出した。

```text
Type 'number' is not assignable to type 'string'.
```

テストコードを削除した後は、型エラーがないことを確認した。

## 今日理解したこと

* JSONからPrisma/PostgreSQLへのCRUD移行が完了した。
* PostgreSQLの任意項目は`null`で返ることがある。
* Zodの`.optional()`は`undefined`、`.nullish()`は`undefined`と`null`を許可する。
* `req.body`に型を付けると、存在しないプロパティや型の間違いを検出できる。
* PrismaのDBモデル型と、フロントから受け取る入力型は役割が異なる。
* Expressの型引数は`<Params, ResBody, ReqBody>`の順番。
* 削除APIはbodyを使わず、URLの`:id`だけを使用する。
* サーバーの型チェックでは`server/tsconfig.json`を明示する。
* `F12`を使うと、関数や型がどこで定義されているか確認できる。
* TypeScriptの型は開発中の間違いを検出するが、実際に届く不正なデータの検証には別途バリデーションが必要。
