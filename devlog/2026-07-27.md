## 2. PostgreSQLの`null`とZodの型エラーを修正

看護記録を編集すると、未入力のバイタル項目で次のエラーが発生した。

```text
Invalid input: expected string, received null
```

PostgreSQLでは、未入力の任意項目が`null`として返される。

```ts
{
  T: 35,
  P: 50,
  R: null,
  SBP: null,
  DBP: null,
  SPO2: null
}
```

以前の`optionalNumber`では、`undefined`は許可していたが、`null`は許可していなかった。

```ts
z.union([z.string(), z.number()]).optional()
```

`.optional()`を`.nullish()`へ変更した。

```ts
export const optionalNumber = (
  min: number,
  max: number,
  msgMin: string,
  msgMax: string,
) =>
  z
    .union([z.string(), z.number()])
    .nullish()
    .transform((v) => (v == null ? "" : String(v).trim()))
    .transform((v) => (v === "" ? undefined : Number(v)))
    .refine((v) => v === undefined || Number.isFinite(v), {
      message: "数字を入力して下さい",
    })
    .refine((v) => v === undefined || v >= min, {
      message: msgMin,
    })
    .refine((v) => v === undefined || v <= max, {
      message: msgMax,
    });
```

違いは以下のとおり。

```ts
.optional(); // undefinedを許可
.nullish();  // undefinedとnullを許可
```

変更後は、PostgreSQLから返された`null`がフォームの空欄として正しく扱われるようになった。

## 4. Expressの`req.body`に型を付けた

Expressでは、型を指定しない場合、`req.body`の中身をTypeScriptが正確に認識できない。

患者追加・編集で受け取るデータの型を作成した。

```ts
type CreatePatientBody = {
  name: string;
  room: number;
  age?: number;
  disease?: string;
  history?: string;
  progress?: string;
};
```

看護記録で受け取るバイタルと記録の型を作成した。

```ts
type VitalSignsBody = {
  T?: number;
  P?: number;
  R?: number;
  SBP?: number;
  DBP?: number;
  SPO2?: number;
};

type CreateRecordBody = {
  patientId: string;
  date: string;
  author: string;
  content?: string;
  vitals: VitalSignsBody;
};
```

Prismaが生成した`VitalSigns`型には、DB側で作られる`id`と`recordId`も含まれる。

そのため、フロントエンドから受け取るデータには、送信用の`VitalSignsBody`を使用した。

## 8. 看護記録編集APIの型付け

```ts
app.put<{ id: string }, {}, CreateRecordBody>(
  "/api/records/:id",
  async (req, res) => {
    try {
      const { id } = req.params;
      const { vitals, ...recordData } = req.body;

      const updatedRecord = await prisma.nursingRecord.update({
        where: {
          id,
        },
        data: {
          ...recordData,
          vitals: {
            upsert: {
              create: vitals,
              update: vitals,
            },
          },
        },
        include: {
          vitals: true,
        },
      });

      res.json(updatedRecord);
    } catch (error) {
      console.error("PUT /api/records/:id error:", error);
      res.status(500).json({ error: "Failed to update record" });
    }
  },
);
```

`upsert`は、関連するバイタルの有無によって処理を切り替える。

```text
バイタルが存在する → update
バイタルが存在しない → create
```

## 10. Expressのジェネリクスの順番

Expressのルートで使用した3つの型は、以下の順番になっている。

```ts
<Params, ResBody, ReqBody>
```

覚え方は以下のとおり。

```text
URLから受け取る → APIから返す → bodyで受け取る
```

使用例：

```ts
// :idなし、bodyあり
app.post<{}, {}, CreatePatientBody>
```

```ts
// :idあり、bodyあり
app.put<{ id: string }, {}, CreatePatientBody>
```

```ts
// :idあり、bodyなし
app.delete<{ id: string }>
```

今回の型指定では、以下の場所に型が反映される。

```ts
app.put<{ id: string }, {}, CreateRecordBody>(
  "/api/records/:id",
  async (req, res) => {
    req.params.id; // string
    req.body;      // CreateRecordBody
  },
);
```

この型引数の順番は、Expressの型定義ファイルで決められている。

```text
node_modules/@types/express-serve-static-core/index.d.ts
```

## 今日理解したこと

* JSONからPrisma/PostgreSQLへのCRUD移行が完了した。
* PostgreSQLの任意項目は`null`で返ることがある。
* Zodの`.optional()`は`undefined`、`.nullish()`は`undefined`と`null`を許可する。
* `req.body`に型を付けると、存在しないプロパティや型の間違いを検出できる。
* PrismaのDBモデル型と、フロントから受け取る入力型は役割が異なる。
* Expressの型引数は`<Params, ResBody, ReqBody>`の順番。
* 削除APIはbodyを使わず、URLの`:id`だけを使用する。
* サーバーの型チェックでは`server/tsconfig.json`を明示する。
* `F12`を使うと、関数や型がどこで定義されているか確認できる。
* TypeScriptの型は開発中の間違いを検出するが、実際に届く不正なデータの検証には別途バリデーションが必要。
