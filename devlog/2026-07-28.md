## 1. 患者データのZod検証

患者の追加・更新時に、`req.body`をそのままPrismaへ渡さず、Zodで検証するように変更した。

```ts
const result = createPatientSchema.safeParse(req.body);

if (!result.success) {
  res.status(400).json({
    error: "Invalid patient data",
    details: result.error.flatten(),
  });
  return;
}
```

検証に成功した場合は、未検証の`req.body`ではなく、検証済みの`result.data`をPrismaへ渡す。

```ts
const newPatient = await prisma.patient.create({
  data: result.data,
});
```

### `return`が必要な理由

```ts
if (!result.success) {
  res.status(400).json({
    error: "Invalid patient data",
    details: result.error.flatten(),
  });
  return;
}
```

`return`には、次の2つの役割がある。

* エラーレスポンスを返した後に、Prismaの処理へ進ませない
* TypeScriptに、これより下では検証に成功していると判断させる

## 2. 看護記録データのZod検証

看護記録の追加・更新でも、`createRecordSchema`を使ってデータを検証するように変更した。

```ts
const result = createRecordSchema.safeParse(req.body);

if (!result.success) {
  res.status(400).json({
    error: "Invalid record data",
    details: result.error.flatten(),
  });
  return;
}
```

検証後のデータを、看護記録本体とバイタルに分ける。

```ts
const { vitals, ...recordData } = result.data;
```

* `vitals`：体温、脈拍、呼吸数、血圧、SPO2
* `recordData`：`patientId`、日付、記録者、記録内容

## 3. バックエンドのZodスキーマ

```ts
import { z } from "zod";

export const createPatientSchema = z.object({
  name: z.string().min(1, "氏名は必須です"),
  room: z.number().int().min(1).max(999),
  age: z.number().int().min(0).max(150).optional(),
  disease: z.string().optional(),
  history: z.string().optional(),
  progress: z.string().optional(),
});

export type CreatePatientBody = z.infer<typeof createPatientSchema>;

export const createRecordSchema = z.object({
  patientId: z.string().min(1, "患者IDは必須"),
  date: z.string().min(1, "日付は必須"),
  author: z.string().min(1, "記録者は必須"),
  content: z.string().optional(),

  vitals: z.object({
    T: z.number().min(35).max(42).optional(),
    P: z.number().int().min(0).max(200).optional(),
    R: z.number().int().min(0).max(40).optional(),
    SBP: z.number().int().min(0).max(250).optional(),
    DBP: z.number().int().min(0).max(150).optional(),
    SPO2: z.number().int().min(0).max(100).optional(),
  }),
});

export type CreateRecordBody = z.infer<typeof createRecordSchema>;
```

### 体温から`.int()`を外した理由

体温は`36.5`などの小数になるため、整数だけを許可する`.int()`は使用しない。

```ts
T: z.number().min(35).max(42).optional(),
```

その他の脈拍や呼吸数などは整数として扱う。

```ts
P: z.number().int().min(0).max(200).optional(),
```

## 4. 看護記録の追加処理

```ts
app.post<{}, {}, CreateRecordBody>("/api/records", async (req, res) => {
  try {
    const result = createRecordSchema.safeParse(req.body);

    if (!result.success) {
      res.status(400).json({
        error: "Invalid record data",
        details: result.error.flatten(),
      });
      return;
    }

    const { vitals, ...recordData } = result.data;

    const newRecord = await prisma.nursingRecord.create({
      data: {
        ...recordData,
        vitals: {
          create: vitals,
        },
      },
      include: {
        vitals: true,
      },
    });

    res.status(201).json(newRecord);
  } catch (error) {
    console.error("POST /api/records error", error);
    res.status(500).json({
      error: "Failed to create record",
    });
  }
});
```

`vitals: { create: vitals }`により、看護記録と関連するバイタルを同時に作成できる。

## 5. 看護記録の更新処理

```ts
app.put<{ id: string }, {}, CreateRecordBody>(
  "/api/records/:id",
  async (req, res) => {
    try {
      const result = createRecordSchema.safeParse(req.body);

      if (!result.success) {
        res.status(400).json({
          error: "Invalid record data",
          details: result.error.flatten(),
        });
        return;
      }

      const { id } = req.params;
      const { vitals, ...recordData } = result.data;

      const updatedRecord = await prisma.nursingRecord.update({
        where: {
          id,
        },
        data: {
          ...recordData,
          vitals: {
            upsert: {
              create: vitals,
              update: vitals,
            },
          },
        },
        include: {
          vitals: true,
        },
      });

      res.json(updatedRecord);
    } catch (error) {
      console.error("PUT /api/records/:id error:", error);
      res.status(500).json({
        error: "Failed to update record",
      });
    }
  },
);
```

`upsert`によって、バイタルが存在する場合は更新し、存在しない場合は新しく作成する。

## 6. `patientId`が必要な理由

患者を作成するとき、フロントエンドからは`id`を送信しない。

```ts
{
  name: "鈴木次郎",
  room: 108
}
```

患者IDは、Prismaスキーマの次の設定によって自動作成される。

```prisma
id String @id @default(uuid())
```

一方、看護記録を作成するときは、どの患者の記録なのかを指定する必要がある。

そのため、看護記録には既存患者のIDを`patientId`として入れる。

```ts
{
  patientId: "9e749e4a-480e-477b-8057-909f572abccc",
  date: "2026-07-28",
  author: "岡崎洋子",
  vitals: {
    T: 35,
    P: 50
  }
}
```

バックエンドでは、次のZodスキーマで`patientId`が送信されているか確認する。

```ts
patientId: z.string().min(1, "患者IDは必須"),
```

これは患者IDを新しく作る処理ではなく、既存患者のIDが送られてきたかを検証する処理である。

## 7. `patient.id`から`patientId`への流れ

看護記録フォームの送信処理で、次のように`addRecord`を呼び出している。

```ts
const handleAddRecordSubmit = async (
  data: RecordOutput,
): Promise<void> => {
  const savedRecord = await addRecord(data, patient.id);

  if (!savedRecord) {
    return;
  }

  setIsAdding(false);
  setFormData(createEmptyRecord());
};
```

呼び出し時の対応関係は次のとおり。

```ts
addRecord(data, patient.id);
          ↓         ↓
       record    patientId
```

App.tsxでは、次の引数名で受け取る。

```ts
const addRecord = async (
  record: RecordOutput,
  patientId: string,
): Promise<NursingRecord | undefined> => {
```

JavaScriptでは、引数は名前ではなく順番で対応する。

```ts
record === data;
patientId === patient.id;
```

同じ値を関数の中で別の変数名によって扱っている。

## 8. フォームデータと患者IDの合体

App.tsxでは、フォームデータと患者IDを合体させてAPI送信用データを作る。

```ts
const recordToAdd: Omit<NursingRecord, "id"> = {
  ...record,
  patientId,
};
```

次の省略記法が使われている。

```ts
patientId,
```

これは次と同じ意味。

```ts
patientId: patientId,
```

* 左側：オブジェクトのプロパティ名
* 右側：関数の引数で受け取った値

完成するデータは次のようになる。

```ts
{
  date: "2026-07-28",
  author: "岡崎洋子",
  content: "",
  vitals: {
    T: 35,
    P: 50
  },
  patientId: "9e749e4a-480e-477b-8057-909f572abccc"
}
```

## 10. CRUDの動作確認

実際に次の処理が動作することを確認した。

* 患者の追加

* 患者の更新
* 患者の削除

* 看護記録の削除
* 看護記録とバイタルの関連取得
* 患者削除時の関連記録の自動削除

患者を削除すると、その患者の看護記録とバイタルも削除された。

これはPrismaスキーマの`onDelete: Cascade`が機能しているためである。

```prisma
patient Patient @relation(
  fields: [patientId],
  references: [id],
  onDelete: Cascade
)
```

## 今日理解したこと

* TypeScriptの型だけでは、実際にAPIへ送られてくるデータを検証できない
* Zodを使うと、実行時の`req.body`を検証できる
* Prismaには、未検証の`req.body`ではなく`result.data`を渡す
* 検証失敗時は`return`で処理を終了する
* 患者IDは患者作成時にPrismaがUUIDとして作成する
* 看護記録の`patientId`には、既存患者の`id`を入れる
* 関数の引数は変数名ではなく順番で対応する
* `record ← data`は、値が変化したのではなく、関数内での呼び名が変わっただけ
* フロントエンドのフォーム用スキーマと、バックエンドのAPI用スキーマでは検証対象が異なる
* `onDelete: Cascade`により、患者削除時に関連データも削除できる
