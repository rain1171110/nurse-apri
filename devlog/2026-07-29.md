## 1. `patientId`の流れ

記録追加時の`patientId`は、フロントから送信され、サーバーの`req.body`に入る。

```ts
const result = createRecordSchema.safeParse(req.body);
const { vitals, ...recordData } = result.data;
```

`vitals`以外のデータは、すべて`recordData`に入る。

```ts
const recordData = {
  patientId: "患者ID",
  date: "2026-07-29",
  author: "岡﨑",
  content: "体調は安定",
};
```

その後、`...recordData`によって`patientId`もPrismaへ渡される。

```ts
const newRecord = await prisma.nursingRecord.create({
  data: {
    ...recordData,
    vitals: {
      create: vitals,
    },
  },
});
```

### `id`と`patientId`の違い

- `id`：記録自身のID
- `patientId`：その記録が所属する患者のID

```ts
const { id } = req.params;
const { vitals, ...recordData } = result.data;
```

## 2. `.optional()`と`.nullish()`の違い

```ts
z.string().optional();
```

`.optional()`は、通常の値と`undefined`を許可する。

```ts
"文字列";
undefined;
```

`null`は許可されない。

```ts
z.string().nullish();
```

`.nullish()`は、通常の値・`undefined`・`null`を許可する。

```ts
"文字列";
undefined;
null;
```

| Zod | `undefined` | `null` |
|---|---:|---:|
| `.optional()` | 許可 | 不可 |
| `.nullable()` | 不可 | 許可 |
| `.nullish()` | 許可 | 許可 |

## 5. 部屋番号の重複エラー処理

`Patient`の`room`には、`@unique`が設定されている。

```prisma
room Int @unique
```

そのため、同じ部屋番号を保存しようとすると、PostgreSQLが保存を拒否し、Prismaから`P2002`が発生する。

### 変更前

重複保存自体は防げていたが、すべて`500`として返していた。

```text
PostgreSQLが重複を拒否
        ↓
PrismaがP2002を出す
        ↓
Expressが500を返す
```

### 変更後

`P2002`を判定し、重複を表す`409 Conflict`を返すようにした。

```text
PostgreSQLが重複を拒否
        ↓
PrismaがP2002を出す
        ↓
ExpressがP2002を判定
        ↓
409 Conflictを返す
```

## 6. `catch`の`error`が`unknown`になる理由

```ts
catch (error)
```

`catch`には、Prismaエラーだけでなく、文字列や別のオブジェクトなどが入る可能性がある。

そのため、TypeScriptでは`error`が`unknown`になる。

```ts
// error: unknown
```

次のように`any`を付けると赤線は消えるが、型チェックも無効になるため使用しなかった。

```ts
catch (error: any)
```

今回は、条件を順番に確認して、安全に`code`を使用した。

```ts
if (
  typeof error === "object" &&
  error !== null &&
  "code" in error &&
  error.code === "P2002"
) {
  // P2002の処理
}
```

確認している内容は次のとおり。

```ts
typeof error === "object"
```

`error`がオブジェクトか確認する。

```ts
error !== null
```

`null`を除外する。

```ts
"code" in error
```

`code`プロパティが存在するか確認する。

```ts
error.code === "P2002"
```

Prismaの重複エラーか確認する。

## 7. 患者追加時の完成コード

```ts
app.post<{}, {}, CreatePatientBody>("/api/patients", async (req, res) => {
  try {
    const result = createPatientSchema.safeParse(req.body);

    if (!result.success) {
      res.status(400).json({
        error: "Invalid patient data",
        details: result.error.flatten(),
      });
      return;
    }

    const newPatient = await prisma.patient.create({
      data: result.data,
    });

    res.status(201).json(newPatient);
  } catch (error) {
    if (
      typeof error === "object" &&
      error !== null &&
      "code" in error &&
      error.code === "P2002"
    ) {
      res.status(409).json({
        error: "This room number is already in use",
      });
      return;
    }

    console.error("POST /api/patients error", error);
    res.status(500).json({
      error: "Failed to create patient",
    });
  }
});
```

## 8. 患者編集時の重複処理

患者を編集するときも、既に使用されている部屋番号へ変更すると`P2002`が発生する。

そのため、`PUT /api/patients/:id`にも同じ処理を追加した。

```ts
app.put<{ id: string }, {}, CreatePatientBody>(
  "/api/patients/:id",
  async (req, res) => {
    try {
      const result = createPatientSchema.safeParse(req.body);

      if (!result.success) {
        res.status(400).json({
          error: "Invalid patient data",
          details: result.error.flatten(),
        });
        return;
      }

      const { id } = req.params;

      const updatedPatient = await prisma.patient.update({
        where: {
          id,
        },
        data: result.data,
      });

      res.json(updatedPatient);
    } catch (error) {
      if (
        typeof error === "object" &&
        error !== null &&
        "code" in error &&
        error.code === "P2002"
      ) {
        res.status(409).json({
          error: "This room number is already in use",
        });
        return;
      }

      console.error("PUT /api/patients/:id error:", error);
      res.status(500).json({
        error: "Failed to update patient",
      });
    }
  },
);
```

## 9. フロント・バックエンド・DBの役割

部屋番号の重複は、3段階で確認される。

| 場所 | 役割 |
|---|---|
| フロント | 入力時にすぐエラーを表示する |
| バックエンド | Prismaのエラーを適切なHTTPエラーへ変換する |
| PostgreSQL | `@unique`によって重複保存を確実に防ぐ |

```text
フロント
「この部屋番号は使用されています」
        ↓
バックエンド
「PrismaのP2002なら409を返す」
        ↓
PostgreSQL
「@uniqueなので重複保存を拒否する」
```

今回追加した処理は、重複保存を新しく防ぐ処理ではない。

重複保存は、もともとPostgreSQLの`@unique`によって防がれていた。

今回行ったのは、Prismaの`P2002`をバックエンドで判定し、原因不明の`500`ではなく、重複を示す`409`へ変換する処理である。

## 今日理解したこと

- `patientId`は`recordData`に含まれてPrismaへ渡される
- `id`は記録自身、`patientId`は所属する患者を表す
- `.optional()`は`undefined`を許可する
- `.nullish()`は`undefined`と`null`を許可する
- `npm run`は`package.json`のスクリプトを実行する
- `npx prisma`はPrisma CLIを直接実行する
- `catch`の`error`は安全のため`unknown`になる
- `P2002`は一意制約の重複エラー
- `409`は既存データとの競合を表す
- 重複保存を防ぐのはPostgreSQLの`@unique`
- バックエンドはPrismaエラーを適切なHTTPレスポンスへ変換する
