## 1. `safeParse()`の役割

```ts
const result = createPatientSchema.safeParse(req.body);
```

`safeParse()`は、受け取ったデータがZodスキーマのルールに合っているか検証するメソッド。

* 成功：`success: true`と検証済みの`data`を返す
* 失敗：`success: false`と`error`を返す
* 検証に失敗しても例外を投げない

```ts
const result = createPatientSchema.safeParse(req.body);

if (!result.success) {
  res.status(400).json({
    error: "Invalid patient data",
    details: result.error.flatten(),
  });
  return;
}
```

検証成功後は、元の`req.body`ではなく、検証済みの`result.data`をデータベースへ渡す。

```ts
const newPatient = await prisma.patient.create({
  data: result.data,
});
```

---

## 2. `flatten()`の役割

```ts
details: result.error.flatten(),
```

`flatten()`は、Zodの複雑なエラー情報を、フロントエンドで扱いやすい形に整理するメソッド。

```json
{
  "formErrors": [],
  "fieldErrors": {
    "name": ["氏名を入力してください"],
    "room": ["部屋番号は1以上で入力してください"]
  }
}
```

* `fieldErrors`：`name`や`room`など、入力項目ごとのエラー
* `formErrors`：特定の項目ではなく、フォーム全体に関係するエラー

`flatten()`がエラーを検出するのではなく、`safeParse()`で検出されたエラーを整理している。

## 3. 現在のフロント側の問題

現在の`createPatientApi`では、APIが失敗した場合にHTTPステータスしか取得していない。

```ts
if (!response.ok) {
  throw new Error(`API error: ${response.status}`);
}
```

そのため、バックエンドが次のエラーを返しても、

```ts
res.status(409).json({
  error: "This room number is already in use",
});
```

フロントエンドには次のメッセージしか渡らない。

```text
API error: 409
```

## 4. バックエンドのエラーをフロントへ渡す

バックエンドから返されたJSONを読み取り、そのメッセージを`Error`として投げ直す。

```ts
export const createPatientApi = async (
  patient: Omit<Patient, "id">,
): Promise<Patient> => {
  const response = await fetch(`${API_BASE}/patients`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(patient),
  });

  if (!response.ok) {
    const errorData: { error?: string } = await response.json();

    throw new Error(
      errorData.error ?? `API error: ${response.status}`,
    );
  }

  const data: Patient = await response.json();
  return data;
};
```

この処理によって、次のようにエラーがつながる。

```text
バックエンド
「This room number is already in use」
        ↓
api.tsでresponse.json()を実行
        ↓
throw new Error(errorData.error)
        ↓
App.tsxのcatchで受け取る
        ↓
setApiError(error.message)
        ↓
Reactの画面に表示
```

---

## 5. `??`の意味

```ts
errorData.error ?? `API error: ${response.status}`
```

`??`は、左側が`null`または`undefined`の場合に、右側の値を使用する演算子。

* `errorData.error`がある：バックエンドのメッセージを使用
* `errorData.error`がない：HTTPステータスを使用

## 6. `AddPatientForm`の役割

APIエラーの状態は`App.tsx`で管理しているため、基本的には`AddPatientForm.tsx`へ直接`apiError`の処理を追加する必要はない。

`AddPatientForm`には、すでに次の処理がある。

```ts
const savedPatient = await onSubmit(data);

if (!savedPatient) {
  return;
}

reset();
setShowAddForm(false);
```

APIエラーが発生して`onSubmit()`から`undefined`が返ると、次の処理で終了する。

```ts
if (!savedPatient) {
  return;
}
```

そのため、エラー発生時には以下の成功後の処理は実行されない。

```ts
reset();
setShowAddForm(false);
```

結果として、入力フォームは閉じずにそのまま残る。

## 今日の理解

* `safeParse()`は、データがZodスキーマに合っているか安全に検証する
* `flatten()`は、Zodエラーを項目別に扱いやすく整理する
* `response.ok`が`false`の場合は、レスポンス本文を自動では利用できない
* `response.json()`でバックエンドのエラーメッセージを読み取る必要がある
* 読み取ったメッセージを`throw new Error()`で`App.tsx`の`catch`へ渡せる
* `setApiError()`で状態に保存した後、JSXで描画すると画面に表示できる
* APIエラー時は患者追加フォームを閉じず、入力内容を残す設計になっている
