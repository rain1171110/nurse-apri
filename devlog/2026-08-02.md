## 1. `Error`オブジェクトの確認

```ts
if (error instanceof Error) {
  setApiError(error.message);
}
```

`error instanceof Error`は、`error`がJavaScript標準の`Error`クラスから作られたオブジェクトか確認している。

Zodのエラーかどうかを確認しているわけではない。

```ts
throw new Error("This room number is already in use");
```

`new Error()`で作られたオブジェクトには、渡した文字列が`message`として保存される。

```ts
error.message;
// "This room number is already in use"
```

処理の流れは次のとおり。

```text
new Error("エラーメッセージ")
        ↓
throw
        ↓
catch (error)
        ↓
error instanceof Error
        ↓
error.message
```

---

## 2. API関数でバックエンドのエラーを受け取る

これまでは、HTTPステータスだけを使ってエラーを作っていた。

```ts
if (!response.ok) {
  throw new Error(`API error:${response.status}`);
}
```

この場合、画面には次のような情報しか表示できない。

```text
API error:409
```

バックエンドが返した具体的なメッセージを使うため、次のように変更した。

```ts
if (!response.ok) {
  const errorData: { error?: string } = await response.json();

  throw new Error(
    errorData.error ?? `API error:${response.status}`,
  );
}
```

`errorData.error`にメッセージがあれば、それを使用する。

メッセージが`undefined`または`null`なら、`??`の右側を予備メッセージとして使用する。

```ts
errorData.error ?? `API error:${response.status}`;
```

## 3. 患者APIのエラー処理

`updatePatientApi`と`deletePatientApi`で、バックエンドのメッセージを受け取れるようにした。

```ts
export const updatePatientApi = async (
  id: string,
  patient: Omit<Patient, "id">,
): Promise<Patient> => {
  const response = await fetch(`${API_BASE}/patients/${id}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(patient),
  });

  if (!response.ok) {
    const errorData: { error?: string } = await response.json();

    throw new Error(
      errorData.error ?? `API error:${response.status}`,
    );
  }

  const data: Patient = await response.json();
  return data;
};
```

```ts
export const deletePatientApi = async (
  id: string,
): Promise<{ id: string }> => {
  const response = await fetch(`${API_BASE}/patients/${id}`, {
    method: "DELETE",
  });

  if (!response.ok) {
    const errorData: { error?: string } = await response.json();

    throw new Error(
      errorData.error ?? `API error:${response.status}`,
    );
  }

  const data: { id: string } = await response.json();
  return data;
};
```

## 5. App.tsxでエラーを受け取る

患者と看護記録の追加・更新・削除処理で、API関数から投げられたエラーを受け取るように統一した。

```ts
catch (error) {
  console.error("処理に失敗しました", error);

  if (error instanceof Error) {
    setApiError(error.message);
  } else {
    setApiError("処理に失敗しました");
  }

  return undefined;
}
```

削除処理では、失敗時に`false`を返す。

```ts
catch (error) {
  console.error("削除に失敗しました", error);

  if (error instanceof Error) {
    setApiError(error.message);
  } else {
    setApiError("削除に失敗しました");
  }

  return false;
}
```

戻り値の役割は次のとおり。

```text
更新成功 → 更新後のデータ
更新失敗 → undefined

削除成功 → true
削除失敗 → false
```

## 6. PatientPageでAPIエラーを表示

これまでは`apiError`を`PatientList`にしか渡していなかったため、患者ページ上では看護記録などのAPIエラーを表示できなかった。

`App.tsx`から`PatientPage`へ`apiError`を渡した。

```tsx
<PatientPage
  patients={appData.patients}
  records={appData.records}
  apiError={apiError}
  updatePatient={updatePatient}
  addRecord={addRecord}
  updateRecord={updateRecord}
  deleteRecord={deleteRecord}
  deletePatient={deletePatient}
/>
```

`PatientPageProps`にも型を追加した。

```ts
type PatientPageProps = {
  patients: Patient[];
  records: NursingRecord[];
  apiError: string;
} & Pick<
  PatientOutletContext,
  | "updatePatient"
  | "updateRecord"
  | "deleteRecord"
  | "deletePatient"
  | "addRecord"
>;
```

`PatientPage`で`apiError`を受け取り、`Outlet`と一緒に画面へ返した。

```tsx
return (
  <>
    {apiError && <p className="api-error">{apiError}</p>}
    <Outlet context={outletContext} />
  </>
);
```

次のように`return`の外側へJSXを書いても、Reactへ返されないため画面には表示されない。

```tsx
// 表示されない
{
  apiError && <p>{apiError}</p>;
}
```

画面へ表示したいJSXは、`return`の中に入れる必要がある。

## 7. フロントとバックエンドの二重チェック

通常、病室番号の重複はフロント側のZodが先に検出する。

```text
病室番号を入力
      ↓
フロントのZodが重複を検出
      ↓
APIを呼び出さずにエラーを表示
```

しかし、別のブラウザやタブで情報が変更されると、フロントが持っている情報が古くなる場合がある。

```text
タブA：病室111は空いていると思っている
タブB：別の患者を病室111へ変更
DB：病室111は使用中
```

この状態でタブAから病室111へ更新すると、フロントの検証は通るが、データベースが重複を検出する。

```text
フロントのZodを通過
      ↓
バックエンドへPUTリクエスト
      ↓
PostgreSQLが重複を検出
      ↓
PrismaがP2002を発生
      ↓
バックエンドが409を返す
      ↓
フロントでエラーを表示
```

実際に2つのタブを使って確認し、次のエラーがコンソールと画面に表示された。

```text
Error: This room number is already in use
```

これにより、フロントからバックエンドまでエラー処理がつながっていることを確認できた。

## 8. バックエンドのメッセージを日英併記

バックエンドのエラーメッセージを、英語と日本語の両方で表示するように変更した。

### 病室番号の重複

```ts
res.status(409).json({
  error:
    "This room number is already in use / この部屋番号はすでに使用されています",
});
```

### 患者が存在しない

```ts
res.status(404).json({
  error: "Patient not found / 患者が見つかりません",
});
```

### 看護記録が存在しない

```ts
res.status(404).json({
  error: "Record not found / 看護記録が見つかりません",
});
```

PrismaエラーとHTTPステータスの対応は次のとおり。

```text
P2002 → 409 Conflict
一意制約違反（病室番号の重複）

P2003 → 404 Not Found
関連する患者が存在しない

P2025 → 404 Not Found
更新・削除対象が存在しない
```

`P2025`と一般的な`500`エラーは意味が異なる。

```text
P2025・404
→ 更新・削除しようとした対象が存在しない

500
→ サーバー内部の問題で処理に失敗した
```

## 今日理解したこと

* `error instanceof Error`は、JavaScript標準の`Error`オブジェクトか確認している
* `new Error("メッセージ")`の文字列は`.message`に保存される
* `throw`されたエラーは、呼び出し元の`catch`へ渡される
* `response.ok`が`false`なら、HTTPリクエストは成功していない
* `response.json()`でバックエンドのエラーメッセージを取得できる
* `??`を使うと、メッセージがない場合の予備メッセージを設定できる
* JSXは`return`の中に入れなければ画面に表示されない
* フロントの検証は利用者へ素早くエラーを伝える役割がある
* バックエンドとデータベースは、最新のデータを使って最終確認する
* データベースを正しい情報源として管理することで、複数ユーザーによる変更にも対応できる
* フロントとバックエンドの二重チェックによって、使いやすさとデータの安全性を両立できる

```ts
if (
  typeof error === "object" &&
  error !== null &&
  "code" in error &&
  error.code === "P2002"

  res.status(409).json({
    error:
```

```text

↓
App.tsxのcatchが受け取る
↓
setApiError(error.message)
↓
画面にエラーを表示
```

コンソールには、次の呼び出し順も表示された。

