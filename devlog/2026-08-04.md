## 1. 2つのタブを使った重複登録の確認

アプリを2つのタブで開いた状態で、一方のタブから登録済みの部屋番号を、もう一方のタブから登録した。

フロント側の患者一覧はタブ間で自動同期されないため、フロントのZodでは重複を検出できなかった。

しかし、バックエンドとPostgreSQLでは重複を検出できた。

```text
タブAで部屋番号3を登録
        ↓
タブBは古い患者一覧を保持
        ↓
タブBのフロント側チェックを通過
        ↓
バックエンドへリクエスト
        ↓
PostgreSQLの一意制約で重複を検出
        ↓
PrismaのP2002
        ↓
HTTP 409
        ↓
フロントにエラーメッセージを表示
```

フロントだけでなく、バックエンドとデータベースでも重複を防ぐ必要性を確認できた。

## 2. APIエラー時に患者一覧が消える原因

`PatientList.tsx`で、患者一覧に次の表示条件を設定していた。

```tsx
{!isLoading && !apiError && (
  <section className="section">
    {/* 患者一覧 */}
  </section>
)}
```

`apiError`に文字列が入ると、`!apiError`が`false`になる。

そのため、エラー発生時に`section`全体が非表示になり、患者一覧と追加フォームが消えていた。

修正後は、`apiError`を表示条件から外した。

```tsx
{!isLoading && (
  <section className="section">
    {/* 患者一覧 */}
  </section>
)}
```

これにより、APIエラーが発生しても患者一覧と入力フォームが表示されたままになった。

## 3. APIエラー表示をApp.tsxへ集約

以前は`PatientList`と`PatientPage`の両方でエラーを表示していた。

APIエラーは患者一覧、患者編集、看護記録など、どの画面でも発生する可能性がある。

そのため、全画面の親である`App.tsx`にSnackbarを配置した。

```tsx
const [apiError, setApiError] = useState("");

const onClearApiError = (): void => {
  setApiError("");
};
```

```tsx
<Snackbar
  open={Boolean(apiError)}
  autoHideDuration={5000}
  onClose={onClearApiError}
  anchorOrigin={{
    vertical: "top",
    horizontal: "center",
  }}
>
  <Alert
    severity="error"
    onClose={onClearApiError}
    variant="filled"
    sx={{ width: "100%" }}
  >
    {apiError}
  </Alert>
</Snackbar>
```

### 処理の流れ

```text
APIエラー発生
        ↓
setApiError(error.message)
        ↓
apiErrorに文字列が入る
        ↓
Boolean(apiError)がtrue
        ↓
Snackbarが開く
```

閉じるときは次の流れになる。

```text
×ボタンを押す、または5秒経過
        ↓
onClearApiErrorが実行される
        ↓
setApiError("")
        ↓
Boolean(apiError)がfalse
        ↓
Snackbarが閉じる
```

## 5. severity="error"でも赤くならなかった原因

MUIでは、次の指定でエラー用の赤色が適用される。

```tsx
<Alert
  severity="error"
  variant="filled"
>
```

しかし、ダークモード用CSSがMUIの色を上書きしていた。

```css
.MuiAlert-root {
  background-color: var(--color-bg-secondary) !important;
  color: var(--color-text-primary) !important;
}
```

さらに、アイコンの色も上書きしていた。

```css
.MuiAlert-icon {
  color: inherit !important;
}
```

`!important`によって、MUIが設定したエラー色よりCSSが優先されていた。

この2つの指定を削除し、MUI本来のエラー色が適用されるようにした。

`--color-bg-secondary`自体は、入力欄やセカンダリボタンなどのダークモード表示に使うため、そのまま残した。

## 6. フロントのバリデーションエラーを赤く表示

```css
.MuiFormHelperText-root {
  color: var(--color-text-secondary) !important;
```

エラー時専用のCSSを追加した。

```css
.MuiFormLabel-root.Mui-error {
  color: var(--color-error) !important;

}
```

これにより、以下が赤く表示されるようになった。

- 入力欄のラベル
- 入力欄の枠線
- ヘルパーテキストのエラーメッセージ

## 7. 同じバリデーションエラーが2回表示されなかった原因

以前は、`errors`の変化を`useEffect`で監視していた。

```tsx
useEffect(() => {
  const signature = JSON.stringify(errors);

  if (signature === prevErrorSignatureRef.current) {
    return;
  }

  prevErrorSignatureRef.current = signature;

  if (onErrorsChange) {
    onErrorsChange(errors);
  }
}, [errors, onErrorsChange]);
```

この処理では、エラーを文字列に変換して前回のエラーと比較していた。

```tsx
const signature = JSON.stringify(errors);
```

同じエラーの場合は、ここで処理を終了していた。

```tsx
if (signature === prevErrorSignatureRef.current) {
  return;
}
```

そのため、右下の開発用エラーパネルが消えたあとに同じエラーで再度保存しても、2回目は表示されなかった。

画面を更新すると`useRef`が初期化されるため、再び1回だけ表示されていた。

## 8. handleSubmitの第2引数を使用

React Hook Formの`handleSubmit`には、成功時と失敗時の2つの関数を渡せる。

```tsx
handleSubmit(
  バリデーション成功時の関数,
  バリデーション失敗時の関数,
)
```

患者追加フォームに、失敗時の関数を追加した。

```tsx
const handleInvalidSubmit = (
  formErrors: FieldErrors<PatientInput>,
): void => {
  onErrorsChange?.(formErrors);
};
```

```tsx
<form
  onSubmit={handleSubmit(
    handleAddPatientSubmit,
    handleInvalidSubmit,
  )}
>
```

これにより、保存ボタンを押して検証に失敗するたびに、エラーを親へ渡せるようになった。

```text
保存ボタンを押す
        ↓
React Hook Formがバリデーション
        ↓
失敗
        ↓
handleInvalidSubmit(formErrors)
        ↓
onErrorsChange(formErrors)
        ↓
App.tsxのglobalErrorsを更新
        ↓
右下の開発用パネルを表示
```

## handleInvalidSubmitの役割

以前は、バリデーションに失敗したときの関数をフォーム内に作成していた。

```tsx
const handleInvalidSubmit = (
  formErrors: FieldErrors<PatientInput>,
): void => {
  onErrorsChange?.(formErrors);
};
```

```tsx
<form
  onSubmit={handleSubmit(
    handleAddPatientSubmit,
    handleInvalidSubmit,
  )}
>
```

処理の流れは次のとおり。

```text
handleSubmit
→ handleInvalidSubmit(formErrors)
→ onErrorsChange(formErrors)
```

しかし、`handleInvalidSubmit`は受け取った`formErrors`を加工せず、そのまま`onErrorsChange`へ渡しているだけだった。

そのため、中継関数を省略して直接渡せる。

```tsx
<form
  onSubmit={handleSubmit(
    handleAddPatientSubmit,
    onErrorsChange,
  )}
>
```

修正後の流れ：

```text
バリデーション成功
→ handleAddPatientSubmit(data)

バリデーション失敗
→ onErrorsChange(errors)
```

## なぜonErrorsChangeを直接渡せるのか

`handleSubmit`の第2引数が求める関数：

```tsx
(errors: FieldErrors<PatientInput>) => void
```

`onErrorsChange`の型：

```tsx
(errors: FieldErrors<PatientInput>) => void
```

引数と戻り値の型が一致しているため、直接渡せる。

```text
変更前：
React Hook Form
→ handleInvalidSubmit
→ onErrorsChange

変更後：
React Hook Form
→ onErrorsChange
```

`handleInvalidSubmit`から別の処理へ変更したわけではない。

受け取った値をそのまま渡していた中継関数を省略しただけである。

## 中継関数を残す場合

追加処理がある場合は、`handleInvalidSubmit`を作る意味がある。

```tsx
const handleInvalidSubmit = (
  formErrors: FieldErrors<PatientInput>,
): void => {
  console.error("入力エラー", formErrors);
  window.scrollTo({ top: 0 });
  onErrorsChange?.(formErrors);
};
```

現在は追加処理がないため、直接渡す形が適している。

## stateを親と子のどちらで管理するか

「stateは子で持ってはいけない」という決まりではない。

基本は、そのstateをどこで使用するかによって決める。

```text
そのコンポーネントだけで使うstate
→ 子で管理する

複数のコンポーネントで共有するstate
→ 共通の親で管理する
```

今回の役割分担：

| 状態 | 管理場所 | 理由 |
|---|---|---|
| フォームの入力値 | React Hook Form | そのフォームだけで使う |
| フォームの`errors` | React Hook Form | 入力欄のエラー表示に使う |
| `globalErrors` | `App.tsx` | 全画面共通の開発用パネルに使う |
| `apiError` | `App.tsx` | 全画面共通のSnackbarに使う |

子コンポーネントは、エラーを親へ知らせる。

```tsx
onErrorsChange?.(formErrors);
```

実際にエラーをstateへ保存しているのは、親の`App.tsx`にある`setGlobalErrors`である。

---

## 今日理解したこと

- `handleInvalidSubmit`の中でも、最初から`onErrorsChange`を使っていた
- `handleInvalidSubmit`はエラーを保存する関数ではなく、中継関数だった
- 関数の型が一致すれば、コールバックを直接渡せる
- 単純な中継だけなら関数を省略できる
- 追加処理がある場合は中継関数を残す
- stateは常に親で持つわけではない
- フォーム固有の状態はフォーム側で管理してよい
- 複数画面で共有する状態は共通の親で管理する
