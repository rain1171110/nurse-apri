## 1. ログイン・ログアウト機能の仕上げ

`fetchAppData()`が401を受け取った場合、`throw`によって以降の処理が止まり、`loadAppData()`の`catch`へ移動する流れを確認した。

```ts
if (!response.ok) {
  throw new Error(`API error:${response.status}`);
}
```

401の場合、以下は実行されない。

```ts
const data = await fetchAppData();
setAppData(data);
```

一方、`finally`は成功・失敗にかかわらず実行される。

```ts
finally {
  setLoading(false);
}
```

### 401とその他のエラーを分けた

```ts
const loadAppData = async (): Promise<void> => {
  setLoading(true);
  setApiError("");

  try {
    const data = await fetchAppData();

    setIsLoggedIn(true);
    setAppData({
      patients: Array.isArray(data.patients) ? data.patients : [],
      records: Array.isArray(data.records) ? data.records : [],
    });
  } catch (error) {
    if (error instanceof Error && error.message === "API error:401") {
      setIsLoggedIn(false);
      setAppData({
        patients: [],
        records: [],
      });
    } else {
      console.error(error);
      setApiError("APIから読み込めませんでした");
    }
  } finally {
    setLoading(false);
  }
};
```

### 理解したこと

- 401は、未ログインまたは認証期限切れとして処理する
- 401では不要な`console.error()`を実行しない
- 401以外の通信障害や500エラーは利用者と開発者へ知らせる
- 認証切れのときは、メモリ内の患者・看護記録データも削除する
- Network欄で401が赤く表示されても、HTTP通信の結果なので異常ではない

## 4. 認証と認可の違い

ログイン機能完成後、ユーザーごとの患者データ分離に着手した。

```text
認証
→ 誰がログインしているか確認する

認可
→ ログインした人が、どのデータを操作できるか制限する
```

現在のAPIでは、ログインしていれば全患者を取得できる。

```ts
const patients = await prisma.patient.findMany();
```

今後はJWTに保存された`userId`を使い、そのユーザーに所属する患者だけを取得する。

```text
User A
├─ Patient A
└─ Patient B

User B
└─ Patient C
```

User Aでログインした場合、Patient AとPatient Bだけを扱えるようにする。

## 5. JWTからuserIdを取得

ログイン時には、ユーザーIDをJWTへ保存している。

```ts
const token = jwt.sign({ userId: user.id }, JWT_SECRET, {
  expiresIn: "1h",
});
```

以前の`requireAuth`では、JWTを検証するだけで戻り値を利用していなかった。

```ts
jwt.verify(token, JWT_SECRET);
```

検証結果を`decoded`へ保存するように変更した。

```ts
const decoded = jwt.verify(token, JWT_SECRET);
```

`jwt.verify()`の戻り値は`string | JwtPayload`なので、そのままでは`decoded.userId`へアクセスできない。

そこで、型と内容を確認した。

```ts
if (typeof decoded === "string" || typeof decoded.userId !== "string") {
  res.status(401).json({
    error: "Invalid token payload / トークン内容が無効です",
  });
  return;
}
```

確認後に`userId`を取得する。

```ts
const userId = decoded.userId;
```

さらに、後続のAPIでも使えるように`req`へ保存する。

```ts
req.userId = userId;

next();
```

## 6. ExpressのRequest型を拡張

`req.userId`を追加すると、TypeScriptから次のエラーが出た。

```text
プロパティ 'userId' は型 'Request' に存在しません
```

そこで、次の型定義ファイルを作成した。

```text
server/express.d.ts
```

内容：

```ts
export {};

declare global {
  namespace Express {
    interface Request {
      userId?: string;
    }
  }
}
```

### 理解したこと

- JavaScriptでは`req.userId`を追加できても、TypeScriptには型定義が必要
- `.d.ts`は型を宣言するファイル
- Expressの既存の`Request`型へ`userId`を追加した
- この仕組みを「宣言マージ」という
- 型拡張すると、ほかのAPIでも毎回`AuthRequest`型を宣言せずに`req.userId`を使える
- 型定義は使用許可を与えるだけで、実際の値は`requireAuth`が代入する

```text
express.d.ts
→ req.userIdが存在するとTypeScriptへ伝える

requireAuth
→ JWTから取得した実際のuserIdをreqへ入れる
```

## 7. UserとPatientの関連付け

1人のユーザーが複数の患者を持つため、関係は「1対多」になる。

```text
User 1人 → Patient 複数
Patient 1人 → User 1人
```

`User`モデルへ患者の配列を追加した。

```prisma
model User {
  id           String    @id @default(uuid())
  email        String    @unique
  passwordHash String
  createdAt    DateTime  @default(now())
  patients     Patient[]
}
```

`Patient`モデルには、所有者となるユーザーIDを追加した。

```prisma
model Patient {
  id       String          @id @default(uuid())
  name     String
  room     Int             @unique
  age      Int?
  disease  String?
  history  String?
  progress String?
  records  NursingRecord[]
  userId   String
}
```

`User.id`が`String`なので、関連する`Patient.userId`も`String`にする。
