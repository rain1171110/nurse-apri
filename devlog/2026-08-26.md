## 1. UserとPatientの関連

`Patient`モデルに、所有者となるユーザーとの関連を追加した。

```prisma
model Patient {
  id       String          @id @default(uuid())
  name     String
  room     Int             @unique
  age      Int?
  disease  String?
  history  String?
  progress String?
  records  NursingRecord[]
  userId   String
  user     User            @relation(fields: [userId], references: [id])
}
```

`User`モデルには、1人のユーザーが複数の患者を持つことを表すフィールドを追加した。

```prisma
model User {
  id           String    @id @default(uuid())
  email        String    @unique
  passwordHash String
  createdAt    DateTime  @default(now())
  patients     Patient[]
}
```

関連全体は次のようになる。

```text
User 1人 ── Patient 複数人

Patient.userId → User.id
```

---

## 2. 関連フィールドの読み方

```prisma
user User @relation(fields: [userId], references: [id])
```

それぞれの意味は次のとおり。

```text
user
→ Patientから見た関連フィールド名
→ ownerなど、別の名前へ変更可能

User
→ 関連先のmodel User
→ 定義されているモデル名と一致させる

@relation
→ 2つのモデルの関連を設定する

fields: [userId]
→ Patient側で外部キーとして使用するフィールド
→ Patient.userId

references: [id]
→ 関連先であるUser側の参照フィールド
→ User.id
```

`references: [id]`が`User.id`を意味するのは、関連フィールドの型に`User`を指定しているため。

```prisma
user User @relation(...)
     ^^^^
```

## 3. userIdとuserの違い

```prisma
userId String
user   User @relation(fields: [userId], references: [id])
```

### `userId`

DBの`Patient`テーブルに実際の列として作られる。

```text
Patient.userId
→ 関連するユーザーのIDを保存する
```

### `user`

DBに`user`という列が作られるわけではない。

Prismaから関連するユーザーを扱うための関連フィールド。

```ts
patient.user
patient.user.email
```

マイグレーションによってDBへ反映される主な内容は次の2つ。

```text
1. PatientテーブルへuserId列を追加
2. Patient.userIdからUser.idへの外部キー制約を追加
```

## 6. P3005が発生した原因

最初に次のコマンドを実行した。

```bash
npx prisma migrate dev --name add_patient_user_relation
```

次のエラーが発生した。

```text
Error: P3005
The database schema is not empty.
```

当時の状態：

```text
DB
→ PatientやUserなどのテーブルがすでに存在
→ 患者データも入っている

schema.prisma
→ DBの設計図が書かれている

prisma/migrations
→ 存在しない
→ マイグレーション履歴がない
```

問題だったのは、次の組み合わせ。

```text
DBは空ではない
＋
マイグレーション履歴がない
```

`schema.prisma`には患者などの実データが入っているわけではない。

```text
schema.prisma
→ テーブルやフィールドの設計図

PostgreSQL
→ 実際のテーブルとデータ
```

## 7. 既存DBのベースライン作成

既存DBをマイグレーション管理の開始地点にするため、`0_init`を作成した。

まだDBへ反映していない関連フィールドを一時的に削除して、変更前のスキーマへ戻した。

ベースライン用フォルダを作成した。

```bash
mkdir -p prisma/migrations/0_init
```

現在のスキーマを作るためのSQLを生成した。

```bash
npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script > prisma/migrations/0_init/migration.sql
```

意味：

```text
--from-empty
→ 空のDBを開始地点にする

--to-schema prisma/schema.prisma
→ 現在のスキーマを完成地点にする

--script
→ 差分をSQLとして出力する

> prisma/migrations/0_init/migration.sql
→ SQLをmigration.sqlへ保存する
```

生成されたSQLを確認した。

```bash
sed -n '1,40p' prisma/migrations/0_init/migration.sql
```

`0_init`のSQLは実行せず、すでに適用済みとして登録した。

```bash
npx prisma migrate resolve --applied 0_init
```

これはテーブルを作成するコマンドではない。

```text
現在のDBは0_initまで適用済み
```

とPrismaの履歴へ登録するコマンド。

状態を確認した。

```bash
npx prisma migrate status
```

成功時：

```text
1 migration found in prisma/migrations

Database schema is up to date!
```

## 8. P3006が発生した原因

ベースライン作成後、再びマイグレーションを実行すると次のエラーが発生した。

```text
Error: P3006

Migration `0_init` failed to apply cleanly to the shadow database.

ERROR: relation "Patient" already exists
```

原因は、`prisma.config.ts`でシャドウDBを指定していなかったこと。

`prisma dev`では、次の2つのDBが用意されていた。

```text
localhost:51214
→ メインDB
→ 実際の患者データを保存する

localhost:51215
→ シャドウDB
→ マイグレーションを検証する
```

`.env`には最初から両方のURLがあった。

```env
DATABASE_URL="メインDBのURL"
SHADOW_DATABASE_URL="シャドウDBのURL"
```

しかし、`prisma.config.ts`ではメインDBしか指定していなかった。

変更前：

```ts
datasource: {
  url: process.env["DATABASE_URL"],
},
```

変更後：

```ts
datasource: {
  url: process.env["DATABASE_URL"],
  shadowDatabaseUrl: process.env["SHADOW_DATABASE_URL"],
},
```

これによって、Prismaがマイグレーション検証専用のDBを正しく使用できるようになった。

```text
P3005
→ 既存DBにマイグレーション履歴がなかった

P3006
→ shadowDatabaseUrlをprisma.config.tsで指定していなかった
```

## 11. Prisma Clientとは

Prisma Clientは、TypeScriptやJavaScriptからDBを操作するためのツール。

```text
schema.prisma
→ DBの設計図を書く

Prisma Migrate
→ 設計図の変更をDBへ反映する

Prisma Client
→ バックエンドコードからDBを操作する
```

例えば、患者一覧を取得する場合：

```ts
const patients = await prisma.patient.findMany();
```

所有者未設定の患者数を確認する場合：

```ts
const count = await prisma.patient.count({
  where: {
    userId: null,
  },
});
```

Prisma Clientを使わず、SQLで書く場合：

```sql
SELECT *
FROM "Patient"
WHERE "userId" = 'abc-123';
```

Prisma Clientで書く場合：

```ts
const patients = await prisma.patient.findMany({
  where: {
    userId: "abc-123",
  },
});
```

対応関係：

```text
SQL                           Prisma Client
SELECT                        findMany
FROM "Patient"                prisma.patient
WHERE "userId" = 'abc-123'    where: { userId: "abc-123" }
```

`SELECT`は取得、`INSERT`は新規作成。

SQLで患者を作成する場合：

```sql
INSERT INTO "Patient" ("id", "name", "room", "userId")
VALUES ('患者ID', '山田太郎', 101, 'ユーザーID');
```

Prisma Clientの場合：

```ts
await prisma.patient.create({
  data: {
    name: "山田太郎",
    room: 101,
    userId,
  },
});
```

## 12. ターミナルから一時的にPrismaを実行する方法

今日使用したコマンド：

```bash
npx tsx -e 'import { prisma } from "./server/db.ts"; (async () => { console.log({ unassignedPatients: await prisma.patient.count({ where: { userId: null } }) }); await prisma.$disconnect(); })();'
```

見やすくすると次の処理になる。

```ts
import { prisma } from "./server/db.ts";

const main = async () => {
  const unassignedPatients = await prisma.patient.count({
    where: {
      userId: null,
    },
  });

  console.log({
    unassignedPatients,
  });

  await prisma.$disconnect();
};

main();
```

それぞれの意味：

```text
npx tsx
→ TypeScriptを直接実行する

-e
→ ファイルを作らず、後ろのコードを直接実行する

(async () => {})()
→ async関数を定義してすぐ実行する

prisma.patient.count()
→ Patientの件数を数える

where: { userId: null }
→ userIdがnullの患者だけに絞る

prisma.$disconnect()
→ 一時処理の終了後にDB接続を閉じる
```

このコマンド全体を暗記する必要はない。

重要なのは、次の中心部分を理解すること。

```ts
prisma.patient.count({
  where: {
    userId: null,
  },
});
```

## 14. userIdを必須化

すべての既存患者へ`userId`を設定したため、`?`を外した。

変更前：

```prisma
userId String?
user   User?   @relation(fields: [userId], references: [id])
```

変更後：

```prisma
userId String
user   User   @relation(fields: [userId], references: [id])
```

マイグレーションを実行した。

```bash
npx prisma migrate dev --name make_patient_user_required
```

これによって、DB側でも`userId`が必須になった。

```text
Patient.userId
NULL許可 → NOT NULL
```

今後は、所有者のいない患者をDBへ保存できない。

## 15. IDがStringである理由

現在のID：

```prisma
id String @id @default(uuid())
```

UUIDは次のように、数字以外の文字やハイフンを含む。

```text
9e749e4a-480e-477b-8057-909f572abccc
```

そのため、`Int`ではなく`String`で保存する。

```text
id
→ フィールド名

String
→ 文字列型

@id
→ 主キー

@default(uuid())
→ UUIDを自動生成する
```

連番のIDを使う場合は次のように書ける。

```prisma
id Int @id @default(autoincrement())
```

この場合は、

```text
1
2
3
4
```

のようなIDになる。

## 今日の理解

- `User`と`Patient`の1対多の関連を定義できた
- `Patient.userId`が実際にDBへ保存される外部キーだと理解した
- `Patient.user`はPrisma上の関連フィールドだと理解した
- `references: [id]`は、関連先として指定した`User.id`を参照する
- `schema.prisma`はデータではなくDBの設計図
- `P3005`は、既存DBにマイグレーション履歴がなかったことが原因
- `P3006`は、シャドウDBの接続設定が不足していたことが原因
- 既存データがある場合、任意項目で追加してからデータを埋め、最後に必須化する
- Prisma Clientは、TypeScriptからDBを操作しやすくするツール
- スキーマ変更後は`npx prisma generate`でClientを更新する
- SQLの`SELECT`は取得、`INSERT`は新規作成
