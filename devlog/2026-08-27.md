## 1. PatientのIDとuserIdの違い

```prisma
model Patient {
  id       String          @id @default(uuid())
  name     String
  room     Int             @unique
  age      Int?
  disease  String?
  history  String?
  progress String?
  records  NursingRecord[]
  userId   String
  user     User            @relation(fields: [userId], references: [id])
}
```

### `Patient.id`

```prisma
id String @id @default(uuid())
```

患者自身を識別するID。

患者を新しく作成すると、UUIDが自動生成される。

### `Patient.userId`

```prisma
userId String
```

患者を所有しているユーザーのID。

新しいUUIDを作るのではなく、すでに存在する`User.id`を保存する。

```prisma
model User {
  id String @id @default(uuid())
}
```

関係は次のとおり。

```text
User.id
   ↓ 同じ値を保存
Patient.userId
```

例：

```text
User.id        = "abc-123"
Patient.userId = "abc-123"
```

`Patient.userId`に`@id @default(uuid())`は付けない。

## 2. Prisma ClientとSQLの違い

### Prisma Clientを使用する場合

```ts
const patients = await prisma.patient.findMany({
  where: {
    userId: req.userId,
  },
});
```

### SQLを直接使用する場合

Prismaを使わない場合は、例えば`pg`などのPostgreSQL接続ライブラリを使用する。

```ts
const result = await pool.query(
  `SELECT *
   FROM "Patient"
   WHERE "userId" = $1`,
  [req.userId],
);

const patients = result.rows;
```

どちらもバックエンドのAPI処理に記載する。

違うのは記載場所ではなく、DBへ問い合わせる方法。

```text
Prismaを使う
→ prisma.patient.findMany()

SQLを直接使う
→ pool.query()
```

現在の`nurse-apri`ではPrismaを使用しているため、Prisma Clientの書き方を使う。

## 3. マイグレーションファイルの役割

```text
prisma/migrations/
├─ 0_init/
│  └─ migration.sql
├─ 20260825211441_add_patient_user_relation/
│  └─ migration.sql
└─ 20260825212655_make_patient_user_required/
   └─ migration.sql
```

これらはDB構造を変更した履歴。

```text
0_init
→ 最初のテーブルを作成

add_patient_user_relation
→ PatientにuserIdとUserとの関連を追加

make_patient_user_required
→ Patient.userIdを必須に変更
```

### `schema.prisma`との違い

```text
schema.prisma
→ 現在のDB構造

migration.sql
→ 現在の構造になるまでの変更履歴
```

新しいDB構造の変更について`prisma migrate dev`を実行すると、基本的に新しいマイグレーションフォルダが増える。

適用済みのマイグレーションは基本的に編集せず、新しい変更は新しいマイグレーションとして追加する。

## 5. ログインユーザーの患者だけを取得する仕組み

現在の処理では、すべての患者を取得している。

```ts
const patients = await prisma.patient.findMany();
```

これから、ログインユーザーの患者だけを取得する処理へ変更する。

関係するのは次の3か所。

```text
auth.ts
→ JWTからログインユーザーのIDを取り出す

server/index.ts
→ ログインユーザーのIDをPrismaへ渡す

schema.prisma
→ Patient.userIdを定義している
```

### `auth.ts`

`requireAuth`がJWTを検証し、ユーザーIDをリクエストへ保存する。

```ts
req.userId = decoded.userId;
```

仮にログインユーザーのIDが`abc-123`なら、次の状態になる。

```ts
req.userId === "abc-123"
```

### `schema.prisma`

```prisma
model Patient {
  userId String
  user   User @relation(fields: [userId], references: [id])
}
```

患者がどのユーザーに所属しているかを`userId`で管理する。

### `server/index.ts`

Prismaの`where`を使って患者を絞り込む。

```ts
const patients = await prisma.patient.findMany({
  where: {
    userId: req.userId,
  },
});
```

この1行の左右には、それぞれ違う場所から来た値がある。

```ts
userId: req.userId
```

```text
左側のuserId
→ schema.prismaで定義したPatient.userId

右側のreq.userId
→ auth.tsが設定したログインユーザーのID
```

つまり、次の条件で検索している。

```text
Patient.userIdとログインユーザーのIDが一致する患者
```

---

## Prismaのwhereとは

`where`はPrisma Clientで決められている検索条件の書き方。

```ts
prisma.patient.findMany({
  where: {
    userId: "abc-123",
  },
});
```

日本語にすると次の意味になる。

```text
Patientを複数取得する。
ただし、userIdがabc-123の患者だけを取得する。
```

JavaScriptの`if`を使って取得後に比較するのではなく、Prismaの`where`を使ってDBから取得する段階で対象を絞る。

---

## 今日の重要ポイント

```text
auth.tsでログインユーザーのIDを取得
        ↓
req.userIdへ保存
        ↓
server/index.tsで検索条件に使用
        ↓
schema.prismaのPatient.userIdと照合
        ↓
ログインユーザーの患者だけ取得
```

`where`はJavaScriptの`if`ではなく、Prismaが用意しているDB検索条件。
