## 1. `req.userId`の役割

`requireAuth`でJWTを検証し、取得したユーザーIDを`req`に保存している。

```ts
const userId = decoded.userId;
req.userId = userId;
next();
```

`const userId`は`requireAuth`の中だけで使えるローカル変数である。

そこで、後続のAPI処理でも使えるように、同じリクエスト内で引き継がれる`req`へ保存する。

```text
CookieのJWT
↓
requireAuthで検証
↓
decoded.userIdを取得
↓
req.userIdへ保存
↓
next()
↓
後続のAPIでreq.userIdを使用
```

`export`しただけでは自動的に認証されない。

各APIに`requireAuth`を指定した場合だけ実行される。

```ts
app.get("/api/data", requireAuth, async (req, res) => {
  console.log(req.userId);
});
```

## 3. PatientとNursingRecordのリレーション

`schema.prisma`では、患者と看護記録が次のようにつながっている。

```prisma
model Patient {
  id       String          @id @default(uuid())
  name     String
  room     Int             @unique
  age      Int?
  disease  String?
  history  String?
  progress String?
  records  NursingRecord[]
  userId   String
  user     User            @relation(fields: [userId], references: [id])
}

model NursingRecord {
  id        String      @id @default(uuid())
  patientId String
  date      String
  author    String
  content   String?
  patient   Patient     @relation(
    fields: [patientId],
    references: [id],
    onDelete: Cascade
  )
  vitals    VitalSigns?
}
```

次の`@relation`が、看護記録と患者のつながりをPrismaに教えている。

```prisma
patient Patient @relation(
  fields: [patientId],
  references: [id],
  onDelete: Cascade
)
```

それぞれの意味は以下のとおり。

```text
patient
→ Patientモデルをたどるときの名前

fields: [patientId]
→ NursingRecord.patientIdを使用する

references: [id]
→ Patient.idと照合する

onDelete: Cascade
→ Patientを削除したら、関連するNursingRecordも削除する
```

実際の接続は次のとおり。

```text
NursingRecord.patientId === Patient.id
```

## 4. ログインユーザーの看護記録だけを取得

`NursingRecord`には`userId`が直接存在しない。

そのため、リレーションフィールドの`patient`を経由して、`Patient.userId`を確認する。

```ts
const records = await prisma.nursingRecord.findMany({
  where: {
    patient: {
      userId: req.userId,
    },
  },
  include: {
    vitals: true,
  },
});
```

処理の流れは以下のとおり。

```text
NursingRecord
↓ patientリレーション
Patient
↓ userId
req.userIdと比較
```

つまり、条件は以下になる。

```text
看護記録が属する患者のuserId
===
ログインユーザーのreq.userId
```

`patientId`と`req.userId`は比較できない。

```text
patientId  → Patient.id
req.userId → User.id
```

種類の異なるIDだからである。

## 5. `/api/data`のユーザー制限

```ts
app.get("/api/data", requireAuth, async (req, res) => {
  try {
    const patients = await prisma.patient.findMany({
      where: {
        userId: req.userId,
      },
    });

    const records = await prisma.nursingRecord.findMany({
      where: {
        patient: {
          userId: req.userId,
        },
      },

      },

      patients,
      records,

    });
  }
});
```

## 6. 患者追加時に`userId`を保存

`Patient.userId`を必須にしたため、患者情報だけでは新しい患者を作成できなくなった。

修正前は、フォームの患者情報しか保存していなかった。

```ts
const newPatient = await prisma.patient.create({
  data: result.data,
});
```

修正後は、ログインユーザーのIDも保存する。

```ts
const userId = req.userId;

if (!userId) {
  res.status(401).json({
    error: "Unauthorized / 認証が必要です",
  });
  return;
}

const newPatient = await prisma.patient.create({
  data: {
    ...result.data,
    userId,
  },
});
```

`...result.data`で患者情報を展開し、`userId`を追加している。

```ts
{
  ...result.data,
  userId,
}
```

最終的にPrismaへ渡されるデータのイメージは以下になる。

```ts
{
  name: "山田太郎",
  room: 101,
  age: 70,
  userId: "ログインユーザーのID",
}
```

患者追加が正常に動作することを確認できた。

## 7. なぜ`req.userId`は`string | undefined`なのか

Expressの宣言マージで、次のように定義している。

```ts
export {};

declare global {
  namespace Express {
    interface Request {
      userId?: string;
    }
  }
}
```

次の`?`は、値が存在しない可能性を表す。

```ts
userId?: string;
```

これは、ほぼ次と同じ意味になる。

```ts
userId: string | undefined;
```

したがって、`req.userId`を取り出した直後の型は以下になる。

```ts
const userId = req.userId;
// string | undefined
```

`if`で`undefined`の場合を終了させる。

```ts
if (!userId) {
  res.status(401).json({
    error: "Unauthorized / 認証が必要です",
  });
  return;
}
```

この処理より下に進めるのは、`userId`が存在する場合だけである。

```ts
const userId = req.userId;
// string | undefined

if (!userId) {
  return;
}

// ここではstring
```

このように、複数の型の可能性から型を限定することを「型の絞り込み」という。

この処理はJWTをもう一度検証しているのではない。

- `requireAuth`：実際のJWT認証を行う
- `if (!userId)`：安全確認とTypeScriptの型の絞り込みを行う

## 8. `jwt.verify()`と`typeof`

```ts
const decoded = jwt.verify(token, JWT_SECRET);
```

`jwt.verify()`の戻り値は、ライブラリの型定義で基本的に次のように定義されている。

```ts
JwtPayload | string
```

型定義は通常、次のファイルで確認できる。

```text
node_modules/@types/jsonwebtoken/index.d.ts
```

VS Codeでは、`verify`にカーソルを置いて`F12`を押すと型定義へ移動できる。

JWTの中身が正しい形か、以下の条件で確認している。

```ts
if (
  typeof decoded === "string" ||
  typeof decoded.userId !== "string"
) {
  res.status(401).json({
    error: "Invalid token payload / トークン内容が無効です",
  });
  return;
}
```

2つの条件は、確認対象が異なる。

```ts
typeof decoded === "string"
```

これは`decoded`全体を確認している。

`decoded`全体が文字列の場合、`userId`を持つオブジェクトではないためエラーにする。

```ts
typeof decoded.userId !== "string"
```

これは`decoded`の中にある`userId`を確認している。

`userId`が文字列でなければエラーにする。

求めている正常な形は以下である。

```ts
const decoded = {
  userId: "user-001",
};
```

整理すると以下になる。

```text
decoded        → オブジェクトであること
decoded.userId → 文字列であること
```

`typeof decoded === "string"`の`"string"`は型指定ではなく、`typeof`の結果との比較である。

```ts
typeof "hello";
// "string"

typeof 123;
// "number"

typeof {};
// "object"
```

正常なデータでは、エラー条件が両方とも`false`になる。

```ts
const decoded = {
  userId: "user-001",
};

typeof decoded === "string";
// false

typeof decoded.userId !== "string";
// false
```
