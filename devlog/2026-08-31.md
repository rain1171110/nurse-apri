## 3. 実装の要点（理解を深める）

### 3-1. 看護記録保存処理の全体像

```ts
app.post<{}, {}, CreateRecordBody>(
  "/api/records",
  requireAuth,
  async (req, res) => {
    const userId = req.userId;
    if (!userId) {
      res.status(401).json({
        error: "Unauthorized / 認証が必要です",
      });
      return;
    }

    try {
      const result = createRecordSchema.safeParse(req.body);
      if (!result.success) {
        res.status(400).json({
          error: "Invalid record data / 無効な看護記録データ",
          details: result.error.flatten(),
        });
        return;
      }

      const { vitals, ...recordData } = result.data;

      const patient = await prisma.patient.findFirst({
        where: {
          id: recordData.patientId,
          userId,
        },
      });

      if (!patient) {
        res.status(404).json({
          error: "Patient not found / 患者が見つかりません",
        });
        return;
      }

      const newRecord = await prisma.nursingRecord.create({
        data: {
          ...recordData,
          vitals: {
            create: vitals,
          },
        },
        include: {
          vitals: true,
        },
      });

      res.status(201).json(newRecord);
    } catch (error) {
      if (isPrismaError(error, "P2003")) {
        res.status(404).json({
          error: "Patient not found / 患者が見つかりません",
        });
        return;
      }
      console.error("POST /api/records error", error);
      res.status(500).json({
        error: "Failed to create record / 看護記録の追加に失敗しました",
      });
    }
  },
);
```

- このコードの責務（1文）:
  - 認証済みユーザーが、自分の患者に対して看護記録とバイタルを保存する処理を行う
- 入力:
  - `req.body` に入る看護記録データ
- 出力:
  - `201` と新しく作成した `newRecord`
- 副作用（ある場合）:
  - `prisma.nursingRecord.create()` により、データベースに新しいレコードが保存される
  - `vitals.create` により、別テーブルにも保存される
- 型をどう絞り込んだか:
  - `CreateRecordBody` で受け取るデータの型を固定している
- null / undefined をどう安全に扱ったか:
  - `if (!userId)` と `if (!patient)` で、認証や患者の存在チェックをしている
- 型で守れていること:
  - `patientId` が必要なデータであること
  - `vitals` を別で扱うこと
- 似た書き方との違い:
  - `create` は「新規保存」
  - `include` は「返り値に含める」
- 改善余地（命名/分割/境界条件）:
  - エラーハンドリングの分岐をもう少し整理すると、読みやすくなる

### 3-2. `include` の意味

```ts
const newRecord = await prisma.nursingRecord.create({
  data: {
    ...recordData,
    vitals: {
      create: vitals,
    },
  },
  include: {
    vitals: true,
  },
});
```

- `create: vitals` は、データベースへ `vitals` を保存する指定
- `include: { vitals: true }` は、返り値に `vitals` を含める指定

つまり、保存自体は両方とも行われるが、返ってくるオブジェクトの中身が変わる。

```ts
// include がある場合
newRecord = {
  id: "...",
  patientId: "...",
  content: "...",
  vitals: {
    temperature: 36.5,
  },
};
```

```ts
// include がない場合
newRecord = {
  id: "...",
  patientId: "...",
  content: "...",
};
```

- 重要なポイント:
  - `include` は保存ではなく、返り値の中身に関係する

### 3-3. `upsert` の意味

```ts
vitals: {
  upsert: {
    create: vitals,
    update: vitals,
  },
}
```

- バイタルが存在しない → `create: vitals`
- バイタルが存在する → `update: vitals`

つまり、

> 「あれば更新し、なければ新しく作る」

という一つの処理になる。

### 3-4. 更新時の認可チェック

```ts
const updatedRecord = await prisma.nursingRecord.update({
  where: {
    id,
    patient: { userId },
  },
```

この `where` は、次の2つを両方満たすものだけを更新対象にする。

```ts
id;
```

```ts
patient: {
  userId;
}
```

これは、

- URL で指定した記録IDが一致する
- その記録の患者がログインユーザーの患者である

という条件を満たしているか確認している。

例：

```text
更新対象の記録ID: record-123
記録の患者のuserId: user-A
ログイン中のuserId: user-B
```

この場合、`id` は合っていても、`patient.userId` が違うので更新できない。

つまり、

> ログインユーザーが他人の看護記録IDを知っていても、患者の所有者が違えば更新できない

という認可の仕組みになる。
