## 2. 今日変更した認可処理

### 看護記録の削除

```ts
app.delete<{ id: string }>(
  "/api/records/:id",
  requireAuth,
  async (req, res) => {
    try {
      const userId = req.userId;

      if (!userId) {
        res.status(401).json({
          error: "Unauthorized / 認証が必要です",
        });
        return;
      }

      const { id } = req.params;

      await prisma.nursingRecord.delete({
        where: {
          id,
          patient: {
            userId,
          },
        },
      });

      res.json({ id });
    } catch (error) {
      if (isPrismaError(error, "P2025")) {
        res.status(404).json({
          error: "Record not found / 看護記録が見つかりません",
        });
        return;
      }

      console.error("DELETE /api/records/:id error:", error);

      res.status(500).json({
        error: "Failed to delete record / 看護記録の削除に失敗しました",
      });
    }
  },
);
```

次の条件を同時に満たす看護記録だけ削除する。

```ts
where: {
  id,
  patient: {
    userId,
  },
},
```

- `id`：削除する看護記録のID
- `patient.userId`：その記録に紐づく患者の所有者
- `userId`：現在ログインしているユーザーのID

削除処理では、既存の看護記録から患者をたどって認可を確認できるため、事前の`findFirst()`は不要。

### 患者と看護記録の一括取得

```ts
app.get("/api/data", requireAuth, async (req, res) => {
  const userId = req.userId;

  if (!userId) {
    res.status(401).json({
      error: "Unauthorized / 認証が必要です",
    });
    return;
  }

  try {
    const patients = await prisma.patient.findMany({
      where: {
        userId,
      },
    });

    const records = await prisma.nursingRecord.findMany({
      where: {
        patient: {
          userId,
        },
      },
      include: {
        vitals: true,
      },
    });

    const data = {
      patients,
      records,
    };

    res.json(data);
  } catch (error) {
    console.error("GET /api/data error:", error);

    res.status(500).json({
      error: "Failed to read data / データの読み込みに失敗しました",
    });
  }
});
```

患者は直接`userId`を持っているため、次の条件で取得する。

```ts
where: {
  userId,
},
```

看護記録は直接`userId`を持っていないため、関連する患者を経由して確認する。

```ts
where: {
  patient: {
    userId,
  },
},
```

## 4. ユーザー分離テスト

### テストの目的

次の流れを自動テストで確認する。

1. ユーザーAで患者を作成する
2. ユーザーBを登録してログインする
3. ユーザーBで患者一覧を取得する
4. ユーザーAの患者が一覧に含まれていないことを確認する

### 途中まで作成したコード

```ts
describe("GET /api/patients", () => {
  it("他のユーザーの患者は取得できない", async () => {
    const otherAgent = request.agent(app);

    const testUserB = {
      email: `test-b-${Date.now()}@example.com`,
      password: "test-password",
    };

    const registerResponse = await otherAgent
      .post("/api/auth/register")
      .send(testUserB);

    expect(registerResponse.status).toBe(201);

    const loginResponse = await otherAgent
      .post("/api/auth/login")
      .send(testUserB);

    expect(loginResponse.status).toBe(200);

    const createPatientResponse = await agent.post("/api/patients").send({
      name: "テスト患者",
      room: 999,
    });

    expect(createPatientResponse.status).toBe(201);

    const getPatientResponse = await otherAgent.get("/api/patients");

    expect(getPatientResponse.status).toBe(200);

    const patientIds = getPatientResponse.body.map(
      (patient: { id: string }) => patient.id,
    );

    expect(patientIds).not.toContain(createPatientResponse.body.id);
  });
});
```

## 5. `agent`の役割

```ts
const agent = request.agent(app);
```

- `request`：Supertestの機能
- `app`：テスト対象のExpressアプリ
- `agent`：Cookieを保持しながら`app`へリクエストを送るテスト用クライアント

今回のテストでは、次のように使い分ける。

```ts
agent       // ユーザーAとして通信
otherAgent  // ユーザーBとして通信
```

ログインすると、バックエンドがJWTをCookieとして返す。

`agent`はそのCookieを保持し、次のリクエストでも送信する。そのため、バックエンドはどのユーザーからのリクエストか判別できる。

---

## 6. `.post()`と`.send()`の役割

```ts
const createPatientResponse = await agent.post("/api/patients").send({
  name: "テスト患者",
  room: 999,
});
```

### `.post("/api/patients")`

Expressの次のルートにつながる。

```ts
app.post("/api/patients", requireAuth, async (req, res) => {
  // 患者作成処理
});
```

HTTPメソッドとパスの両方が一致することで、対応するバックエンド処理が実行される。

```text
agent.post("/api/patients")
            ↓
app.post("/api/patients", ...)
```

### `.send()`

バックエンドへ送るリクエスト本文を指定する。

```ts
.send({
  name: "テスト患者",
  room: 999,
});
```

バックエンドでは`req.body`として受け取る。

```ts
req.body = {
  name: "テスト患者",
  room: 999,
};
```

---

## 7. `createPatientResponse`の中身

`.send()`で送信するのは`name`と`room`だけだが、`createPatientResponse`にはサーバーから返されたHTTPレスポンス全体が入る。

```ts
createPatientResponse
```

レスポンス全体。

```ts
createPatientResponse.body
```

サーバーが返した患者データ。

```ts
createPatientResponse.body.id
```

作成された患者のIDだけ。

そのため、患者IDの配列と比較するときは次のように書く。

```ts
expect(patientIds).not.toContain(createPatientResponse.body.id);
```

次の書き方では、患者IDの配列とレスポンス全体を比較してしまうため、正しい認可テストにならない。

```ts
expect(patientIds).not.toContain(createPatientResponse);
```

比較する値の形をそろえることが重要。

```text
patientIds                       → 患者IDの配列
createPatientResponse.body.id    → 1件の患者ID
```

## 8. 今日理解できたこと

- `agent.post("/api/patients")`がExpressの患者作成APIを呼び出す
- HTTPメソッドとURLパスの両方が一致するルートが実行される
- `.send()`の内容はバックエンドの`req.body`に入る
- `agent`はCookieを保持できるテスト用クライアント
- `agent`と`otherAgent`を使うことで、別のログインユーザーを再現できる
- リクエストで送るデータと、サーバーから返るレスポンスは別物
- `createPatientResponse`は患者データだけではなく、HTTPレスポンス全体
- 配列の中身を検証するときは、比較対象の型と形をそろえる
- 認証済みでも、認可がなければ他人のデータを操作できる可能性がある
- `where`に`userId`を含めることで、ユーザーごとにデータを分離できる
