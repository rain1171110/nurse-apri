## 2. 発生した問題

### 問題1：患者作成で`409`が返った

```text
Expected: 201
Received: 409
```

レスポンスの内容を確認すると、病室番号の重複だった。

```text
This room number is already in use /
この部屋番号はすでに使用されています
```

テストで患者作成APIを実行すると、実際にDBへ患者が保存される。

```ts
await agent.post("/api/patients").send({
  name: "テスト患者",
  room: 999,
});
```

テスト終了後も患者を削除していなかったため、次回のテストで同じ`room`を使うと重複した。

```text
1回目：room 999を保存 → 201
2回目：room 999を再登録 → 409
```

### 問題2：大きな病室番号で`400`が返った

最初は`Date.now()`を使って大きな番号を作ろうとしたが、Zodの検証に失敗した。

```text
Too big: expected number to be <=999
```

`room`は`999`以下でなければならないため、`1〜999`の範囲でランダム生成するようにした。

```ts
const uniqueRoom = Math.floor(Math.random() * 999) + 1;
```

## 3. 実装したテストデータの後片付け

Vitestから`afterAll`を読み込んだ。

```ts
import { afterAll, beforeAll, describe, expect, it } from "vitest";
```

テストファイルからDBを操作できるよう、Prisma Clientを読み込んだ。

```ts
import { prisma } from "./db.js";
```

すべてのテスト終了後に、テストユーザーの患者を削除する。

```ts
afterAll(async () => {
  await prisma.patient.deleteMany({
    where: {
      user: {
        email: testUser.email,
      },
    },
  });

  await prisma.user.deleteMany({
    where: {
      email: {
        in: [testUser.email, testUserB.email],
      },
    },
  });
});
```

削除する順番は次のとおり。

```text
Patientを削除
↓
Userを削除
```

`Patient`が`User`を参照しているため、先に患者を削除してからユーザーを削除する。

## 4. 今日理解したこと

### `afterAll`

`afterAll`は、ファイル内のすべてのテストが終了したあとに1回だけ実行される。

```text
beforeAll：すべてのテストが始まる前
afterAll ：すべてのテストが終わった後
```

今回は、テストで作成したDBデータの後片付けに使用した。

### Prismaの`in`

```ts
email: {
  in: [testUser.email, testUserB.email],
}
```

`in`はANDではなく、「配列内のどれかに一致する」というORに近い条件。

```ts
email === testUser.email ||
email === testUserB.email
```

SQLでは次のイメージ。

```sql
WHERE email IN ('ユーザーAのメール', 'ユーザーBのメール');
```

### テストの実行順序に依存させない

`otherAgent`の登録・ログインをGETテスト内だけで行うと、別のテストがGETテストの実行後であることに依存してしまう。

そのため、ユーザーAとユーザーBの登録・ログインは`beforeAll`で済ませる。

```text
agent      → testUserとしてログイン
otherAgent → testUserBとしてログイン
```

それぞれが別のCookieを保持するため、別ユーザーとして認可テストができる。
