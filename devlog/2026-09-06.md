## 2. 今日理解したこと

### 患者を特定するためにIDを使う

```ts
.put(`/api/patients/${createPatientResponse.body.id}`)
```

`otherAgent`が作成した患者のIDをURLへ入れることで、更新対象の患者を特定する。

```ts
createPatientResponse.body.id
```

これは、患者作成APIから返された患者データのIDである。

---

### 固定した部屋番号によって409が発生した

最初は、次の固定値を使っていた。

```ts
room: 998
```

しかし、同じ部屋番号の患者がデータベースに残っていたため、患者作成時に`409`が返った。

```text
Expected: 201
Received: 409
```

これは認可テストの失敗ではなく、患者の作成に失敗していたことが原因だった。

対策として、部屋番号をランダムに作成した。

```ts
const uniqueRoom = Math.floor(Math.random() * 999) + 1;
```

このコードでは、Zodの制限に収まる`1〜999`の数値を作成する。

## 3. 他ユーザーの患者を更新できないテスト

```ts
describe("PUT /api/patients/:id", () => {
  const uniqueRoom = Math.floor(Math.random() * 999) + 1;

  it("他のユーザーの患者は更新できない", async () => {
    const createPatientResponse = await otherAgent
      .post("/api/patients")
      .send({
        name: "他ユーザーの患者",
        room: uniqueRoom,
      });

    expect(createPatientResponse.status).toBe(201);

    const updatePatientResponse = await agent
      .put(`/api/patients/${createPatientResponse.body.id}`)
      .send({
        name: "更新しようとした患者",
        room: uniqueRoom,
      });

    expect(updatePatientResponse.status).toBe(404);
  });

  it("存在しない患者を更新すると404を返す", async () => {
    const response = await agent
      .put("/api/patients/00000000-0000-0000-0000-000000000000")
      .send({
        name: "テスト患者",
        room: uniqueRoom,
      });

    expect(response.status).toBe(404);
    expect(response.body.error).toBe(
      "Patient not found / 患者が見つかりません",
    );
  });
});
```

### テストの流れ

1. `otherAgent`で患者を作成する
2. 作成された患者のIDを取得する
3. `agent`でその患者の更新を試す
4. `agent`の所有する患者ではないため`404`になる

## 4. テスト終了後の削除処理

認可テスト自体は成功したが、`afterAll`で次のエラーが発生した。

```text
Foreign key constraint violated on the constraint: Patient_userId_fkey
```

### 原因

`otherAgent`が作成した患者が残っている状態で、その患者の所有者であるユーザーを削除しようとした。

患者の`userId`がユーザーを参照しているため、患者を残したままユーザーだけを削除することはできない。

### 修正したコード

```ts
afterAll(async () => {
  await prisma.patient.deleteMany({
    where: {
      user: {
        email: {
          in: [testUser.email, testUserB.email],
        },
      },
    },
  });

  await prisma.user.deleteMany({
    where: {
      email: {
        in: [testUser.email, testUserB.email],
      },
    },
  });
});
```

### 削除する順番

```text
患者を削除
↓
ユーザーを削除
```

先に患者を削除してから、患者に参照されなくなったユーザーを削除する。

```ts
in: [testUser.email, testUserB.email]
```

これは、`testUser`または`testUserB`のメールアドレスに一致するデータを対象にする。

## 5. 他ユーザーの患者を削除できないテスト

```ts
describe("DELETE /api/patients/:id", () => {
  const uniqueRoom = Math.floor(Math.random() * 999) + 1;

  it("他のユーザーの患者は削除できない", async () => {
    const createPatientResponse = await otherAgent
      .post("/api/patients")
      .send({
        name: "他ユーザーの患者",
        room: uniqueRoom,
      });

    expect(createPatientResponse.status).toBe(201);

    const deletePatientResponse = await agent.delete(
      `/api/patients/${createPatientResponse.body.id}`,
    );

    expect(deletePatientResponse.status).toBe(404);
  });

  it("存在しない患者を削除すると404を返す", async () => {
    const response = await agent.delete(
      "/api/patients/00000000-0000-0000-0000-000000000000",
    );

    expect(response.status).toBe(404);
    expect(response.body.error).toBe(
      "Patient not found / 患者が見つかりません",
    );
  });
});
```

### 更新と削除の違い

```ts
.put(...).send(...) // 患者を更新する
.delete(...)        // 患者を削除する
```

削除では、患者の更新内容を送らないため`.send()`は不要。

## 7. 看護記録のスキーマ

```ts
export const createRecordSchema = z.object({
  patientId: z.string().min(1, "患者IDは必須"),
  date: z.string().min(1, "日付は必須"),
  author: z.string().min(1, "記録者は必須"),
  content: z.string().optional(),
  vitals: z.object({
    T: z.number().min(35).max(42).optional(),
    P: z.number().int().min(0).max(200).optional(),
    R: z.number().int().min(0).max(40).optional(),
    SBP: z.number().int().min(0).max(250).optional(),
    DBP: z.number().int().min(0).max(150).optional(),
    SPO2: z.number().int().min(0).max(100).optional(),
  }),
});
```

### 必須項目

| 項目 | 必須か |
|---|---|
| `patientId` | 必須 |
| `date` | 必須 |
| `author` | 必須 |
| `content` | 任意 |
| `vitals` | 必須 |
| `vitals`内の各項目 | 任意 |

`vitals`自体は必須だが、中の項目はすべて任意なので、次の形式でもバリデーションを通過する。

```ts
vitals: {}
```

### 400と404の違い

```text
送信したデータの形式が不正
→ 400 Bad Request

データ形式は正しいが、自分の所有する患者ではない
→ 404 Not Found
```

認可処理まで到達させるには、まずスキーマに合った正しい看護記録データを送る必要がある。
