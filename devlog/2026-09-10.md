## 2. 今日は理解したこと

### 1. フロントからバックエンドへ送る

```ts
const response = await fetch(`${API_BASE}/auth/register`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify(receiveRegister),
});
```

ここで大事なのは、JavaScriptのオブジェクトをそのまま送っているわけではないということです。

```ts
{
  email: "test@example.com",
  password: "password123",
}
```

このままではネットワークの通信では扱いにくいので、`JSON.stringify()`で文字列に変換して送っています。

つまり、

> 送る前に「文字列にして通信できる形」にする

という作業をしています。

---

### 2. バックエンドが受け取るときの流れ

```ts
app.use(express.json());
```

この処理があると、送られてきたJSON文字列をJavaScriptのオブジェクトに変換してくれます。

その後、`req.body`に値が入ります。

```ts
const { email, password } = req.body;
```

これは、

> 送られてきたデータを、コード内で扱える形に変換した結果

を表しています。

---

### 3. データはそのまま使わず、検査する

```ts
const result = registerSchema.safeParse(req.body);
```

ここで大事なのは、`req.body`をそのままDBに入れないことです。

`safeParse()`は、

- emailが文字列か
- passwordが存在しているか
- ルールに合っているか

を確認する役割があります。

```ts
if (!result.success) {
  res.status(400).json({
    error: "Invalid registration data / 無効な登録データ",
    details: result.error.flatten(),
  });
  return;
}
```

もしルールに合わない場合は、ここで止めます。これが「入力チェック」です。

つまり、

> 不正なデータを次の処理に進めない

という安全装置です。

---

### 4. パスワードはそのまま保存しない

```ts
const passwordHash = await bcrypt.hash(password, 10);
```

ここでパスワードをハッシュ化しています。ハッシュ化とは、元の値をそのまま見えない形に変える処理です。

例えると、

- 文字のまま保管する → そのまま盗まれたら危険
- ハッシュ化した値を保管する → 取り出しにくくなる

というイメージです。

そして DB には `passwordHash` を保存します。

```ts
const newUser = await prisma.user.create({
  data: {
    email,
    passwordHash,
  },
});
```

このとき `newUser` には保存後のユーザー情報が入ります。

---

### 5. 成功時に返すデータは最低限にする

```ts
res.status(201).json({
  id: newUser.id,
  email: newUser.email,
  createdAt: newUser.createdAt,
});
```

ここでは `password` や `passwordHash` は返していません。

理由は、

- パスワードは秘密情報だから
- 返す必要がないから

です。

クライアント側は `id` と `email` などだけあれば十分です。

---

## 3. 型の考え方が少しわかった

### フロントが送る型

```ts
type RegisterData = {
  email: string;
  password: string;
};
```

これは、バックエンドに送る「入力データ」の型です。

### バックエンドが返す型

```ts
type RegisterResponse = {
  id: string;
  email: string;
  createdAt: string;
};
```

これは、登録成功後にフロントに返す「出力データ」の型です。

つまり、

> 送るデータと返すデータは役割が違うので、型も別にする

という考え方です。

## 4. 今日の一番の理解

一番大事だったのは、「APIの登録処理は 1 つの流れとしてつながっている」ということです。

1. フロントがデータを送る
2. バックエンドが JSON をオブジェクトに変える
3. `safeParse()`で検査する
4. 不正なら止める
5. パスワードをハッシュ化する
6. DB に保存する
7. 成功した情報だけ返す

この順番を理解できたのが、今回の大きな成長でした。

## 6. 3行まとめ

1. 登録APIは「送る → 検査する → 保存する → 返す」の流れで動く。
2. `safeParse()`とハッシュ化は、セキュリティと正しさを守るための大事な工程だ。
3. 送る型と返す型を分けることで、どこに何が入るかを明確にできる。

バックエンドの返り値と型を一致させる。

```ts
res.status(201).json({
  id: newUser.id,
  email: newUser.email,
  createdAt: newUser.createdAt,
});
```

パスワードが`RegisterResponse`にない理由は、バックエンドがパスワードを返していないためである。

## 5. JSONを使う理由

HTTP通信でJSONしか使えないわけではない。

登録情報のような構造化データを、項目名と値の関係を保ったまま送受信しやすいため、JSONを使用している。

```json
{
  "email": "test@example.com",
  "password": "password123"
}
```

画像・動画・PDFなどは、通常はバイナリデータや`FormData`として送信する。

JSONを使用する主な理由は次のとおり。

- 項目名と値の関係を表現できる
- 配列や入れ子のデータを表現できる
- JavaScriptオブジェクトとの変換が簡単
- 多くのプログラミング言語で扱える
- Web APIで広く使用されている

## 8. 現時点の理解度

### 理解できたこと

- JSONはHTTP通信で唯一の形式ではない
- 構造化データを送るためにJSONが適している
- フロントエンドの`body`とバックエンドの`req.body`がつながっている
- `safeParse()`は保存処理ではなく検査処理
- `result.data`は検査済みデータ
- 生のパスワードはデータベースへ保存しない
- 送信データと受信データでは必要な型が異なる
- レスポンスの型は、バックエンドが返すデータに合わせる
