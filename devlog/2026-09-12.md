### 役割

## 3. 作成したテスト

```tsx
// @vitest-environment jsdom

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";
import { MemoryRouter } from "react-router-dom";
import RegisterPage from "./RegisterPage";
import { registerApi } from "./api/authApi";

vi.mock("./api/authApi", () => ({
  registerApi: vi.fn(),
}));

describe("RegisterPage", () => {
  it("入力した登録情報でregisterApiが呼ばれる", async () => {
    const user = userEvent.setup();

    render(
      <MemoryRouter>
        <RegisterPage />
      </MemoryRouter>,
    );

    const emailInput = screen.getByLabelText("新規メールアドレス");
    const passwordInput = screen.getByLabelText("新規パスワード");

    await user.type(emailInput, "test@example.com");
    await user.type(passwordInput, "password123");

    const registerButton = screen.getByRole("button", {
      name: "登録ボタン",
    });

    await user.click(registerButton);

    expect(registerApi).toHaveBeenCalledWith({
      email: "test@example.com",
      password: "password123",
    });
  });
});
```

## 5. 技術判断ログ（エンジニア視点）

- 解決したかった課題:
  - フロントエンドテストで、画面上の入力操作が実際に `registerApi` に渡るか確認したかった
  - `document` がない環境で出るエラーを、テスト環境に合わせて解決したかった
- 検討した選択肢（最低2つ）:
  - 案A: `registerApi` を実際に呼ばず、テストを作れない状態のまま進める
  - 案B: `vi.mock()` で API を置き換えて、画面の入力と送信を分離してテストする
- 採用した案:
  - 案B
- 採用理由（性能/保守性/実装コスト/安全性）:
  - API の実体に依存せず、画面側の責務だけを検証できる
  - テストが速く、失敗の原因を特定しやすい
  - 実際の DB やネットワークに影響を与えない
- 採用しなかった案を捨てた理由:
  - 実APIを使うと、テストが不安定になり、外部要因の影響を受けやすい

## 6. 今日理解したこと

### 1. `render()` の意味

```tsx
render(
  <MemoryRouter>
    <RegisterPage />
  </MemoryRouter>,
);
```

`render()` は、Reactコンポーネントをテスト用の画面へ表示する関数です。

`RegisterPage` では `useNavigate` と `Link` を使っているため、`MemoryRouter` で囲む必要があります。

### 2. `getByLabelText()` の意味

```ts
const emailInput = screen.getByLabelText("新規メールアドレス");
```

ラベルと関連付けられた入力欄を取得します。

```tsx
<label htmlFor="email">新規メールアドレス</label>
<input id="email" />
```

このような関係があると、`htmlFor` と `id` がつながっているので、画面上の入力欄を見つけやすくなります。

### 3. `getByRole()` の意味

```ts
const registerButton = screen.getByRole("button", {
  name: "登録ボタン",
});
```

役割が `button` で、表示名が「登録ボタン」の要素を取得します。

`type="submit"` はボタンの種類であり、見た目の名前ではありません。

### 4. `userEvent` の意味

```ts
const user = userEvent.setup();

await user.type(emailInput, "test@example.com");
await user.click(registerButton);
```

テストの中で、ユーザーが入力したりクリックしたりした動作を再現できます。

### 5. `vi.mock()` の意味

```ts
vi.mock("./api/authApi", () => ({
  registerApi: vi.fn(),
}));
```

本物の `registerApi` を、テスト専用の関数に置き換えます。

これにより、実際の API や DB にアクセスせずに、画面の動作だけをテストできます。

### 6. `toHaveBeenCalledWith()` の意味

```ts
expect(registerApi).toHaveBeenCalledWith({
  email: "test@example.com",
  password: "password123",
});
```

`registerApi` が、指定した引数で呼ばれたかを確認します。

このテストでは、入力欄の値が JS のオブジェクトとして正しく渡されたかを見るために使っています。

## 7. 発生したエラーと解決方法

### エラー内容

```text
TypeError: Cannot read properties of undefined
```

### 原因

Vitest が Node.js 環境で動いており、`userEvent` が必要とするブラウザの `document` が存在しなかったためです。

### 解決方法

`jsdom` を導入し、テストファイルの先頭に次を追加しました。

```ts
// @vitest-environment jsdom
```

これで `RegisterPage.test.tsx` だけが `jsdom` 環境で動きます。

バックエンドテストはそのまま Node.js 環境で使えるので、`vite.config.ts` は変更していません。
