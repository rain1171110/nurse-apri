## 4. 修正したポイント

### 4-1. エラーメッセージを一致させる

修正前：

```ts
mockRejectedValue(new Error("登録に失敗しました"));
```

テストで探していた文字：

```ts
screen.findByText("ログインに失敗しました");
```

`LoginPage`では、受け取った`Error`の`message`をそのまま表示する。

```ts
if (error instanceof Error) {
  setApiError(error.message);
}
```

そのため、モック側も「ログインに失敗しました」に統一した。

```ts
mockRejectedValue(new Error("ログインに失敗しました"));
```

### 4-2. `Route`を`Routes`で囲む

修正前：

```tsx

  <Route path="/login" element={<LoginPage />} />

```

```tsx
<MemoryRouter initialEntries={["/login"]}>
  <Routes>
    <Route path="/login" element={<LoginPage />} />
  </Routes>
</MemoryRouter>
```

React Routerでは、`Route`を`Routes`の中に置く必要がある。

## 5. `initialEntries`の理解

```tsx
<MemoryRouter initialEntries={["/login"]}>
```

`initialEntries`は、テスト開始時の現在地を決める。

```text
initialEntries={["/login"]}
→ テストを/loginから開始する
```

一方、`Route`はURLと画面の対応を決める。

```tsx
<Route path="/login" element={<LoginPage />} />
```

```text
現在地が/loginならLoginPageを表示する
```

処理の流れ：

```text
initialEntriesで現在地を/loginにする
              ↓
Routesが一致するpathを探す
              ↓
path="/login"が一致する
              ↓
LoginPageが表示される
```

`MemoryRouter`で開始URLを指定しない場合、基本的には`/`から始まる。

そのため、テストしたい画面が`/`なら省略できる。

```tsx
<MemoryRouter>
  <Routes>
    <Route path="/" element={<PatientList />} />
  </Routes>
</MemoryRouter>
```

テストしたい画面が`/login`など、`/`以外なら指定する。

```tsx
<MemoryRouter initialEntries={["/login"]}>
```

## 6. `getByText`と`findByText`の違い

```ts
screen.getByText("ログイン");
```

- 現在の画面をすぐ検索する
- 見つからなければすぐエラーになる
- 通常は`await`不要

```ts
await screen.findByText("ログイン");
```

- 要素が表示されるまで待って検索する
- `Promise`を返すため`await`が必要
- API処理やstate更新後の表示確認に使う

今回のエラー表示は、次の順番で非同期に表示される。

```text
loginApiが失敗
  ↓
catchが実行される
  ↓
setApiError(error.message)
  ↓
Reactが再レンダー
  ↓
エラーメッセージを表示
```

そのため、`findByText()`を使用した。

## 7. `mockResolvedValue`と`mockRejectedValue`

非同期処理の成功を再現：

```ts
vi.mocked(loginApi).mockResolvedValue(undefined);
```

非同期処理の失敗を再現：

```ts
vi.mocked(loginApi).mockRejectedValue(
  new Error("ログインに失敗しました"),
);
```

厳密には、`mockRejectedValue()`は「エラーを戻り値として返す」のではない。

```text
loginApiが返すPromiseを、エラーでrejectさせる
```

その結果、`await loginApi()`が失敗して`catch`へ進む。

## 9. VitestとE2Eテストの違い

### Vitest

機能を細かく分けて確認する。

```text
LoginPage
→ 正しい情報でAPIを呼ぶか
→ 成功後に移動するか
→ 失敗時にエラーを表示するか

App
→ 未ログインなら/loginへ移動するか
→ ログイン済みなら患者一覧を表示するか

バックエンド
→ 未認証なら401を返すか
→ 他人のデータへアクセスできないか
```

長所：

- 実行が速い
- 不具合の場所を特定しやすい
- 細かい条件を確認しやすい

### E2Eテスト

利用者の操作を最初から最後まで通して確認する。

```text
ブラウザを開く
  ↓
ログイン情報を入力
  ↓
ログインボタンを押す
  ↓
本物のバックエンドへ通信
  ↓
DBでユーザーを確認
  ↓
Cookieを発行
  ↓
患者一覧を表示
```

長所：

- アプリ全体がつながって動くことを確認できる
- 実際の利用者に近い操作を再現できる

短所：

- 実行が遅い
- 準備が多い
- 失敗時の原因特定が難しい

基本方針：

```text
Vitestで細かい機能を確認
        ↓
各機能を安定させる
        ↓
E2Eで重要な操作全体を確認
```
