  fetchAppData: vi.fn(),

  beforeEach(() => {
    vi.resetAllMocks();
  });

  afterEach(() => {
    cleanup();
  });

  it("未ログインならログイン画面を表示する", async () => {
    vi.mocked(fetchAppData).mockRejectedValue(

      <MemoryRouter>

      await screen.findByRole("button", { name: "ログインボタン" }),

  });

      </MemoryRouter>,

    ).toBeInTheDocument();

## 3. 今日理解したこと

### `mockResolvedValue`と`mockRejectedValue`

```ts
// Promiseの成功を再現
vi.mocked(fetchAppData).mockResolvedValue({
  patients: [],
  records: [],
});

// Promiseの失敗を再現
vi.mocked(fetchAppData).mockRejectedValue(
  new Error("API error:401"),
);
```

- `mockResolvedValue`：APIが正常にデータを返す状態
- `mockRejectedValue`：APIでエラーが発生した状態

### テスト側に`if`を書かない理由

エラーを判定する`if / else`は、すでに`App.tsx`に実装されている。

テストの役割は次の3段階。

1. モックで条件を作る
2. `App`を動かす
3. 画面に現れた結果を確認する

テスト側に同じ`if / else`を書くと、`App`ではなくテスト自身の分岐を確認することになってしまう。

### `MemoryRouter`と`initialEntries`

```tsx
<MemoryRouter initialEntries={["/register"]}>
  <Routes>
    <Route path="/register" element={<RegisterPage />} />
    <Route path="/login" element={<p>ログイン画面</p>} />
  </Routes>
</MemoryRouter>
```

- `MemoryRouter`：ブラウザを使わず、テスト内にルーティング環境を作る
- `initialEntries={["/register"]}`：テスト開始時のURLを`/register`にする
- `Routes`：現在のURLに一致する`Route`を探す
- `Route`：URLと表示するコンポーネントを対応させる

### `findByRole`と`findByText`

```ts
await screen.findByRole("button", { name: "ログインボタン" });
await screen.findByText("患者一覧");
```

- `findByRole`：役割と名前で探す
- `findByText`：表示文字から探す
- どちらも非同期処理後に要素が表示されるまで待つ
- `findAllByText`は複数要素の配列を返す

### `toBe()`と`toBeInTheDocument()`

```ts
expect(response.status).toBe(401);

expect(
  await screen.findByText("患者一覧"),
).toBeInTheDocument();
```

- `toBe()`：数値・文字列・真偽値などの値が一致するか確認する
- `toBeInTheDocument()`：取得したHTML要素が画面内に存在するか確認する

## 4. 今日の間違いと修正

### テストを入れ子にした

`it`の中へ別の`it`を書かず、`describe`内の同じ階層に並べる。

```ts
// 修正前：複数要素の配列を返す
screen.findAllByText("APIから読み込めませんでした");

// 修正後：単一要素を返す
screen.findByText("APIから読み込めませんでした");
```

### `App.tsx`の`if / else`をテストへコピーした

テストでは分岐処理を再実装せず、モックで分岐条件を作り、表示結果を確認する。
