## 3. `isLoggedIn`と`!isLoggedIn`

```tsx
if (!isLoggedIn) {
  return <Navigate to="/login" replace />;
}
```

`!`は真偽値を反対にする。

| 状態 | `isLoggedIn` | `!isLoggedIn` | 結果 |
|---|---:|---:|---|
| ログイン済み | `true` | `false` | ログイン画面へ移動しない |
| 未ログイン | `false` | `true` | ログイン画面へ移動する |

```tsx
const isLoggedIn = false;

// !falseはtrue
if (!isLoggedIn) {
  // 実行される
}
```

## 4. 未ログイン時のテスト

確認したい動作は次のとおり。

```text
未ログインで患者一覧URL「/」へアクセス
↓
ログイン画面「/login」へ移動
```

そのため、テスト開始時のURLは`/login`ではなく`/`にする。

```tsx
it("未ログインならログイン画面を表示する", async () => {
  vi.mocked(fetchAppData).mockRejectedValue(
    new Error("API error:401"),
  );

  render(
    <MemoryRouter initialEntries={["/"]}>
      <App />
    </MemoryRouter>,
  );

  expect(
    await screen.findByRole("button", {
      name: "ログインボタン",
    }),
  ).toBeInTheDocument();
});
```

### ポイント

```tsx
initialEntries={["/"]}
```

患者一覧のURLからテストを開始する。

```tsx
new Error("API error:401")
```

401エラーを再現し、未ログイン状態にする。

```tsx
await screen.findByRole("button", {
  name: "ログインボタン",
});
```

非同期処理後にログイン画面が表示されるまで待つ。

## 5. 401と通常エラーの区別

Appでは、エラーメッセージによって処理を分けている。

```tsx
try {
  const data = await fetchAppData();

  setIsLoggedIn(true);

  setAppData({
    patients: Array.isArray(data.patients)
      ? data.patients
      : [],
    records: Array.isArray(data.records)
      ? data.records
      : [],
  });
} catch (error) {
  if (
    error instanceof Error &&
    error.message === "API error:401"
  ) {
    setIsLoggedIn(false);

    setAppData({
      patients: [],
      records: [],
    });
  } else {
    console.error(error);
    setApiError("APIから読み込めませんでした");
  }
} finally {
  setLoading(false);
}
```

### 401の場合

```tsx
new Error("API error:401")
```

`if`へ入り、未ログイン状態にする。

### その他のエラーの場合

```tsx
new Error("Network Error")
```

`else`へ入り、読み込みエラーを表示する。

### `finally`

```tsx
finally {
  setLoading(false);
}
```

成功・401・その他のエラーに関係なく、最後に必ず実行される。

## 6. ローディング状態のテスト

データ取得が完了しない状態を意図的に作成した。

```tsx
vi.mocked(fetchAppData).mockImplementation(
  () => new Promise(() => {}),
);
```

`resolve`も`reject`も呼んでいないため、このPromiseは終了しない。

```text
fetchAppDataが完了しない
↓
App内部のawaitが待ち続ける
↓
loadingがfalseにならない
↓
「読み込み中…」が表示され続ける
```

### 実装したテスト

```tsx
it("データ取得中は読み込み中の表示をする", () => {
  vi.mocked(fetchAppData).mockImplementation(
    () => new Promise(() => {}),
  );

  render(
    <MemoryRouter initialEntries={["/"]}>
      <App />
    </MemoryRouter>,
  );

  expect(
    screen.getByText("読み込み中…"),
  ).toBeInTheDocument();
});
```

## 7. なぜ終了しないPromiseがあってもテストは終わるのか

次のPromise自体は終了しない。

```tsx
new Promise(() => {})
```

しかし、テスト側ではこのPromiseを`await`していない。

```tsx
expect(
  screen.getByText("読み込み中…"),
).toBeInTheDocument();
```

表示確認が終わり、テスト関数の最後まで到達すると、Vitestはテスト終了と判断する。

### 終了しない例

```tsx
it("終了しないテスト", async () => {
  const promise = new Promise(() => {});

  await promise;
});
```

終わらないPromiseを直接`await`すると、その場所で待ち続けてタイムアウトする。

## 8. `getByText`と`findByText`

### `getByText`

現在すでに表示されている要素を、すぐに検索する。

```tsx
screen.getByText("読み込み中…");
```

- Promiseを返さない
- `async`不要
- `await`不要
- 見つからなければすぐ失敗する

### `findByText`

後から表示される要素を待ちながら検索する。

```tsx
await screen.findByText("患者一覧");
```

- Promiseを返す
- `async`が必要
- `await`が必要
- 一定時間待っても見つからなければ失敗する

### 覚え方

```text
現在すでにある表示 → getBy
あとから出る表示   → await findBy
```

今回はローディング状態を意図的に固定し、「読み込み中…」がすぐ表示されるため、`getByText`を使用した。

## 9. `mockImplementation`

`mockImplementation`は、モック関数が呼ばれたときの処理全体を自分で定義する。

```tsx
vi.mocked(fetchAppData).mockImplementation(() => {
  return new Promise(() => {});
});
```

### モックの使い分け

```tsx
// Promiseを成功させる
vi.mocked(fetchAppData).mockResolvedValue({
  patients: [],
  records: [],
});
```

```tsx
// Promiseを失敗させる
vi.mocked(fetchAppData).mockRejectedValue(
  new Error("Network Error"),
);
```

```tsx
// 独自の処理を定義する
vi.mocked(fetchAppData).mockImplementation(
  () => new Promise(() => {}),
);
```

| メソッド | 用途 |
|---|---|
| `mockResolvedValue` | 成功を再現する |
| `mockRejectedValue` | 失敗を再現する |
| `mockImplementation` | モックの処理全体を定義する |

## 13. 今日理解できたこと

- `isLoggedIn`と`!isLoggedIn`の違い
- 未ログインテストを`/`から開始する理由
- 401と通常の通信エラーの処理の違い
- `finally`は成功・失敗に関係なく実行される
- 終了しないPromiseでローディング状態を固定できる
- Promiseが存在するだけではテストは止まらない
- 終わらないPromiseを`await`するとテストも終わらない
- `getByText`は現在の表示をすぐ探す
- `findByText`は後から現れる表示を待つ
- `mockImplementation`でモックの処理全体を定義できる
