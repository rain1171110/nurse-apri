## 4. 今日追加したログアウト成功テスト

### テストの目的

```text
Appを表示
↓
fetchAppData成功
↓
ログイン済みになる
↓
ログアウトボタンが表示される
↓
ログアウトボタンをクリック
↓
logoutApi成功
↓
isLoggedInがfalseになる
↓
ログイン画面が表示される
```

### 完成したテスト

```tsx
it("ログアウトボタンを押したらログイン画面を表示する", async () => {
  vi.mocked(fetchAppData).mockResolvedValue({
    patients: [],
    records: [],
  });
  vi.mocked(logoutApi).mockResolvedValue(undefined);

  const user = userEvent.setup();

  render(
    <MemoryRouter initialEntries={["/"]}>
      <App />
    </MemoryRouter>,
  );

  const logoutButton = await screen.findByRole("button", {
    name: "ログアウトボタン",
  });

  await user.click(logoutButton);

  expect(logoutApi).toHaveBeenCalledTimes(1);

  expect(
    await screen.findByRole("button", {
      name: "ログインボタン",
    }),
  ).toBeInTheDocument();
});
```

## 5. `authApi`のモック

### import

```tsx
import { logoutApi } from "./api/authApi";
```

### モック定義

```tsx
vi.mock("./api/authApi", async (importOriginal) => {
  const actual = await importOriginal<typeof import("./api/authApi")>();

  return {
    ...actual,
    logoutApi: vi.fn(),
  };
});
```

### 意味

`authApi`にある他の関数は本物のまま残し、`logoutApi`だけを偽物の関数へ置き換える。

```text
...actual
→ authApiにある元の関数を残す

logoutApi: vi.fn()
→ logoutApiだけをテスト用の偽物に置き換える
```

`vi.mock()`は個別の`it`の中ではなく、ファイル上部に記述する。

## 6. `vi.mock()`とは

### 基本

モックとは、単なる仮データではない。

> 本物の関数や外部処理を、テスト用の偽物に置き換える仕組み

### appDataApiのモック

```tsx
vi.mock("./api/appDataApi", () => ({
  fetchAppData: vi.fn(),
}));
```

これは次の意味。

```text
./api/appDataApiをテスト用に置き換える
↓
本物のfetchAppDataを使用しない
↓
fetchAppDataをvi.fn()で作った偽物にする
```

通常時とテスト時の違い。

```text
通常時
App
→ 本物のfetchAppData
→ バックエンドへ通信
→ データベースからデータ取得

テスト時
App
→ 偽物のfetchAppData
→ バックエンドへ通信しない
→ テスト内で指定した結果を返す
```

---

## 7. モックとモックデータの違い

### モック

```tsx
fetchAppData: vi.fn()
```

本物の`fetchAppData`の代わりになる偽物の関数。

### モックデータ

```tsx
{
  patients: [],
  records: [],
}
```

偽物の関数から返す仮のデータ。

### 整理

```text
vi.mock()
→ 本物を偽物へ交換する

vi.fn()
→ 偽物の関数を作る

mockResolvedValue()
→ 偽物の関数が成功時に何を返すか決める

mockRejectedValue()
→ 偽物の関数がどんなエラーを返すか決める
```

---

## 8. `vi.mock()`と`mockResolvedValue()`の違い

### 本物を偽物へ交換

```tsx
vi.mock("./api/appDataApi", () => ({
  fetchAppData: vi.fn(),
}));
```

この時点では、`fetchAppData`が何を返すかはまだ決まっていない。

### 今回のテストで返す内容を設定

```tsx
vi.mocked(fetchAppData).mockResolvedValue({
  patients: [],
  records: [],
});
```

これはAPI成功を再現している。

```tsx
vi.mocked(fetchAppData).mockRejectedValue(
  new Error("Network Error"),
);
```

これはAPI失敗を再現している。

## 9. なぜ`fetchAppData`を成功させるのか

`App.tsx`では、`fetchAppData()`が成功するとログイン済みになる。

```tsx
const data = await fetchAppData();
setIsLoggedIn(true);
```

そのため、ログアウトボタンを表示するには、最初に`fetchAppData`を成功させる必要がある。

```tsx
vi.mocked(fetchAppData).mockResolvedValue({
  patients: [],
  records: [],
});
```

重要な点。

```text
患者が存在するからログイン済み
ではない

fetchAppDataが成功したからログイン済み
```

患者0件、記録0件でも、API通信が成功すればログイン済みになる。

## 10. なぜ`findByRole`を使うのか

Appを表示した直後は、まだデータ取得中。

```tsx
loading === true
```

この時点ではログアウトボタンは表示されず、「読み込み中…」が表示される。

`fetchAppData()`が完了した後にログアウトボタンが表示されるため、表示を待てる`findByRole`を使う。

```tsx
const logoutButton = await screen.findByRole("button", {
  name: "ログアウトボタン",
});
```

### 違い

```text
getByRole
→ 今すぐ画面内を探す

findByRole
→ 要素が表示されるまで待って探す
```

`findByRole()`はPromiseを返すため、`await`が必要。

## 12. 今日つまずいた点

### 最初はLoginPageを直接表示していた

ログアウト処理は`App.tsx`にあるため、テスト対象は`LoginPage`ではなく`App`。

```tsx
render(
  <MemoryRouter initialEntries={["/"]}>
    <App />
  </MemoryRouter>,
);
```

### 存在しないメッセージを確認しようとした

最初は次を確認しようとしていた。

```tsx
screen.findByText("ログアウトしました");
```

しかし、`App.tsx`には「ログアウトしました」という表示はない。

実際のログアウト成功後はログイン画面が表示されるため、「ログインボタン」を確認する。

### `findByRole`に`await`が抜けた

誤り。

```tsx
const logoutButton = screen.findByRole("button", {
  name: "ログアウトボタン",
});
```

正しいコード。

```tsx
const logoutButton = await screen.findByRole("button", {
  name: "ログアウトボタン",
});
```
