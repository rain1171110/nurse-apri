## 3. 実装の要点（理解を深める）

```tsx
const onSubmit = vi.fn().mockResolvedValue(undefined);
const setShowAddForm = vi.fn();

const nameInput = screen.getByLabelText("氏名");
const roomInput = screen.getByLabelText("部屋番号");
await user.type(nameInput, "testName");
await user.type(roomInput, "999");

await user.click(screen.getByRole("button", { name: "保存" }));

await waitFor(() => {
  expect(onSubmit).toHaveBeenCalledTimes(1);
});

expect(nameInput).toHaveValue("testName");
expect(roomInput).toHaveValue("999");
expect(setShowAddForm).not.toHaveBeenCalled();
```

- このコードの責務: `onSubmit` が `undefined` を返す設定で保存し、呼び出しとフォームの状態を確認する。
- 入力: 氏名 `"testName"`、部屋番号 `"999"`。
- 出力: `onSubmit` のモックは `undefined` に解決する Promise を返す。
- 副作用: 保存操作によって `onSubmit` が呼ばれる。
- 型をどう絞り込んだか: このテスト内では型ガードを追加していない。コンポーネント側の `if (!savedPatient)` が戻り値を判定する。
- `undefined` をどう安全に扱ったか: `savedPatient` が falsy なら `return` し、`reset()` と `setShowAddForm(false)` に進まない。
- 型で守れていること: `onSubmit` の型は `Promise<Patient | undefined>` で、保存できなかった場合も表現できる。
- 似た書き方との違い: `toHaveBeenCalledWith(...)` は渡した**引数**、`toHaveBeenCalledTimes(1)` は呼ばれた**回数**を確認する。どちらも戻り値の確認ではない。
- 改善余地: このテストの `waitFor` は呼び出しまでしか待たない。保存処理の完了後も入力が残ることを厳密に保証するテストには、別の完了確認が必要。

保存成功時は `await onSubmit(data)` の後に `reset()` するため、入力欄が空になる変化を `waitFor` で待つ。キャンセル時はクリック処理で直接 `reset()` を呼ぶため、次回は以下を既存のキャンセルテストに追加する。

```tsx
const nameInput = screen.getByLabelText("氏名");
await user.type(nameInput, "testName");

await user.click(cancelButton);

expect(nameInput).toHaveValue("");
expect(setShowAddForm).toHaveBeenCalledWith(false);
```

## 5. つまずきから学ぶ（再発防止まで）

- つまずいた現象: `toHaveBeenCalledWith(1)` の `1` を、戻り値や呼び出し回数と混同した。
- 直接原因: `CalledWith` が検査するのは関数へ渡された引数だと整理できていなかった。
- 根本原因: 関数の「引数」「戻り値」「呼び出し回数」と、Promiseの「処理完了」を一緒に考えていた。
- 切り分け手順:
  1. モックが何を返す設定か確認する。
  2. コンポーネントがモックに何を渡すか確認する。
  3. `expect` が引数・回数・画面状態のどれを検査しているか読む。
  4. その確認が非同期処理の完了後に行われるか考える。
- 再発防止ルール: `waitFor` を書く前に、「何が変化するのを待つのか」を1文で言う。
