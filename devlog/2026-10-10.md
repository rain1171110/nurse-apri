## 2. 復習クイズと振り返り

結果：3／5問正解。

| テーマ | 結果 | 理解した内容 |
| --- | --- | --- |
| 保存結果がundefined | 正解 | 成功時の処理は実行されず、フォームと入力が残る |
| 要素の非存在確認 | 正解 | queryByRoleとnot.toBeInTheDocumentを使う |
| 0とnullの扱い | 正解 | ??は0を保持し、null・undefinedだけ置き換える |
| 患者データの取得制限 | 誤答 | 認証済みユーザーIDでwhere条件を指定する |
| 非同期のフォーム終了 | 誤答 | falseで閉じる処理をwaitForで確認する |

### ユーザーごとの患者取得

条件なしのfindManyでは、他ユーザーの患者も取得する。
認証処理で確認したユーザーIDを使って絞り込む。

```ts
prisma.patient.findMany({
  where: { userId: req.userId },
});
```

req.body.userIdは利用者が変更できる値なので、認証済みIDの代わりに使わない。

### 保存後にフォームを閉じる処理

```tsx
await waitFor(() => {
  expect(setShowAddForm).toHaveBeenCalledWith(false);
});
```

- true：フォームを表示する
- false：フォームを閉じる
- waitFor：期待する非同期処理の結果を待つ

## 3. 不具合と修正内容

### ① CORSによるAPI通信の失敗

症状：
- Failed to fetch
- NetworkでCORSエラー

原因：
- サーバーがlocalhostの画面だけを許可していた

修正：
- ローカルと固定の本番URLを許可した
- デプロイごとに変わるURLではなく、本番ドメインを使用した

```ts
app.use(
  cors({
    origin: [
      "http://localhost:5173",
      "https://nurse-apri.vercel.app",
    ],
    credentials: true,
  }),
);
```

### ② /loginを再読み込みすると404

原因：
- VercelでReact Routerのパスへの直接アクセスを処理する設定がなかった

修正：
- プロジェクト直下にvercel.jsonを追加した

```json
{
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

### ③ Prisma Clientが存在しない

症状：
- Vercelの型チェックで生成ファイルが見つからない
- Renderでも同じ生成先のモジュールが見つからず起動失敗

修正：
- ビルド時にPrisma Clientを生成するようにした

package.json：

```json
"build": "prisma generate && npm run typecheck && vite build"
```

Renderの最終的なBuild Command：

```bash
npm install && npx prisma generate && npx prisma migrate deploy
```

RenderのStart Command：

```bash
npm run api
```

### ④ Renderの環境変数が未設定

症状：
- DATABASE_URL is not defined
- JWT_SECRET is not defined

対応：
- Renderに公開用PostgreSQLを作成した
- Internal Database URLをDATABASE_URLに設定した
- ランダムな秘密鍵を生成し、JWT_SECRETに設定した
- 公開DBに3件のマイグレーションを適用した

理解した点：
- ローカルの.envはRenderへ自動で反映されない
- 自分のPCのlocalhostは、Renderから接続できない
- Prisma Clientの生成と、DBのテーブル作成は別の処理

### ⑤ ログイン成功後もdataが401

症状：
- register：201
- login：200
- data：401

原因：
- CookieがSameSite=Strictで、VercelとRenderをまたぐ認証通信に適していなかった

修正：
- ログインとログアウトの両方で、本番のSameSiteをnoneに変更した

```ts
sameSite: process.env.NODE_ENV === "production" ? "none" : "strict",
```

既存の設定：

```ts
secure: process.env.NODE_ENV === "production",
httpOnly: true,
```

修正後：
- login：200
- data：200
- 再読み込み後もログイン状態を維持
- ログアウト後もログアウト状態を維持

## 5. 今日の気づき

- Networkでは、名前だけでなく種類も見る。documentのloginと、fetchのloginは別の通信。
- 204のプリフライト応答だけでは、実際のAPI通信の成功を判断できない。
- 401は未認証を示す。未ログイン時なら正常だが、ログイン直後なら認証の引き継ぎを確認する。
- 304はエラーではなく、変更がないためキャッシュを再利用する応答。
- GitHubへpushしただけでは公開環境への反映は完了しない。対象コミットとLive／Readyを確認する。
- Build successfulでもAPI起動に失敗することがある。起動ログとLiveまで確認する。
- 古いデプロイログと最新ログを、コミット・開始時刻・Build Commandで区別する。
- 保存成功は、画面表示だけでなく再読み込み後のデータでも確認する。
- ユーザーごとのデータ分離と、管理者などの役割による権限管理は別の機能。
