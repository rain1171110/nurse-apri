- 修正前のコードの問題点: 同じ元の行をA/Bで別々に変更していたため、Gitがどちらを採用するか決められなかった。
- 修正後の意図: AとBの意図を両方残し、失いたくない情報を手動で統合する。
- なぜその修正で直ったのか（3行で説明）:
  1. 競合マーカー（`<<<<<<<`など）を除去して、最終的に残す内容を人間が決めた。
  2. `git add`で「このファイルは解消済み」とGitに伝えた。
  3. `git commit`でマージを確定し、競合状態を終了した。
- 自分が理解した手順:
  1. 競合発生を`git status`で確認する
  2. 競合ファイルを開いて、残す内容を決める
  3. 競合マーカーを削除して保存する
  4. `git add`して解消済みにする
  5. `git commit`してマージ完了にする
- 次回同じような時にやること: `git merge`実行前に「今いるブランチ」と「取り込むブランチ」を声に出して確認する。

## 2. 技術判断ログ（エンジニア視点）

- 解決したかった課題: 競合の発生条件を体験し、解消の標準手順を再現可能にする。
- 検討した選択肢:
  - 案A: 競合時にどちらか片方の変更だけを採用する
  - 案B: 競合時にA/B両方の内容を残して手動統合する
- 採用した案: 案B
- 採用理由（性能/保守性/実装コスト/安全性）: 練習目的として、両側の変更を読み取って統合する力をつけられるため。
- 採用しなかった案を捨てた理由: 片方のみ採用すると、もう片方の意図を失い、競合解消の理解が浅くなるため。

## 3. 実装の要点（理解を深める）

```bash
git switch practice/conflict-a-repeat
git merge practice/conflict-b-repeat
git status
cat ファイル名
git add ファイル名
git commit -m "Resolve merge conflict"
```

- このコードの責務（1文）: 競合を発生させた後、内容確認と解消完了までを実行する。
- 入力: 現在ブランチ（A）、取り込み対象ブランチ（B）、競合したファイル内容。
- 出力: 競合が解消され、マージコミットが作成された状態。
- 副作用（ある場合）: ブランチ履歴にマージコミットが追加される。
- 型をどう絞り込んだか（typeof / in / instanceof / 判別可能な Union など）: 対象外（CLI操作のため）。
- null / undefined をどう安全に扱ったか（?. / ?? / nullチェック など）: 対象外（CLI操作のため）。
- 型で守れていること: 対象外。
- 似た書き方との違い（例: || と ?? / 型キャスト と 型ガード）: `git merge ブランチ名`は「指定ブランチを、今いるブランチに取り込む」点が重要。
- 修正ポイント（自分がどこを変えたか）: 競合マーカーを削除し、A/Bの両行を残した統合内容に編集した。
- その修正で理解したこと: 競合はGitのエラーではなく、「最終版を人が決める場面」だと理解できた。
- 改善余地（命名/分割/重複/境界条件）: 練習時に使う文字列（例: `orginal`）は今後`original`へ統一し、見間違いを減らす。

## 5. つまずきから学ぶ（再発防止まで）

- つまずいた現象: 競合解消後に何をすればマージ完了になるか曖昧になりやすい。
- 直接原因: 編集完了とGitへの解消報告（`git add`）を同じものとして捉えていた。
- 根本原因（思考・知識・確認不足のどれか）: 手順の区切り（編集・報告・確定）の理解不足。
- 切り分け手順（次回使える手順化）:
  - 1. `git status`で「unmerged paths」があるか確認する
  - 2. ファイル編集で競合マーカーを除去する
  - 3. `git add`で解消済みとして登録する
  - 4. `git status`で競合表示が消えたことを確認する
  - 5. `git commit`でマージを確定する
- 再発防止ルール（チェック項目にする）: 「編集しただけでは完了しない。`add`と`commit`までで1セット」を毎回確認する。
