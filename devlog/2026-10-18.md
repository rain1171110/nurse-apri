## 3. 実装の要点（理解を深める）

```ts
const agentDataResponse = await agent.get("/api/data");
const otherAgentDataResponse = await otherAgent.get("/api/data");

const agentRecordIds = agentDataResponse.body.records.map(
  (record: { id: string }) => record.id,
);

const otherAgentRecordIds = otherAgentDataResponse.body.records.map(
  (record: { id: string }) => record.id,
);

expect(agentRecordIds).toContain(createRecordResponse.body.id);
expect(agentRecordIds).not.toContain(createOtherRecordResponse.body.id);

expect(otherAgentRecordIds).toContain(createOtherRecordResponse.body.id);
expect(otherAgentRecordIds).not.toContain(createRecordResponse.body.id);
```

- このコードの責務：A/Bそれぞれの記録一覧に、自分の記録だけが含まれることを確認する。
- 入力：A/BそれぞれのGETレスポンスと、POSTで作成した記録ID。
- 出力：条件を満たせばテスト成功、満たさなければ失敗。
- 副作用：GET自体に記録作成の副作用はない。患者・看護記録は先行するPOSTで作成する。
- 型をどう絞り込んだか：`record`に`{ id: string }`を指定した。これは型注釈であり、実行時のデータ検証ではない。
- `null` / `undefined`の扱い：このコードでは個別に扱っていない。
- 型で守れていること：コールバック内の`record.id`が文字列であること。Supertestの`body`全体の型は別途確認が必要。
- 似た書き方との違い：`toContain`はID配列の値を比較する。オブジェクト配列を直接調べる場合は`toContainEqual`と`objectContaining`を使える。
- 修正ポイント：記録作成の期待ステータスを`201`に合わせ、GET結果の記録IDを比較した。
- 改善余地：テストは`describe("POST /api/records")`の中にあるが、閲覧確認は`GET /api/data`で行っている。内容に合わせたテスト名にすると明確。

## 5. つまずきから学ぶ（再発防止まで）

- つまずいた現象：テストが「Expected 200, Received 201」で失敗した。
- 直接原因：記録作成のステータス期待値が実際のAPIと違っていた。
- 根本原因：既存APIの返却値を確認する前に`200`と決めていた。
- 切り分け手順：
  1. エラー出力のExpectedとReceivedを確認する。
  2. 対象APIの実装や既存テストで成功時の値を確認する。
  3. 原因に対応する期待値だけを修正する。
  4. 同じテストコマンドで再実行する。
- 再発防止ルール：POST成功時のステータスとレスポンス形状は、既存テストまたはAPI実装を確認してから書く。
