## 2. 技術判断ログ

- 解決したかった課題：APIテストのデータを開発用DBと混ぜないようにする
- 検討した選択肢：
  - 案A：開発用DBでテストし、`afterAll`でテストデータを削除する
  - 案B：テスト用DBを用意し、テストをそのDB内で実行する
- 採用した案：テスト用DBを使う
- 採用理由：強制終了、削除処理の失敗、テストコードのミスがあっても、開発用データへの影響を抑えやすい
- 採用しなかった案を捨てた理由：`afterAll`だけでは、常に後片付けが成功するとは限らない

### 今日理解したこと

- `beforeAll`はテスト前の準備、`afterAll`はテスト後の後片付けに使う。
- 後片付けがあっても、強制終了や削除失敗などでデータが残る可能性はある。
- テスト用DBを分けると、その場合に開発用データを守りやすい。

- 責務・目的：各コマンドで設定、DB、テスト結果、READMEの差分を確認する
- 入力：ファイル名、検索語、環境変数、テスト対象
- 出力：検索結果、DB名、マイグレーション結果、テスト結果、差分
- 副作用：マイグレーションとAPIテストはDBに接続する。APIテストはテストデータを作成・削除する
- 型の絞り込み：該当なし
- null／undefinedの扱い：該当なし
- 型で守れていること：該当なし
- 似た書き方との違い：`grep`で`|`を「または」として使うには`-E`が必要
- 改善余地：コマンドを実行する前に、どの環境設定・DBが対象になるか確認する

## 5. 質問・つまずきと再発防止

- 質問したこと：`beforeAll`と`afterAll`でデータを準備・削除しているなら、テスト用DBを分けなくてもよいのではないか
- つまずいた現象：コマンドの目的や、`.env.test`を指定する理由が分からなくなった
- 直接原因：複数の確認作業が続き、各コマンドが何を対象にしているか見えにくくなった
- 根本原因：コマンドの目的・対象・結果を順番に整理できていなかった
- 最終的に理解したこと：`afterAll`は後片付けをするが、失敗や強制終了に備えるためDBを分ける
- 次回の切り分け手順：
  1. 何を確認するコマンドか説明する
  2. どのファイル・DB・環境設定を使うか確認する
  3. 実行結果が何を意味するか読む
  4. 分からない結果を一つずつ確認する
- 再発防止ルール：DBに関係するコマンドでは、実行前に`.env`と`.env.test`のどちらを使うか確認する

## 追加学習：PostgreSQLのDB一覧の表示結果

実行したSQLは、PostgreSQLが管理しているデータベース一覧から、テンプレート用ではないDB名を取得する。

```sql
SELECT datname
FROM pg_database
WHERE datistemplate = false
```

取得結果を`rows`に入れ、`console.log(rows)`で表示するため、次のような形式になった。

```text
[
  { datname: 'postgres' },
  { datname: 'nurse_apri_dev' },
  { datname: 'nurse_apri_test' }
]
```

この結果から、今回の接続先では`postgres`、`nurse_apri_dev`、`nurse_apri_test`の3つが一覧に含まれていると分かる。DB名の一覧であり、各DB内のテーブルや患者データを表示したものではない。

以前設定した`nurse_apri_shadow`は今回の結果に表示されなかった。SQLでその名前を除外してはいないため、現在の接続先には存在しないか、別の接続先にある可能性がある。`.env`の`SHADOW_DATABASE_URL`が示す接続先を、パスワードなどを表示しない方法で次回確認する。
