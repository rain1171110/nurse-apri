## 3. 実装・技術の要点

- 重要なコードまたはコマンド：今日、コマンドは使用していない。確認した既存コードの要点は次のとおり。

```ts
const decoded = jwt.verify(token, JWT_SECRET);

if (typeof decoded === "string" || typeof decoded.userId !== "string") {
  res.status(401).json({
    error: "Invalid token payload / トークン内容が無効です",
  });
  return;
}

req.userId = decoded.userId;
next();
```

- 責務・目的：`requireAuth`がCookie内のトークンを検証し、認証に成功したユーザーのIDを後続処理へ渡す
- 入力：リクエストの`req.cookies.token`
- 出力：認証成功時は`req.userId`を設定して`next()`を呼ぶ。Cookieがない、またはトークンが無効な場合は401を返す
- 副作用：リクエストに`userId`を設定する。認証失敗時はレスポンスを返す
- 型の絞り込み（該当する場合）：`typeof decoded === "string"`を先に確認し、その後`decoded.userId`が文字列か確認する
- null／undefinedの扱い（該当する場合）：トークンがない場合は401を返す。`JWT_SECRET`がない場合は初期化時にエラーにする
- 型で守れていること：確認したコードでは、JWTの内容が文字列ではなく、`userId`が文字列であることを確認している。`req.userId`の型宣言は未確認
- 似た書き方との違い：`jwt.decode()`ではなく`jwt.verify()`を使い、署名などを検証している
- 今日理解したこと：
  - ブラウザーは、Cookieの保存先や`SameSite`などの条件に合うリクエストへCookieを自動で付ける
  - ブラウザーがログイン状態を検証するのではない。APIサーバーがJWTを検証してログイン中のユーザーを判断する
  - 偽のJWTは`jwt.verify()`で拒否される。一方、CSRFは偽のJWTを作る攻撃ではなく、ブラウザーに保存済みの本物のCookieを送らせようとする攻撃
  - フォームの`action`は送信先、`method="POST"`はHTTPメソッドを指定する。実際の送信はフォーム送信処理が行う
  - フォームのメールアドレスとCookie送信は別の話。メールアドレスを取得したからCookieが送られるわけではない
  - CORSはブラウザーのクロスオリジン通信に関する仕組み、JWT検証は認証、患者の`userId`確認は認可、CSRF対策は意図しないリクエストへの対策
- 改善余地：状態を変更するAPIで`Origin`確認やCSRFトークンを使う必要があるか、実際の全ルートとテストを確認する

- 追加実装メモ：`server/index.ts`には、CORSとAPI側のOrigin確認を組み合わせた実装が追加されている

```ts
const allowedOrigins = new Set([
  "http://localhost:5173",
  "https://nurse-apri.vercel.app",
]);

app.use(
  cors({
    origin: [...allowedOrigins],
    credentials: true,
  }),
);

app.use((req, res, next) => {
  const isStateChangingMethod = ["POST", "PUT", "PATCH", "DELETE"].includes(
    req.method,
  );

  if (!isStateChangingMethod) {
    next();
    return;
  }

  const origin = req.get("Origin");
  if (!origin || !allowedOrigins.has(origin)) {
    res.status(403).json({
      error: "Request origin is not allowed",
    });
    return;
  }

  next();
});
```

- 責務・目的：CORSはブラウザーのクロスオリジン通信を許可する設定、OriginチェックはAPI側で「この送信元は許可済みか」を確認する対策、JWT検証は「ログイン済みか」を確認する対策
- 入力：HTTPメソッド、`Origin`ヘッダー、Cookie内のJWT
- 出力：許可外Originは403、JWTがないまたは無効なら401、通過したリクエストは次のミドルウェアやルートへ進む
- 副作用：状態変更リクエストが許可済みOrigin以外から来た場合は終了させる。認証済みリクエストには`req.userId`を持たせる
- 今日理解したこと：
  - CORSとOriginチェックは役割が違う。CORSはブラウザーが通信を許すか判断し、Originチェックはサーバー側が送信元を確認する
  - `Origin`は`http://localhost:5173`のような「どこから来たか」を表す情報で、攻撃者のサイトは通常この値を偽れない
  - 変更系APIだけをOriginでチェックするのは、ログイン状態確認とCSRF対策を分離して考えるための最小構成として理解しやすい
  - 実装を確認した今では、まだ「本当に動くか」をテストで確認する必要がある

## 5. 質問・つまずきと再発防止

- 質問したこと：
  - `httpOnly` Cookieは何を防ぐのか。XSSとは何か
  - `credentials: "include"`は何をするのか
  - CORS、JWT、CSRFの違いは何か
  - CSRFでは、どのように意図しない操作を送らせるのか
  - フォームの`action`と`method`は何を指定し、Cookieはどう送られるのか
- つまずいた現象：フォームのメールアドレスを取得したことで、APIがログイン状態と判断してCookieを送るように見えていた
- 直接原因：フォームの送信内容、ブラウザーがCookieを送る処理、APIがJWTを検証する処理が混同していた
- 根本原因（知識／確認／考え方など）：ブラウザーとAPIサーバーの責務、リクエストの順番が整理できていなかった
- 最終的に理解したこと：
  - ブラウザーは、保存済みCookieと送信先・Cookie属性をもとにCookieを送る
  - APIサーバーがJWTを検証し、ログイン中のユーザーを判断する
  - CSRFは、ログイン済みブラウザーに本人の意図しないリクエストを送らせる攻撃
  - フォームに設定したメールアドレスは送信する操作内容であり、Cookie送信の条件ではない
- 次回の切り分け手順：

  3. 原因候補を絞る
  4. 修正または対応後に確認する
- 再発防止ルール：リクエストの流れを「ブラウザーがCookieを送る」「APIがJWTを検証する」「APIがデータの所有者を確認する」に分けて考える

  - XSS：Webページ上で意図しないスクリプトを実行させる脆弱性
  - CSRF：ログイン中のブラウザーに意図しないリクエストを送らせる攻撃
