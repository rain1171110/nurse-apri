## 2. 技術判断ログ

- 解決したかった課題：`Origin`ヘッダーをなぜリクエストに付けるのか理解する
- 検討した選択肢：
  - 案A：送信元をIPアドレスで確認する
  - 案B：ブラウザが送るOriginヘッダーを確認する
- 採用した案：アプリではOriginヘッダーを許可リストと照合している
- 採用理由（性能／保守性／実装コスト／安全性など）：リクエストを送ったページのOriginを確認し、許可していない送信元からの変更系リクエストを拒否するため
- 採用しなかった案と理由：IPアドレスによる確認は、どのWebページからリクエストが開始されたかを示す情報ではない

## 3. 実装・技術の要点

- 重要なコードまたはコマンド：

```ts
const origin = req.get("Origin");
if (!origin || !allowedOrigins.has(origin)) {
  res.status(403).json({
    error: "Request origin is not allowed",
  });
  return;
}
```

- 責務・目的：リクエストのOriginがない、または許可リストに含まれない場合に403を返す
- 入力：HTTPリクエストの`Origin`ヘッダー
- 出力：許可されない場合は403とエラーメッセージ。許可された場合は、この条件分岐を通過する
- 副作用：拒否時はHTTPレスポンスを返し、`return`で現在のミドルウェアの処理を終える
- 型の絞り込み（該当する場合）：該当なし
- null／undefinedの扱い（該当する場合）：`!origin`でOriginがない場合も拒否する
- 型で守れていること：未記録
- 似た書き方との違い：`.set("Origin", "...")`はSupertestでテストリクエストにヘッダーを付ける書き方。`allowedOrigins.has(origin)`はサーバー側でその値が許可リストにあるか調べる処理
- 今日理解したこと：OriginはユーザーのIPアドレスではなく、リクエスト元のページのオリジンを示す情報。コードの各行の詳しい動きは次回確認する
- 改善余地：許可された場合に後続処理へ進む流れも含めて、ミドルウェア全体を理解する

## 5. 質問・つまずきと再発防止

- 質問したこと：
  - `Origin`はIPアドレスに記載されている情報なのか
  - なぜテストで`.set("Origin", "http://localhost:5173")`を付けるのか
  - `req.get("Origin")`から始まる条件分岐は何をしているのか
- つまずいた現象：Originヘッダーを付ける目的と、許可リストで確認する処理の意味がまだ十分に理解できていない
- 直接原因：テスト側でヘッダーを設定する処理と、サーバー側でOriginを確認する処理の関係が分かりにくかった
- 根本原因（知識／確認／考え方など）：HTTPヘッダー、送信元ページのOrigin、IPアドレスの役割を整理する必要がある
- 最終的に理解したこと：OriginはIPアドレスではなく、リクエスト元のページを示す情報。詳細なコード理解は次回に続ける
