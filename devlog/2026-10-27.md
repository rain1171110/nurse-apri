## 3. 実装・技術の要点

- 重要なコードまたはコマンド：

  実際に確認したOriginチェックの流れ：

```ts
if (!isStateChangingMethod) {
  next();
  return;
}

const origin = req.get("Origin");

if (!origin || !allowedOrigins.has(origin)) {
  res.status(403).json({
    error: "Request origin is not allowed",
  });
  return;
}

next();
```

  確認に使ったコマンド：

```bash
grep -En "clearCookie|jwt\.verify|denylist|revok|jti|tokenVersion|session" server
```

- 用途：`server`内でJWT検証、ログアウト、失効リストなどに関係する語を検索する。
- 結果：`server`がディレクトリであるため、再帰検索の指定がなくエラーになった。

```bash
grep -RInE "clearCookie|jwt\.verify|denylist|revok|jti|tokenVersion|session" server
```

- 用途：`server`以下を再帰的に検索する。
- 意味：`-R`はディレクトリ内も検索、`-I`はバイナリを除外、`-n`は行番号を表示、`-E`は複数パターンの指定。
- 結果：`server/auth.ts`の`jwt.verify`と、`server/index.ts`の`res.clearCookie("token", ...)`が見つかった。検索語と一致する失効リストの記述は見つからなかった。

```bash
sed -n '15,40p' server/auth.ts
sed -n '535,560p' server/index.ts
```

- 用途：指定した行の範囲を表示し、JWT認証処理とログアウト処理を確認する。
- 結果：認証処理はCookieからJWTを読み、`jwt.verify`後に`req.userId`を設定して`next()`する。ログアウト処理はCookieを消去して成功レスポンスを返すコードを確認した。

```bash
grep -n -B 8 -A 15 "allowedOrigins.has" server/index.ts
```

- 用途：`allowedOrigins.has`の前後のコードを表示する。
- 意味：`-B 8`は前8行、`-A 15`は後ろ15行を表示する。
- 結果：変更系メソッドの判定、Origin取得、403レスポンス、`return`、許可時の`next()`を確認した。

- 責務・目的：
  - `express.json()`：JSON形式のリクエスト本文を読み取り、`req.body`から使えるようにする。
  - `cookieParser()`：Cookieヘッダーを読み取り、`req.cookies`に入れる。
  - Originチェック：変更系メソッドのリクエストについて、Originがない場合や許可リストにない場合に403を返す。
  - `requireAuth`：Cookie内のJWTを検証する。
  - `res.json(data)`：サーバーからフロントエンドへJSONレスポンスを返す。
- 入力：
  - HTTPメソッド、パス、ヘッダー、必要に応じてリクエスト本文。
  - `GET /api/data`では、認証用JWTはJSON本文ではなくCookieヘッダーに含まれる。
- 出力：
  - 認証・データ取得が成功した場合、`res.json(data)`でサーバーからデータを返す。
  - Originが許可されない変更系リクエストでは403を返す。
- 副作用：コード修正やテスト実行はなし。
- 型の絞り込み（該当する場合）：該当なし
- null／undefinedの扱い（該当する場合）：`req.get("Origin")`はOriginヘッダーがなければ`undefined`になりうる。`!origin`で値がない場合を判定する。
- 型で守れていること：該当なし
- 似た書き方との違い：
  - `express.json()`はリクエスト本文のJSONを読む。Cookieヘッダーは読まない。
  - `cookieParser()`はCookieヘッダーを読む。リクエスト本文のJSONは読まない。
  - Originチェックミドルウェア内の`next()`は後続ミドルウェアへ渡す。`requireAuth`内の`next()`は同じルート内の次の処理へ進める。
  - 403分岐の`return`はレスポンスを返した後、後続処理に進ませない。
- 今日理解したこと：
  - `req.get("Origin")`はOrigin値を読み取るだけで、許可リストとの照合は別の処理で行う。
  - HTTPヘッダーはHTMLの`<header>`要素とは別。
  - `GET /api/data`は通常JSON本文を送らないが、認証用Cookieをヘッダーに付けて送れる。
  - `GET`は変更系メソッドの判定を通らず、`next()`で後続ミドルウェアへ進む。
  - Expressはミドルウェアを登録順に処理し、その後、HTTPメソッドとパスに一致するルートを実行する。
  - `app.get("/api/data", requireAuth, handler)`では、ルートが一致した後に`requireAuth`、続いてデータ取得処理が実行される。
  - `express.json()`はJSONのリクエスト本文を`req.body`にし、`res.json(data)`はサーバーからのレスポンスを送る。
  - JWTは`expiresIn: "1h"`により、`jwt.sign(...)`で発行した時点から1時間有効。
  - 再ログインは新しいJWTを発行するが、個別失効機能がなければ古いJWTをすぐに無効化するわけではない。
- 改善余地：APIの基本的なリクエスト／レスポンスの流れを復習してから、Originチェックの理解に戻る。

## 5. 質問・つまずきと再発防止

- 質問したこと：
  - HTTPヘッダーはHTMLの`<header>`と同じか。
  - Originヘッダーは必ず付くのか。開発者ツールで見られるか。
  - `next()`はどこに進むのか。`return`の後は処理が終了するのか。
  - `GET /api/data`で認証はどのように行われるのか。
  - `express.json()`はフォーム送信とどう関係するのか。
  - JWTの有効期限はどこで設定し、再ログイン後に古いJWTも使えるのか。
  - JWTの個別失効機能はポートフォリオに必要か。
- つまずいた現象：
  - Originチェック、Expressミドルウェア、APIルート、Cookie、JSON本文、レスポンスの関係が混ざり、処理の流れが分かりにくくなった。
  - `grep`でディレクトリを再帰指定せず検索し、`grep: server: Is a directory`になった。
- 直接原因：
  - `next()`で進む範囲と`return`で終了する範囲、リクエストヘッダーと本文、サーバーからのレスポンスを区別しきれていなかった。
- 根本原因（知識／確認／考え方など）：APIリクエストの基本構造とExpressの処理順を復習する前に、認証とOriginチェックを同時に学んだこと。
- 最終的に理解したこと：
  - JWTはCookieヘッダーに付く。
  - 患者入力などJSON本文を読むのは`express.json()`。
  - Cookieを`req.cookies`に取り出すのは`cookieParser()`。
  - `res.json(data)`はサーバーから送るレスポンス。
  - `next()`後の`return`は現在のミドルウェアを終了させるが、先に呼んだ`next()`によりリクエストは後続処理へ進む。
  - 不許可Originでは403を返して終了し、`next()`は呼ばれない。
- 次回の切り分け手順：
  1. 何が起きたかを言葉にする
  2. 関係する値・設定・ファイルを確認する
  3. 原因候補を絞る
  4. 修正または対応後に確認する
- 再発防止ルール：混乱したら、まず「リクエストのメソッド・パス・ヘッダー・本文」と「サーバーのレスポンス」を分けて整理する。

- 次回も使えるパターン：

- 避けるべきこと：ヘッダー、JSON本文、Cookie、レスポンスを同じ「送信データ」としてまとめて考えない。
- 今日の重要キーワードと意味：
  - HTTPメソッド：リクエストで何をするかを示す。例：GETは取得、POSTは作成。
  - パス：どのAPIを呼ぶかを示す。例：`/api/data`。
  - HTTPヘッダー：リクエストに付ける情報。OriginやCookieなど。
  - リクエスト本文：フォーム入力など、サーバーへ送るデータ。
  - `express.json()`：JSON本文を解析するミドルウェア。
  - `cookieParser()`：Cookieヘッダーを解析し、`req.cookies`に入れるミドルウェア。
  - `next()`：Expressの次の処理へ制御を渡す。
  - `return`：現在の関数の処理を終了する。
  - `requireAuth`：JWTを確認し、認証済みユーザーの情報を後続へ渡す。
  - `res.json(data)`：JSON形式のレスポンスを返す。
  - `expiresIn: "1h"`：JWTを発行時点から1時間有効にする設定。
  - `jti`／失効リスト：JWTを個別に失効させる方法として検討したが、今回は保留。
- テンプレートに追加したいルール：該当なし
- レビューで指摘されそうな点：該当なし
- 今日、自分で説明できるようになったこと：
  - `req.get("Origin")`は値を読むだけで、許可判定は別の処理。
  - 不許可Originでは403となり、後続へ進まない。
  - `GET /api/data`のJWTはCookieヘッダーで送り、JSON本文とは別。
