## 3. 実装・技術の要点

- 重要なコードまたはコマンド：シェルコマンドは未使用。コードは読み取りのみ

```ts
app.post<{}, {}, CreatePatientBody>(
  "/api/patients",
  requireAuth,
  async (req, res) => {
    const userId = req.userId;
    if (!userId) {
      res.status(401).json({ error: "Unauthorized / 認証が必要です" });
      return;
    }

    const result = createPatientSchema.safeParse(req.body);

    if (!result.success) {
      res.status(400).json({
        error: "Invalid patient data / 無効な患者データ",
        details: result.error.flatten(),
      });
      return;
    }

    const newPatient = await prisma.patient.create({
      data: {
        ...result.data,
        userId,
      },
    });

    res.status(201).json(newPatient);
  },
);
```

- 責務・目的：Originの確認、JSON本文の解析、Cookie認証、Zod検証、Prismaへの保存を順に行う
- 入力：テストの `.send({...})` が送るJSON本文、`.set("Origin", "...")` が指定するOrigin、ログイン後の `agent` が保持して送るCookie
- 出力：認証失敗は401、スキーマ検証失敗は400、作成成功は201
- 副作用：成功時はPrisma経由で患者データを保存する。テストは実行していないため、DBへの書き込みは確認していない
- 型の絞り込み：`app.post<{}, {}, CreatePatientBody>` の3つ目の型は `req.body` のコンパイル時の型を指定する。実行時の本文検証はZodの `safeParse`
- null／undefinedの扱い：今日の主題ではない
- 型で守れていること：TypeScriptでルート内の `req.body` の型を扱いやすくする。HTTPで届く値が本当に型に合うかは保証しない
- 似た書き方との違い：`CreatePatientBody` はコンパイル時の型。`createPatientSchema.safeParse(req.body)` は実際のリクエスト本文を実行時に検証する
- 今日理解したこと：
  - テストは `app` をimportする。`app` は `express()` で作られたExpressアプリのインスタンス
  - テストは `auth.ts` を直接importしていないが、`index.ts` が `requireAuth` をimportしてルートに登録しているため、リクエスト時に認証ミドルウェアが実行される
  - `.send({...})` の本文は `express.json()` によって `req.body` として扱われる
  - `result.data` はZod検証を通過した本文。Prismaの `data` は保存内容を渡すための引数
  - `userId` は認証処理がJWTから取得して設定する。患者情報に所有者IDとして追加する
  - 不正なOriginは403を返して `return` するため、`next()` や後続ルートには進まない
  - 許可されたOriginでは `next()` により後続ミドルウェアへ進む
  - `{}` は記録スキーマの必須項目が不足し、400になる。Prismaの登録処理には進まない

### リクエスト処理の順序

1. Originがない、または許可リストにない場合は403を返して終了
2. 許可されていれば `next()` で後続処理へ進む
3. `express.json()` がJSON本文を `req.body` にする
4. `cookieParser()` がCookieを `req.cookies` にする
5. `requireAuth` がCookieのJWTを確認し、認証できれば `req.userId` を設定
6. Zodが `req.body` を検証する
7. 検証失敗は400。成功すれば `result.data` と `userId` をPrismaに渡す
8. 保存成功時は201を返す

| 値 | 由来 | 用途 |
| --- | --- | --- |
| Origin | `.set("Origin", "...")` | 送信元が許可されているか確認 |
| Cookie | ログイン後、`agent` が保持してリクエストに送信 | `requireAuth` がJWTを確認 |
| `req.body` | `.send({...})` のJSON本文 | Zodの検証対象 |
| `req.userId` | `requireAuth` がJWTから設定 | Prismaの患者データに所有者情報として追加 |

- つまずいた現象：本文が `express.json()` で `req.body` になった後、Zodの `result.data` を経てPrismaに渡る流れが分かりにくかった

- 最終的に理解したこと：`.send({...})` → `express.json()` → `req.body` → `safeParse()` → `result.data` → `Prismaのdata` に `userId` を追加 → 保存成功なら201
