## 3. 実装・技術の要点

- 重要なコードまたはコマンド：
  - `CreatePatientBody` とZodスキーマ：

    ````ts
    export const createPatientSchema = z.object({
      name: z.string().min(1, "氏名は必須です"),
      room: z.number().int().min(1).max(999),
      age: z.number().int().min(0).max(150).nullable().optional(),
      disease: z.string().optional(),
      history: z.string().optional(),
      progress: z.string().optional(),
    });

    export type CreatePatientBody = z.infer<typeof createPatientSchema>;
    ````

  - テスト用DBでサーバー統合テストを実行：

    ````bash
    npm run test:server
    ````

  - `package.json` のテストスクリプト：

    ````json
    "test": "node --env-file=.env.test ./node_modules/vitest/vitest.mjs run",
    "test:watch": "node --env-file=.env.test ./node_modules/vitest/vitest.mjs",
    "test:server": "node --env-file=.env.test ./node_modules/vitest/vitest.mjs run server/index.test.ts"
    ````

  - 接続先をURL全体ではなく、ホスト・ポート・DB名だけで確認：

    ````bash
    node --env-file=.env.test -e 'const u = new URL(process.env.DATABASE_URL); console.log({ host: u.hostname, port: u.port, database: u.pathname.slice(1) })'
    ````

  - `.env.test.local` がGitの無視対象か確認：

    ````bash
    git check-ignore -v .env.test.local
    ````

  - PrismaローカルDBの一覧を確認：

    ````bash
    npx prisma dev ls
    ````

- 責務・目的：
  - `createPatientSchema` は患者データの実行時検証を行う。
  - `CreatePatientBody` はZodスキーマからTypeScriptの型を推論する。
  - `npm run test:server` は `.env.test` を読み込んでAPI統合テストを実行する。
- 入力：
  - 患者作成APIには `name`、`room` などのリクエスト本文を送る。
  - テスト実行には `.env.test` の `DATABASE_URL` を使う。
- 出力：
  - 患者作成は成功時201、入力不正時400、部屋番号重複時409。
  - 他ユーザーの患者更新は404。
  - `npm run test:server` は22件すべて成功。
- 副作用：
  - API統合テストはテスト用DBへ登録・更新リクエストを送る。
  - `afterAll` でテストユーザーに関連する患者データを削除する。
- 型の絞り込み（該当する場合）：
  - `z.infer<typeof createPatientSchema>` によりスキーマから型を得る。`safeParse` の成功・失敗で入力検証結果を分岐する。
- null／undefinedの扱い（該当する場合）：
  - `age` は `nullable().optional()` により、省略と `null` の両方を許容する。
- 型で守れていること：
  - `CreatePatientBody` により、患者リクエスト本文のTypeScript上の形を表す。
  - 実際に届いた値の検証は `createPatientSchema.safeParse(req.body)` が行う。
- 似た書き方との違い：
  - `.set("Origin", ...)` はそのリクエストに付けるヘッダーで、次のリクエストへ引き継がれない。
  - Origin検査は `POST`、`PUT`、`PATCH`、`DELETE` に適用される。GETでは `next()` の後に `return` し、Origin検査を通らない。
  - `expect.objectContaining` はオブジェクトの指定項目を検証し、`expect.arrayContaining` は配列内に指定要素があることを検証する。追加のプロパティ、配列要素、順番は固定しない。
- 今日理解したこと：
  - Supertestの `agent` はログイン後のCookieを保持する。`agent` と `otherAgent` は異なるユーザーのセッションとして使う。
  - `req.userId` は更新を試みる `agent` のJWTから設定される。更新対象患者の所有者IDと一致しない場合、更新条件に合わず404になる。
  - 404の確認に加え、所有者の `otherAgent` からGETして患者名が元のままであることも確認できる。
  - PrismaローカルDBが停止していると `ECONNREFUSED`、接続できてもテーブルがなければ `P2021` が起きる。
  - `template1` はPrismaローカルDBで使われるDB名として確認した。DB一覧のSQLでは `datistemplate = false` でテンプレートDBを除外していた。
- 改善余地：
  - `.env.test` を使う npmスクリプトから実行し、テスト接続先を毎回明示する。
  - `npm test` と `npm run test:watch` のどちらも `.env.test` を読み込む設定にした。

## 5. 質問・つまずきと再発防止

- 質問したこと：
  - 型とZodスキーマの対応は何か。
  - Supertestの `agent` はCookieをどう保持するか。
  - POSTにOriginを付け、GETには付けない理由は何か。
  - 他ユーザーの患者を更新するテストで、DBの値も確認できるか。
  - `.env` と `.env.test` のどちらをテストが使うのか。
- つまずいた現象：
  - Prisma停止中は `ECONNREFUSED`。
  - Prisma起動後も `User`、`Patient` テーブルがないDBに接続して `P2021`。
  - DB状態確認アサーションで、期待する患者名の表記が作成時と一致せず1件失敗。
- 直接原因：
  - 接続先DBにアプリのテーブルがなかった。
  - 名前の期待値が `"他のユーザーの患者"`、作成時が `"他ユーザーの患者"` と異なっていた。
- 根本原因（知識／確認／考え方など）：
  - `.env.test` があるだけでは実行時に必ず読み込まれるわけではないことを把握できていなかった。
  - DBの接続状態、接続先、マイグレーション状態を分けて確認する必要があった。
- 最終的に理解したこと：
  - テストはDBを使う統合テストであり、開発用DBとテスト用DBを分ける。
  - Prisma停止の接続失敗と、テーブル未作成のDBエラーは別の原因。
  - `.env.test` を読み込んでからVitestを起動する npmスクリプトを使う。
- 次回の切り分け手順：
  1. 何が起きたかを言葉にする
  2. 関係する値・設定・ファイルを確認する
  3. 原因候補を絞る
  4. 修正または対応後に確認する
- 再発防止ルール：
  - サーバー統合テストは `npm run test:server` で実行する。
  - 通常の `npx vitest` では `.env.test` が選択されると決めつけない。
  - 接続URLやAPIキーを共有しない。

## 7. ナレッジ化

- 次回も使えるパターン：
  - 重複エラーのAPIテストでは、1件目が成功した後に同じ一意キーで2件目を作成する。

  - `.env.test` を指定するnpmスクリプトからサーバー統合テストを起動する。
- 避けるべきこと：
  - 開発用DBとテスト用DBの接続先を確認せずにサーバー統合テストを実行する。
  - URLや秘密情報をそのまま共有する。

- 今日の重要キーワードと意味：
  - `z.infer`：ZodスキーマからTypeScript型を推論する。
  - `safeParse`：入力を実行時に検証し、成功・失敗の結果を返す。
  - `request.agent(app)`：Cookieなどを保持し、複数リクエストに使えるSupertestエージェント。
  - `P2002`：Prismaの一意制約違反。患者作成ルートでは409に変換される。
  - `P2021`：接続先DBに対象テーブルがないエラー。
  - `arrayContaining`：配列に指定要素が含まれることを確認する。
