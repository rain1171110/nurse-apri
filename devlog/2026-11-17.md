#### 解説（原文のまま）

**クッキーとトークンの流れ**

```typescript
【ログイン時】
サーバー：const token = jwt.sign({ userId: user.id }, JWT_SECRET, { expiresIn: "1h" });
サーバー：res.cookie("token", token, { httpOnly: true });
         ↓
ブラウザ：「あ、このトークンを保存しろって言ってる」
        ↓
ブラウザのクッキー保存場所
  ┌─────────────────────┐
  │ token: eyJhbGc...   │
  └─────────────────────┘

【次のリクエスト時】
ブラウザ：fetch(url, { credentials: "include" })
        ↓
        「あ、credentials: "include" が付いてる」
        ↓
        「クッキーを探さなきゃ」
        ↓
        GET /api/data + Cookie: token=eyJhbGc...
        ↓
サーバー：受け取り
        ↓
cookieParser()が解析
        ↓
req.cookies = { token: "eyJhbGc..." }
        ↓
requireAuth で const token = req.cookies.token;
```

**cookieParser() の役割**

```typescript
app.use(express.json());
app.use(cookieParser());  // ← これが req.cookies を作成

// cookieParser() がある場合
const token = req.cookies.token;  // ← 動作する

// cookieParser() がない場合
const token = req.cookies.token;  // ← エラー（req.cookies が undefined）
```

**jwt.verify() の3段階の検証**

```typescript
const decoded = jwt.verify(token, JWT_SECRET);

【検証1：署名の検証】
- JWT_SECRET キーで署名部を検証
- 本当にサーバーが発行したトークンか確認
- 偽造されていないか確認

【検証2：期限切れ確認】
- jwt.sign() で expiresIn: "1h" と設定
- 現在時刻が期限を超えていないか確認
- 期限切れ → catch ブロック → 401エラー

【検証3：戻り値の確認】
if (typeof decoded === "string" || typeof decoded.userId !== "string") {
  res.status(401).json({ error: "..." });
}
```

**TypeScript の型安全性**

jwt.verify() の戻り値の型：
```typescript
jwt.verify(token, secret): JwtPayload | string
// つまり、戻り値は「オブジェクトか文字列」の両方の可能性
```

通常は必ずオブジェクトだが、TypeScript コンパイラは「確認してね」と言っている。

### 自分の理解

#### このコードの役割
- ユーザーがログインしたときに、安全にトークンを発行・保存する
- 次のリクエストで、ブラウザが自動的にトークンを送信する
- サーバーがトークンを受け取り、本物か、期限切れじゃないか確認する
- ユーザーを識別して、そのユーザーのデータだけを返す

#### 入力と出力
- 入力：メール、パスワード
- 出力1：トークン（ブラウザに保存）
- 出力2：req.userId（そのユーザーのID）

#### 重要な処理の流れ

**Step 1：ログイン時のトークン作成**
```
メール・パスワード
  ↓
パスワード確認
  ↓
jwt.sign({ userId: user.id }, JWT_SECRET, { expiresIn: "1h" })
  ↓
トークン生成
  ↓
res.cookie() でブラウザに「保存して」と指示
  ↓
ブラウザが自分のクッキー保存場所に入れる
```

**Step 2：次のリクエスト時**
```
credentials: "include"
  ↓
ブラウザがクッキーを探す
  ↓
Cookie ヘッダーに追加
  ↓
サーバーに送信
  ↓
cookieParser() がヘッダーを解析
  ↓
req.cookies を作成
  ↓
req.cookies.token でアクセス可能
```

**Step 3：jwt.verify() による検証**
```
const token = req.cookies.token;
  ↓
jwt.verify(token, JWT_SECRET)
  ↓
【署名検証】本物か確認
【期限チェック】期限切れじゃないか確認
  ↓
decoded = { userId: "5678", iat: ..., exp: ... }
  ↓
【戻り値チェック】文字列じゃないか、userId が入ってるか確認
  ↓
const userId = decoded.userId;
  ↓
req.userId = userId;
  ↓
次のハンドラーで使える
```

#### 理解したこと

**今日、確実に理解できたこと：**

1. **cookieParser() の存在理由**
   - HTTPリクエストの `Cookie:` ヘッダーを解析
   - JavaScript オブジェクト `req.cookies` に変換
   - `req.cookies.token` でアクセスできるようにする
   - **なくなったら、req.cookies が undefined になってエラー**

2. **jwt.verify() の3段階の検証**
   - 署名検証：本物のトークンか、偽造されていないか
   - 期限チェック：有効期限内か（expiresIn: "1h" で設定）
   - 戻り値チェック：TypeScript の型安全性のため

3. **文字列チェックの意味**
   ```typescript
   if (typeof decoded === "string" || typeof decoded.userId !== "string")
   ```
   - nurse-apri では実際には起こらない
   - **防御的プログラミング**：念の為、エラーハンドリングを入れている
   - TypeScript の型は `JwtPayload | string` なので、両方チェック必要

4. **トークンはブラウザと往復しない**
   - ブラウザに1度保存される
   - 毎回のリクエストで、ブラウザが自動で「コピー」を送信
   - サーバーはコピーを受け取る

5. **複数の安全装置の組み合わせ**
   - JWT_SECRET で署名検証
   - expiresIn で期限設定
   - httpOnly でJavaScript からアクセス不可
   - sameSite で CSRF 対策
   - 型チェックで不正な値を検知
