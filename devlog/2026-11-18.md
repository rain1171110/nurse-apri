#### クッキーは「2往復」で動いている

```typescript
【混乱していたポイント】
「クッキーは POST で送られたら、Response で見えるのでは？」

【実際】
POST（1往復目）: Response に Set-Cookie が含まれる
  ↓
  ブラウザが受け取ってクッキーを保存
  ↓
GET（2往復目）: Request に Cookie が含まれる ← あなたが見たのはこれ

【図解】
POST /api/auth/login
↓ Request body
 → 【Server】Set-Cookie を Response に含める
   ↑ Response headers
     ← クッキー保存

【次のリクエスト】
GET /api/data
↓ Request headers（保存されたクッキーを自動付加）
 → 【Server】受け取ったクッキーを検証
   ↑ Response
     ← データ返す
```

#### 他のユーザーの患者情報を守る処理（コード読解）

```typescript
// server/index.ts の GET /api/data エンドポイント

app.get("/api/data", requireAuth, async (req, res) => {
  const userId = req.userId;  // ← ステップ1：トークンから userId 取得
  
  if (!userId) {
    res.status(401).json({
      error: "Unauthorized / 認証が必要です",
    });
    return;
  }
  
  try {
    // ステップ2：患者を取得するときに、userId で絞込
    const patients = await prisma.patient.findMany({
      where: {
        userId,  // ★ ここ！ userId が一致する患者だけ取得
      },
    });

    // ステップ3：看護記録も、userId で絞込
    const records = await prisma.nursingRecord.findMany({
      where: {
        patient: {
          userId,  // ★ ここ！ 患者の userId が一致する記録だけ取得
        },
      },
      include: {
        vitals: true,
      },
    });

    const data = {
      patients,
      records,
    };

    res.json(data);
  } catch (error) {
    // エラーハンドリング
  }
});
```

**セキュリティの3層防御**

| 層 | 仕組み | 効果 |
|-----|--------|------|
| **UI層** | 患者一覧に自分のだけ表示 | ユーザーが意図的に他人の患者を操作できない |
| **API層** | Prisma の where で userId チェック | UI を迂回されてもデータベースで防ぐ |
| **DB層** | 複合キー（id + userId）で検索 | 一致しないデータは取得不可 |

### 自分の理解

#### このコードの役割
- ブラウザに保存されたクッキーを自動的に送信する
- サーバー側で JWT を検証してユーザーを特定する
- そのユーザーのデータだけを取得・返す
- 他のユーザーのデータにアクセスできないようにする

#### 重要な処理の流れ

**流れ全体（3往復）**

```
【往復1：ユーザー登録またはログイン】
ブラウザ → メール・パスワード → サーバー
           ← Set-Cookie（クッキー設定指示） ← ブラウザが保存

【往復2：ページリロード時に自動実行】
ブラウザ → GET /api/data + Cookie ヘッダー → サーバー
           ← 患者データ（JSON）← 自分のデータだけ

【往復3以降：他のリクエスト】
ブラウザ → PUT/DELETE /api/patients/:id + Cookie ヘッダー → サーバー
           ← 成功/エラーレスポンス
```

## 6. つまずきと学び

#### つまずいたこと
1. **Response Headers に Set-Cookie が見えなかった**
   - 最初、POST /api/auth/login の Response Headers に Set-Cookie が見えず、混乱
   - OPTIONS プリフライトと POST リクエストを区別していなかった

2. **「Request Headers に Cookie が見えるのはなぜ？」という疑問**
   - POST で送られたら Response に見えるはずだと思っていた
   - 実は「2往復」が必要なことを理解していなかった

#### 原因
- クッキーの送信タイミングを「1往復」だと思っていた
- SET-COOKIE（サーバー → ブラウザ）と COOKIE（ブラウザ → サーバー）の違いを理解していなかった

#### どう解決したか
1. Network タブで POST と GET を別々に確認
2. 2つが異なるリクエストだと認識
3. 流れ図を書いて、タイミングの違いを理解

#### 次回試すこと
- 他のユーザーの患者データにアクセスしようとしたときの 404 エラーを、実装で確認
- PUT /api/patients/:id と DELETE /api/patients/:id で、id + userId の複合条件をチェックしている仕組みを詳しく読む

#### 再発防止のための確認項目
- HTTP リクエスト/レスポンス は「往復」の概念が重要
- 1つのリクエストでクッキーが「作成」「送信」両方されるわけではない
- 「Set-Cookie」（作成指示）と「Cookie」（送信）は別のヘッダー

#### 次回も使える考え方
- **開発者ツールは最強のデバッグ手段**：コードと実装が合致しているか確認できる
- **Network タブを見ながらコードを読む**：見えない処理も実装で確認できる
- **Request と Response を区別する**：どちらのヘッダーに何が入っているか意識する
