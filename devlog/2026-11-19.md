## 4. コードと理解したこと

### 解説メモ（会話からそのまま転記）

#### 認証とセキュリティの図書館の例え

```
【図書館の例え：複合条件による防止】

ユーザーA が「ユーザーB の貸出履歴を見たい」と言った場合

ユーザーA：「あ、でもユーザーB の貸出履歴も見たい」
  ↓
「ユーザーB の履歴をください」と直接言う
  ↓
図書館スタッフ：「あなたは ユーザーA ですね。ユーザーB の履歴は見せられません」
  ↓
「そのデータはありません」とエラー返す ✗

【実装での防止】
DELETE /api/patients/:id で、Prisma が以下をチェック：

where: {
  id: "ユーザーB の患者ID",           ← 条件1：そのIDが存在するか？
  userId: "ユーザーA のID"            ← 条件2：かつ、ユーザーA のものか？
}

両方が一致しないと Prisma は P2025 エラー（レコードが見つからない）を返す
  ↓
API は 404 エラーに変換して返す
  ↓
ユーザーA には「そのデータはありません」と見える
```

### 自分の理解

#### このコードの役割

- GET /api/data：userId で患者一覧を絞込（自分のデータのみ表示）
- PUT /api/patients/:id：id と userId の両方をチェック（自分のかつそのIDのデータのみ更新可能）
- DELETE /api/patients/:id：id と userId の両方をチェック（自分のかつそのIDのデータのみ削除可能）

#### 重要な処理の流れ

**セキュリティの3段階確認**

```typescript
【段階1：UI層】
患者一覧には、ユーザーA の患者だけが表示される
  ↓ ユーザーが意図的に他人の患者を操作できない状態

【段階2：API層（Prisma where 条件）】
DELETE /api/patients/:id で以下をチェック：

await prisma.patient.delete({
  where: {
    id: "受け取った id",
    userId: "req.userId"  ← トークンから取得した自分のID
  }
});

条件が一致しないと P2025 エラーが発生
  ↓ サーバー側でデータベースレベルで防止

【段階3：データベース層】
複合キー（id + userId）で検索
一致しないと「そのレコードは存在しない」と返す
  ↓ データベースが最後の砦
```

## 6. つまずきと学び

#### つまずいたこと

1. **curl でのセキュリティテストが複雑**
   - CORS エラーの対応（Origin ヘッダー追加）
   - クッキーの保存と送信管理
   - 複数ユーザーのトークン・クッキー管理
   - コマンドの手入力ミスで何度も失敗

2. **ユーザーが「何をテストしているのか」「何が期待される結果か」を理解できていない状態**
   - curl コマンドのエラーメッセージだけが表示される
   - 実装の流れが見えない
   - 目的と手段が混乱している

#### 原因

- curl でのテストは、ネットワークエラーやヘッダー設定エラーが多い
- エラーメッセージから原因を特定しにくい
- 初心者にとって「データが流れているのか、見えない」

#### どう解決したか

1. curl テストから「ブラウザ + 開発者ツール」に切り替え
2. 「何をテストするのか」を「身近な例え（図書館）」で説明
3. テストのステップをシンプルに整理
4. 次のステップを明確化

#### 次回試すこと

- ユーザーB でログイン
- ユーザーA が作成した患者にアクセス試行
- 複合条件による 404 エラー確認

#### 再発防止のための確認項目

- テスト方法を「実装が見える」方法に変更する判断が重要
- 初心者にとって「見える化」が最優先
- 複雑なコマンド設定より、開発者ツールでの確認が効果的

#### 次回も使える考え方

- **「見える化」は学習効率を大きく左右する**
  - curl はプロ向き。初心者は開発者ツールで十分
- **テストステップは、「目的」「手段」「期待結果」を明確に**
  - 「何をテストするのか」が分からないと、エラーが起きたときに原因特定できない
- **エラーが多い場合は、テスト方法そのものを見直す**
  - 同じ方法で何度も失敗するなら、別の方法を検討すべき
