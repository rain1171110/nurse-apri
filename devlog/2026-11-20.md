## 2. 自分が書いたコードの修正

**修正内容：** ブルートフォース攻撃防止でレート制限を実装

### 修正箇所：server/index.ts

**修正前：**

```typescript
// レート制限なし
```

**修正後：**

```typescript
import rateLimit from "express-rate-limit";

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15分間
  max: 5, // 最大5回
  message: "Too many login attempts",
});

app.post<{}, {}, LoginBody>(
  "/api/auth/login",
  loginLimiter, // ← ミドルウェアを追加
  async (req, res) => {
    // ...
  },
);
```

**起きていた症状：**

- ブルートフォース攻撃で、何度でもパスワード候補を試行できた
- 20万回の試行も受け入れられた

**原因：**

- レート制限の実装がなかった
- サーバーが全てのリクエストを受け入れていた

**どう修正したか：**

- express-rate-limit ライブラリをインストール
- loginLimiter ミドルウェアを設定（15分に最大5回）
- POST /api/auth/login に適用

**修正後の変化：**

- 1～5回目のログイン試行：Status 401（パスワード間違い）
- 6回目以降のログイン試行：Status 429（レート制限に達した）

**なぜ直ったのか：**

- express-rate-limit がメールアドレス単位でリクエスト回数をカウント
- 5回を超えると、自動的に 429 エラーを返す
- 15分経過後にカウンターがリセット

**次に同じ問題が起きたときの確認手順：**

1. npm install express-rate-limit が実行されているか確認
2. server/index.ts に loginLimiter が設定されているか確認
3. POST /api/auth/login に loginLimiter ミドルウェアが追加されているか確認
4. ブラウザコンソールで JavaScript fetch を使ってテスト
5. 6回目で Status 429 が返ってくるか確認

## 4. コードと理解したこと

### 解説メモ（会話からそのまま転記）

#### セキュリティの3層防御

```
【第1層：UI層】
患者一覧には、ログインユーザーの患者だけ表示

【第2層：API層（複合条件）】
where: { id, userId } 両方チェック
→ 他のユーザーのデータは 404

【第3層：認証層（トークン検証）】
クッキーなし → トークンなし → エラー 401
→ 外部からのアクセス防止
```

#### ブルートフォース攻撃と防止

```
【攻撃】
パスワード候補を 1000個用意して、全部試す
  ↓
1秒に 100回送信 → 10秒で全部試行完了

【防止】
レート制限：1メールアドレスから「15分に5回まで」
  ↓
6回目は Status 429 エラー
  ↓
攻撃者は同じアドレスで何度も試行できない
```

#### 5つのセキュリティポイント理解

**A. トークンが別物**

```typescript
// ユーザーA のトークン
eyJhbGc...xyz . eyJ1c2VySWQiOiJkMjE4... . signature123

// ユーザーB のトークン
eyJhbGc...abc . eyJ1c2VySWQiOiI2NDg2... . signature456
                            ↑ ユーザーID が異なる
```

**ポイント：** トークンの中に userId が埋め込まれているから、全ユーザーのトークンが違う。

**B. req.userId の流れ**

```
【ログイン時】
const token = jwt.sign({ userId: user.id }, JWT_SECRET)
  ↓
トークン内に userId が埋め込まれる

【DELETE リクエスト時】
const decoded = jwt.verify(token, JWT_SECRET)
  ↓
const userId = decoded.userId
  ↓
req.userId = userId
  ↓
where: { id, userId } に使用
```

**ポイント：** トークン → userId 抽出 → Prisma where 条件 の流れ。

**C. 複合条件による防止**

```
【id だけだった場合】
await prisma.patient.delete({
  where: { id: "p456" }  // ← userB の患者も削除可能！
});

【id + userId の場合】
await prisma.patient.delete({
  where: {
    id: "p456",         // ← userB の患者
    userId: "userA",    // ← userA がログイン中
  }
});
// ← そんな患者は存在しない → 404 エラー
```

**ポイント：** 複合条件で「アクセス権限チェック」をデータベースレベルで実行。

**D. Status 401 vs 404**

```
【401：Unauthorized】
トークンなし → requireAuth ミドルウェアで止まる
  ↓
エンドポイント実行されない
  ↓
「認証が必要」

【404：Not Found】
トークンあり → requireAuth 通過
  ↓
エンドポイント実行
  ↓
Prisma: id + userId の条件に一致するデータなし
  ↓
「患者が見つかりません」
```

**ポイント：** 401 は認証前、404 は認証後のエラー。

**E. レート制限（実装済み）**

```
loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,  // 15分間
  max: 5,                     // 最大5回
});

POST /api/auth/login に適用
  ↓
1～5回：通常処理
6回目：Status 429（レート制限）
```

**ポイント：** メールアドレス単位でカウント。5回超過で自動的に 429 エラー。

#### bcrypt.hash() と bcrypt.compare() の仕組み

```
【登録時】
password = "testpassword123"
  ↓
passwordHash = await bcrypt.hash(password, 10)
  ↓
"$2a$10$abc...xyz" に変換
  ↓
データベースに保存

【ログイン時】
password = "testpassword123"（入力）
  ↓
await bcrypt.compare(password, user.passwordHash)
  ↓
bcrypt 内部で：
  1. password を同じ方法でハッシュ化
  2. "$2a$10$abc...xyz" に変換
  3. user.passwordHash と比較
  4. 一致したら true
```

**ポイント：** bcrypt.compare() は「内部で自動的に」ハッシュ化して比較。ユーザー側は比較ロジックを意識しない。

#### ブルートフォース攻撃テスト（PowerShell）

```powershell
for ($i = 1; $i -le 7; $i++) {
  try {
    $response = Invoke-WebRequest -Uri "http://localhost:3001/api/auth/login" `
      -Method POST `
      -Headers @{
        "Origin" = "http://localhost:5173"
        "Content-Type" = "application/json"
      } `
      -Body (@{
        email = "testuser1@example.com"
        password = "wrongpassword$i"
      } | ConvertTo-Json) `
      -SkipHttpErrorCheck
    Write-Host "試行 $i 回目: $($response.StatusCode)" -ForegroundColor Green
    if ($response.StatusCode -eq 429) {
      Write-Host "⚠️ レート制限に達しました！" -ForegroundColor Red
      break
    }
  } catch {
    Write-Host "試行 $i 回目: 例外エラー - $($_)" -ForegroundColor Yellow
  }
}
```

**このコマンドの流れ：**

```
【第1段階：ループ開始】
$i = 1 から 7 まで、同じメールアドレスで複数回ログイン試行

【第2段階：各試行内容】
- email：固定（testuser1@example.com）
- password：変更（wrongpassword1, wrongpassword2, ... wrongpassword7）
  → パスワード候補を 7 個試す
  → これが「ブルートフォース攻撃」

【第3段階：結果確認】
- 試行 1～5 回目：StatusCode 401（パスワード間違い）
  → Write-Host で "試行 1 回目: 401" と表示

- 試行 6 回目：StatusCode 429（レート制限エラー）
  → Write-Host で "⚠️ レート制限に達しました！" と表示
  → break で ループ終了

【第4段階：例外処理】
- Invoke-WebRequest が失敗した場合は
- catch ブロックで "例外エラー" と表示
```

**なぜこのコマンドを実行したのか：**

```
【目的】
loginLimiter が「15分に5回まで」という制限を守っているか確認

【検証方法】
同じメールアドレスで 7 回パスワード候補を送信
  ↓
5 回までは 401 エラー（パスワード間違い）
6 回目は 429 エラー（レート制限）
  ↓
「防止が機能している」と確認

【結果】
期待どおり 6 回目で 429 エラー
  → ブルートフォース攻撃防止が実装できた ✓
```

**ブラウザ（JavaScript fetch）との違い：**

【ブラウザコンソール版】
fetch("http://localhost:3001/api/auth/login", {
  method: "POST",

### 自分の理解

#### このコードの役割

- トークンに userId を埋め込み、ユーザーを識別
- トークン → userId 抽出 → Prisma where 条件に使用
- 複合条件（id + userId）で他のユーザーのデータ操作を防止
- bcrypt で パスワードを「一方向暗号化」（ハッシュ化）して保存
- レート制限でブルートフォース攻撃を防止

#### 入力と出力

```
【入力】
- ユーザーがログイン（メール＋パスワード）
- ユーザーが DELETE リクエスト送信

【出力】
- トークン生成 → ブラウザクッキーに保存
- DELETE 実行 → 複合条件で防止 → 404 または成功
```

#### 重要な処理の流れ

```
【ログイン】
メール＋パスワード
  ↓ bcrypt.compare() で検証
  ↓ jwt.sign() でトークン生成
  ↓ res.cookie() で ブラウザに保存

【DELETE】
リクエスト + クッキー
  ↓ requireAuth で トークン検証
  ↓ jwt.verify() で userId 抽出
  ↓ Prisma where: { id, userId } で削除
  ↓ 一致しないと 404 エラー
```

## 6. つまずきと学び

#### つまずいたこと

1. **複数のセキュリティレイヤーを「同時に」理解しようとした**
   - 認証層、API層、暗号化層が混在
   - どこで何が起きているのか、混乱

2. **「トークンの中身」が不可視だった**
   - トークンが何なのか、理解できていなかった
   - JSON.parse(atob(payload)) で デコードすると、userId が見える

3. **「req.userId がどこから来て、どこで使われるのか」の流れが不清晰だった**
   - トークン → jwt.verify() → userId 抽出 → where 条件に使用
   - の流れが一本の線で繋がっていなかった

#### 原因

- セキュリティの複数のポイントを「同時に」学ぶ → 混乱
- 「理解ステップ」が不十分だった
- コード参照なしで、概念だけで説明しようとした

#### どう解決したか

1. **1つずつ、ステップごとに理解**
   - A：トークンが別物 → デコードして確認
   - B：req.userId の流れ → コードで確認
   - C：複合条件による防止 → コード＋テストで確認
   - D：401 vs 404 → テスト結果で確認
   - E：レート制限 → 実装＋テストで確認

2. **「見える化」を重視**
   - トークンをデコードして、中身を表示
   - 複数ユーザーのテストで、実装が動いているのを確認
   - レート制限のテストで、Status 429 を確認

3. **コード参照を活用**
   - 説明の後、すぐにコードを見る
   - 「このコード行で、ここが起きている」と指し示す

#### 次回試すこと

- F：他のセキュリティ防止方法（アカウントロック、ログイン試行ログ）
- G：本番環境でのセキュリティ設定（secure フラグ、sameSite オプション）

#### 再発防止のための確認項目

- セキュリティは「複数レイヤーの組み合わせ」。1つずつ理解してから、全体を繋ぐ
- 「不可視の処理」（トークン、ハッシュ）は「見える化」してから理解する
- テストで「実装が動いているのか」を確認しながら学ぶ

#### 次回も使える考え方

- **「理解ステップ」が学習効率を左右する**
  - 複雑なシステムは、小さなパーツから始める
  - パーツを理解してから、全体を繋ぐ

- **「見える化」は最強の学習ツール**
  - コンソールにログを出す
  - テストで実装を確認する
  - コードで動きを追跡する

- **テスト駆動で理解を深める**
  - 仮説を立てる（6回目で 429 エラーが返ってくるはず）
  - テストで確認する（実際に 429 エラーが返ってくる）
  - 理解が深まる（なぜそうなるのか、納得できる）
