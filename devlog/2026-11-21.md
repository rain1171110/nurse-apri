## 2. 今日の学習内容（実コード参照）

### 【全体像：セキュリティの3層防御】

```
【第1層：UI層】
患者一覧には、ログインユーザーの患者だけ表示

【第2層：API層（複合条件）】
where: { id, userId } 両方チェック
→ 他のユーザーのデータは 404

【第3層：認証層（トークン検証）】
クッキーなし → トークンなし → エラー 401
→ 外部からのアクセス防止
```

### 【A. トークンが別物】

```
【ユーザーA のトークン】
トークン内に userId: "userA" が埋め込まれている
  ↓
トークン例：eyJhbGc...xyz . eyJ1c2VySWQiOiJ1c2VyQSI... . signature123

【ユーザーB のトークン】
トークン内に userId: "userB" が埋め込まれている
  ↓
トークン例：eyJhbGc...abc . eyJ1c2VySWQiOiJ1c2VyQiI... . signature456
                                      ↑ ユーザーID が異なる
```

**ポイント：** 全ユーザーのトークンが違う理由は、各トークンに「誰のトークンか」が入っているから。

### 【B. req.userId の流れ（実コード確認）】

**ステップ1：ログイン時に jwt.sign() でトークンを生成**

```typescript
// server/index.ts (line 536)
const token = jwt.sign({ userId: user.id }, JWT_SECRET, {
  expiresIn: "1h",
});
```

**流れ：**

```
{ userId: user.id }
  ↓
JWT_SECRET（秘密の鍵）を使って署名を追加
  ↓
トークン完成：eyJhbGc...xyz . eyJ1c2VySWQiOi... . signature123abc
  ↓
ブラウザクッキーに保存
```

**ステップ2：DELETE リクエストが来たとき、requireAuth ミドルウェアが実行**

```typescript
// server/auth.ts
export const requireAuth = (
  req: Request,
  res: Response,
  next: NextFunction,
) => {
  try {
    // 1. クッキーからトークンを取り出す
    const token = req.cookies.token;

    if (!token) {
      res.status(401).json({
        error: "Authentication required / 認証が必要です",
      });
      return;
    }

    // 2. トークンを検証してデコード
    const decoded = jwt.verify(token, JWT_SECRET);

    if (typeof decoded === "string" || typeof decoded.userId !== "string") {
      res.status(401).json({
        error: "Invalid token payload / トークン内容が無効です",
      });
      return;
    }

    // 3. decoded から userId を抽出
    const userId = decoded.userId;

    // 4. req というオブジェクトに追加
    req.userId = userId;

    // 5. next() で次のルートに進む
    next();
  } catch (error) {
    res.status(401).json({
      error: "Invalid or expired token / トークンが無効または期限切れです",
    });
    return;
  }
};
```

**流れの図解：**

```
【ステップごとの req の変化】

【初期状態（requireAuth 前）】
req = {
  method: "DELETE",
  path: "/patient/p456",
  cookies: { token: "eyJ..." },
  params: { id: "p456" },
  userId: ???  ← まだない
}

【requireAuth 内部】
const token = req.cookies.token;
  → token = "eyJ... . eyJ1c2VySWQiOi... . signature123abc"

const decoded = jwt.verify(token, JWT_SECRET);
  → 「このトークンは JWT_SECRET で署名された本物だ」と確認
  → decoded = { userId: "userA", iat: 1234567890, exp: 1234571490 }

const userId = decoded.userId;
  → userId = "userA"

req.userId = userId;
  → req に userId を追加

【最終状態（requireAuth 後）】
req = {
  method: "DELETE",
  path: "/patient/p456",
  cookies: { token: "eyJ..." },
  params: { id: "p456" },
  userId: "userA"  ← 新しく追加！
}

next()
  → DELETE ルートに進む（req にはまだ userId が入っている）
```

**ステップ3：DELETE ルートで使用**

```typescript
// server/index.ts (削除処理の例)
app.delete("/patient/:id", requireAuth, async (req, res) => {
  // requireAuth で req.userId が追加されている

  const userId = req.userId;  ← ここで取り出す
                 ↑ requireAuth で追加された値

  await prisma.patient.delete({
    where: {
      id: req.params.id,     ← 患者ID（p456）
      userId: userId         ← DELETE リクエストしたユーザーの ID（userA）
    }
  })
})
```

**最終的な保護メカニズム：**

```
【ユーザーA が DELETE リクエスト】
DELETE /patient/p123 + クッキー（トークンA）
  ↓
requireAuth で req.userId = "userA" に設定
  ↓
where: { id: "p123", userId: "userA" }
  ↓
「p123 で、userA の患者」を削除
  ↓
成功（userA の患者だから）

【ユーザーB が、ユーザーA の患者を削除しようとする】
DELETE /patient/p123 + クッキー（トークンB）
  ↓
requireAuth で req.userId = "userB" に設定
  ↓
where: { id: "p123", userId: "userB" }  ← userA じゃなく userB
  ↓
「p123 で、userB の患者」を検索
  ↓
そんな患者は存在しない
  ↓
404 エラー ← DELETE 失敗！
```

### 【JWT_SECRET の役割】

```typescript
// server/index.ts (line 22-25)
const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET) {
  throw new Error("JWT_SECRET is not defined");
}
```

**JWT_SECRET は .env ファイルから読み込まれる秘密の鍵**

```
【登録時（jwt.sign()）】
JWT_SECRET = "super_secret_key_12345"
  ↓
{ userId: "userA" } + JWT_SECRET
  ↓
署名を作る
  ↓
トークン完成

【検証時（jwt.verify()）】
トークン が返ってきた
  ↓
JWT_SECRET = "super_secret_key_12345" で検証
  ↓
「このトークンは本物だ」と確認
  ↓
userId を抽出

【もし JWT_SECRET が漏れたら】
❌ 誰でもトークンを作れる
❌ 誰でも他のユーザーに成りすまされる
```

**ポイント：** JWT_SECRET が漏れたら、セキュリティが完全に崩壊する。これがセキュリティの根っこ 🔐

## 3. 重要な理解ポイント

### 「req.userId = userId」の正確な意味

```
【よくある誤解】
「サーバーに送っている」

【正確には】
「req というオブジェクトに追加している」
```

**req の役割イメージ：**

```
req = リクエストの「情報を詰める箱」

【ミドルウェア内】
req に userId を詰める（requireAuth が詰める）

【次のルート内】
req から userId を取り出す（DELETE ルートが取り出す）

【例え】
宅配便の箱を思い浮かべると：
  - requireAuth：「userId という荷物を箱に詰める」
  - DELETE ルート：「箱から荷物を取り出して使う」
  - req：「荷物を運ぶ箱」
```

**つまり、req は「リクエストの全情報を運ぶ箱」。ミドルウェアが情報を追加して、後のルートが受け取って使う** ✅

### ミドルウェアの流れ

```
【ユーザーのリクエスト】
DELETE /patient/p456 + クッキー
  ↓
【requireAuth ミドルウェアが実行】
1. クッキーから token を取出
2. jwt.verify() で検証・デコード
3. userId を抽出
4. req.userId に追加
5. next() で次に進む
  ↓
【DELETE ルートが実行】
1. req.userId を取出（requireAuth で追加された値）
2. where: { id, userId } で削除
3. 一致したら削除、なければ 404 エラー
```

## 4. 新しく学んだ概念

### jwt.sign() と jwt.verify() の違い

```
【jwt.sign()】
「トークンを作る」（生成）

【jwt.verify()】
「トークンが本物か確認する」（検証）

【どこで使われるか】
jwt.sign()   → ログイン時にトークン生成
jwt.verify() → DELETE リクエスト時にトークン検証
```

### ミドルウェアとルートの関係

```
【ミドルウェア】
= 全ルートの前に実行される共通処理

requireAuth ミドルウェアの役割：
  - クッキーからトークンを取り出す
  - トークンを検証する
  - userId を抽出する
  - req に追加する
  - 認証がないとエラーで止める

【ルート】
= ミドルウェアを通過した後の具体的な処理

DELETE ルートの役割：
  - req.userId を使用する
  - 複合条件（id + userId）で削除
  - 一致しなければ 404 エラー
```
