### 【Step 1-2】スプレッド演算子（`...`）の役割

### 【Step 1-3】`formatDate()` と時間抽出の詳細

**formatDate 関数（Utils.ts）：**

```typescript
export const formatDate = (
  date: string | number | Date | Dayjs | null | undefined,
): string => {
  return date ? dayjs(date).format("YYYY-MM-DD") : "";
};
```

**役割：**
- 入口：いろいろな形の日付を受け取る
- 処理：dayjs で扱いやすく変換して、`YYYY-MM-DD` 形式に整形
- 出口：必ず文字列を返す

**例：**
```javascript
new Date()
  → Thu Nov 26 2026 05:46:02 GMT+0900
  
formatDate(new Date())
  → "2026-11-26"
```

**時間抽出（`.slice(0, 5)` の説明）：**

```typescript
new Date().toTimeString().slice(0, 5)

new Date().toTimeString()
  → "05:46:02 GMT+0900"

.slice(0, 5)
  → 最初から 5 文字だけ切り出す
  → "05:46"
```

| 位置 | 文字 |
|------|------|
| 0 | "0" |
| 1 | "5" |
| 2 | ":" |
| 3 | "4" |
| 4 | "6" |
| 5 | "0" ← ここまで（位置 5 の手前まで） |

結果：`"05:46"`

---

### 【型定義の役割】入口と出口で別々に定義する理由

```typescript
export const formatDate = (
  date: string | number | Date | Dayjs | null | undefined,  // 【入口】
): string => {  // 【出口】
  return date ? dayjs(date).format("YYYY-MM-DD") : "";
};
```

**なぜ両方書くのか？**

| 型定義の場所 | 役割 |
|-----------|------|
| 引数の型 | 「何が入ってくるのか」をチェック → 関数の使用者に制限を教える |
| 戻り値の型 | 「何が出ていくのか」を保証 → 関数の使用者が次の処理を安全に書ける |

**例：**
```typescript
// 戻り値の型がないと...
const result = formatDate(new Date());
console.log(result.toUpperCase());  // OK？NG？わからない

// 戻り値の型があると...
const result: string = formatDate(new Date());
console.log(result.toUpperCase());  // ✅ OK（result は string だから）
```

### 【3-3】Zod の検証ルール（schema.ts）

```typescript
export const recordSchema = z.object({
  date: z.string().trim().min(1, "日付は必須"),
  time: z.string().trim().optional().refine(...),
  author: z.string().trim().min(1, "記録者は必須"),
  content: z.string().trim().optional(),
  vitals: z.object({
    T: optionalNumber(35, 42, "体温は35以上", "体温は42以下"),
    P: optionalNumber(0, 200, "脈拍は0以上", "脈拍は200以下"),
    R: optionalNumber(0, 40, "呼吸は0以上", "呼吸は40以下"),
    SBP: optionalNumber(0, 250, "収縮期は0以上", "収縮期は250以下"),
    DBP: optionalNumber(0, 150, "拡張期は0以上", "拡張期は150以下"),
    SPO2: optionalNumber(0, 100, "SPO2は0以上", "SPO2は100以下"),
  }),
});
```

**検証の例：**

```
入力値：{ date: "2026-11-26", author: "看護師 A", vitals: { T: "36.5", ... } }

Zod がチェック：
✅ date = "2026-11-26" → 文字列で、空じゃない → OK
✅ author = "看護師 A" → 文字列で、空じゃない → OK
✅ vitals.T = "36.5" → 数字で、35以上42以下 → OK
✅ 全部チェック完了...

結果：すべて OK！ → onSubmit を呼び出す
```

---

### 【3-4】検証前後でデータが変わる

| フェーズ | 型 | 例 |
|---------|----|----|
| **検証前（RecordInput）** | 文字列 | `T: "36.5"` |
| **検証後（RecordOutput）** | 数字 | `T: 36.5` |

**理由：** Zod の `optionalNumber()` が `.transform()` で型を変換しているから

```typescript
export const optionalNumber = (min: number, max: number, ...) =>
  z
    .union([z.string(), z.number()])  // 入力は文字列か数字
    .nullish()
    .transform((v) => (v == null ? "" : String(v).trim()))
    .transform((v) => (v === "" ? undefined : Number(v)))  // ← 数字に変換！
    .refine(...)  // 範囲チェック
```

### 【3-6】handleAddRecordSubmit 関数が実行される

```typescript
const handleAddRecordSubmit = async (data: RecordOutput): Promise<void> => {
  // data = Zod で検証済みのデータ
  // {
  //   date: "2026-11-26",
  //   time: "08:30",
  //   author: "看護師 A",
  //   vitals: {
  //     T: 36.5,      ← 数字に変換済み
  //     P: 72,
  //     R: 16,
  //     SBP: 120,
  //     DBP: 80,
  //     SPO2: 98,
  //   },
  //   content: "患者さんは安定している"
  // }

  const savedRecord = await addRecord(data, patient.id);
  //                                ↑
  //                    App.tsx の addRecord 関数を呼び出す
  //                    第1引数: data（入力済みのフォームデータ）
  //                    第2引数: patient.id（患者の ID）

  if (!savedRecord) {
    return;  // ← API が失敗した場合、ここで終了
  }
  
  setIsAdding(false);           // ← フォームを閉じる
  setFormData(createEmptyRecord());  // ← フォームをリセット
};
```

**重要なポイント：**

```
✅ 成功（API が記録を保存した）
  → savedRecord = { id: "123", date: "2026-11-26", ... }
  → if (!savedRecord) = false （実行されない）
  → フォーム閉じる ✅

❌ 失敗（API がエラーを返した）
  → savedRecord = undefined
  → if (!savedRecord) = true （実行される）
  → return （ここで終了、フォーム閉じない）
  → エラーメッセージが画面に表示される
```

## 【新規作成と編集の違い】

### 新規作成（INSERT）
```
データベース：「まだこの記録がない」
  ↓
新しい ID を自動生成
  ↓
新しい行を INSERT する
  ↓
API エンドポイント：POST /api/records
  ↓
フロント関数：addRecord()
  ↓
フォーム送信関数：handleAddRecordSubmit()
```

### 編集（UPDATE）
```
データベース：「既にこの記録がある」
  ↓
既存の ID を使用
  ↓
既存の行を UPDATE する
  ↓
API エンドポイント：PUT /api/records/{id}
  ↓
フロント関数：updateRecord()
  ↓
フォーム送信関数：handleRecordSubmit()
```

**なぜ分ける？**
- SQL の操作が異なる（INSERT vs UPDATE）
- API エンドポイントが異なる（POST vs PUT）
- 送るデータが異なる（id が含まれるか含まれないか）

## 🎯 本日学んだこと

### ✅ 理解した内容

1. **ボタンクリック時の処理**
   - 空のフォームデータを作成
   - 日付と時間を「今」に設定
   - スプレッド演算子で上書き

2. **型定義の役割**
   - 入口（引数の型）：関数が受け付ける形を制限
   - 出口（戻り値の型）：関数が返す形を保証

3. **react-hook-form と Zod**
   - `handleSubmit` が自動で検証を実行
   - 検証前後でデータの型が変わる
   - エラー時と成功時で異なる処理

4. **親子コンポーネント（Props）**
   - 子コンポーネント（Form）は `onSubmit` Props を受け取る
   - 親コンポーネント（List or Item）から異なる関数を渡す
   - 同じ Form でも、渡される `onSubmit` で動きが変わる

5. **新規作成と編集の違い**
   - 新規作成：INSERT（新しい ID を生成）
   - 編集：UPDATE（既存の ID を使用）
   - SQL 操作が根本的に異なるから、フロント側でも処理を分ける

## 💡 ポイント整理

| 概念 | 説明 |
|------|------|
| **スプレッド演算子（`...`）** | オブジェクトのプロパティをすべてコピーして展開 |
| **型定義の入口と出口** | 入口は「受け付ける形」、出口は「返す形」 |
| **Zod 検証** | 入力値をチェックして、エラーか成功かを判定 |
| **react-hook-form** | フォーム検証と入力値管理を簡潔に書くライブラリ |
| **Props による親子通信** | 親が子に関数を渡して、子がそれを実行する |
| **handleAddRecordSubmit 関数** | 検証成功後に API を呼び出し、結果でフォーム閉じるか判定 |
